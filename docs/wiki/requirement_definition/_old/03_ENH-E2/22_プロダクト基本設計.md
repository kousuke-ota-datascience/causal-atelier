## 2. システム境界

### 2.1. 対象コンポーネント

| コンポーネント | 主な責務 |
|---|---|
| Web App | 入力支援、状態表示、操作要求、DAG可視化、比較、Lineage |
| Web API | 認可、validation、Entity操作、状態Gate、Query Projection |
| Execution Worker | 非同期科学計算、Result / Artifact保存、Execution状態遷移 |
| Metadata DB | 7つの正本Entityと状態の永続化 |
| Artifact Store | Datasetおよび生成物の物理保存 |
| Scientific Core | Discovery、Identification、Eligibility、Estimation、Diagnostics、Refutation、Sensitivity |
| Local CLI | Scientific Coreの独立ローカル実行 |

### 2.2. 正本Entity

```text
Project
Dataset Version
Execution
Result
Artifact
Graph Version
Annotation
```

Project Register画面、Graph Candidate、Graph Comparisonおよびモーダルは正本Entityではない。

## 3. システム構成

```text
Analyst / Viewer
      |
      v
   Web App
      |
      v
   Web API ----------------> Metadata DB
      |  \-----------------> Artifact Store
      |
      +--------------------> Execution Worker
                                  |
                                  v
                            Scientific Core
```

Web APIとWorkerは同一codebaseを共有できるが、同期request処理と長時間科学計算を分離する。

## 4. 横断設計原則

### 4.1. 正本とQuery Modelを分離する

- Comparisonは保存しない
- Lineageは明示参照から導出する
- Graph CandidateはResultとGraph Versionから導出する
- UI表示用statusを新しいEntityへ複製しない

### 4.2. 不変Versionを上書きしない

- Dataset Versionは不変
- Execution SnapshotはSubmit後不変
- Resultは不変
- FIXED Graph Versionは不変
- 条件変更は新Executionまたは新Graph Versionとする

### 4.3. 技術状態と科学状態を分離する

```text
Execution.status = SUCCEEDED
Result.scientific_status = NOT_IDENTIFIED
```

は正常な組合せである。UIは`FAIL`という文字列だけで技術失敗と判断してはならない。

### 4.4. Project archiveはLineageを破壊しない

画面上のProject削除はProjectの`ACTIVE → ARCHIVED`である。

- ACTIVE: write可能
- ARCHIVED: read-only
- hard delete: 禁止

### 4.5. Graph Provenanceを保持する

- Algorithm Output: Discovery Result
- 採用版: DISCOVERED Graph Version
- 手動編集: USER_EDITED child Graph Version
- 制約調整: CONSTRAINT_ADJUSTED Graph Version
- FIXED版の直接編集: 禁止

### 4.6. 操作・状態境界をBackendでも強制する

画面でbuttonをdisabledにするだけでは要件を満たさない。Domain / Application Service / APIは同一の前提状態を検証する。

### 4.7. Outcomeを一貫して継承する

```text
Discovery input
→ Discovery Execution Snapshot
→ Discovery Result
→ Graph Version.designated_outcome_node
→ Inference Causal Question
```

InferenceでOutcomeを独立入力させない。

## 5. 利用者向け情報アーキテクチャ

### 5.1. Global Header / Sidebar

- Project selector
- `Project Register & Management` action
- 4つの分析Workspace navigation
- API health
- 科学的負結果と技術失敗の簡潔な説明

### 5.2. 画面構成

```text
Project Register & Management

Project Analysis
├── Project / Data
├── Discovery
├── Inference
└── Results / Lineage
```

Project Register & Managementは分析Workspaceではなく、global管理画面とする。

### 5.3. 全画面共通表示規則

各ページは次を持つ。

1. ページ名
2. このページで行うこと
3. 入力と出力の概要
4. 主要用語の説明
5. 状態により操作できない場合の理由

各セクションは次を持つ。

- title
- purpose
- main action
- prerequisite

主要入力はtooltipまたはhelp textと入力例を持つ。

## 6. Web App情報設計と操作・状態境界

### 6.1. 共通操作表示

| 表示 | 意味 |
|---|---|
| enabled | 現在の正本状態で操作可能 |
| disabled | 操作不可。理由を表示する |
| read-only | 参照可能だが更新不可 |
| hidden | Actorまたは画面文脈上不要。状態制約の代替には使用しない |

APIが状態不整合を返した場合、Frontendは単なる通信失敗ではなく、対象状態と必要操作を表示する。

### 6.2. Project Register & Management

#### 6.2.1. 目的

Projectの登録、ACTIVE Project一覧の確認および利用停止を行う。

#### 6.2.2. セクション

1. Project Register
2. Project List

#### 6.2.3. Project Register

入力:

- Project Name
- Research topic / Business issue
- Objective
- Memo

作成成功後、Project Listへ追加し、必要に応じて当該Projectを選択できる。

#### 6.2.4. Project List

1行1Projectで次を表示する。

- Project Name
- Research topic / Business issue
- Objective
- Memo
- status
- 削除button

#### 6.2.5. Project操作・状態対応

| 操作 | 前提状態 | 読取 | 生成 | 更新 | 操作後 | UI挙動 |
|---|---|---|---|---|---|---|
| Project登録 | なし | なし | Project | なし | ACTIVE | 成功後に一覧へ追加 |
| Project編集 | ACTIVE | Project | なし | metadata | ACTIVE | Project / Dataで編集 |
| Project削除要求 | ACTIVE | Project | なし | なし | 未変更 | 確認modalを表示 |
| 削除確定 | ACTIVE | Project | なし | status | ARCHIVED | selectorから除外、管理画面へ戻る |
| 削除取消 | ACTIVE | Project | なし | なし | ACTIVE | modalを閉じる |
| ARCHIVED Project write | ARCHIVED | Project | なし | なし | ARCHIVED | disabled、理由表示 |

削除確認文は、既存分析来歴は保持されるが新規分析ができなくなることを明記する。

### 6.3. Project / Data Workspace

#### 6.3.1. 目的

選択中Projectの研究テーマと、分析に使用するDataset Versionを管理する。

ページ説明:

> プロジェクトにおいて取り組むリサーチトピックと、使用するDatasetの管理・登録を行います。

#### 6.3.2. セクション

1. Project
2. Datasets
   - Dataset Register
   - Registered Datasets

#### 6.3.3. Projectセクション

Project登録は行わない。選択中ACTIVE Projectのmetadata編集だけを行う。

#### 6.3.4. Dataset操作・状態対応

| 操作 | 前提 | 読取 | 生成 | 更新 | 操作後 | UI挙動 |
|---|---|---|---|---|---|---|
| Dataset登録 | Project=ACTIVE | Project、file | Dataset Version、Artifact | なし | 不変Version | 登録後一覧更新 |
| Dataset preview | Dataset存在 | Dataset、Artifact | なし | なし | 変更なし | table表示 |
| Dataset選択 | Project=ACTIVE | Dataset | なし | UI context | 変更なし | Discoveryへ進行可 |
| Dataset上書き | 任意 | 既存Dataset | なし | なし | 変更なし | 操作を提供しない |

### 6.4. Discovery Workspace

#### 6.4.1. 目的

Dataset列を指定して複数Discoveryを実行し、Algorithm Outputと派生Graph Versionを比較・採用する。

#### 6.4.2. セクション

1. Discovery Setup
2. Discovery Executions
3. Graph Candidates
4. Direct Graph Registration

独立したGraph Version editorセクションは置かない。

#### 6.4.3. Feature columns selector

- 選択Datasetのschema列をcheckbox一覧で表示する
- 0件選択を許可しない
- text fieldは選択結果をcomma-separatedで表示する
- text fieldに既存列名がある場合、modalを開くとcheckedにする
- 存在しない列名はcheckedにしない
- modal確定時、checked列だけでtext fieldを正規化する
- Cancel時は元のtext fieldを変更しない
- 重複を除去し、Dataset schema順または利用者選択順のどちらか一方で固定する

#### 6.4.4. Outcome selector

- 選択Datasetの列から1件選択する
- Feature columnsに含まれる列のみ選択可能とする
- Dataset変更時は現在値を再検証する
- 存在しない場合は未選択へ戻し理由を表示する
- Discovery実行時に必須とする

#### 6.4.5. Discovery Execution操作

| 操作 | 前提 | 生成 | 操作後 | UI Gate |
|---|---|---|---|---|
| Batch作成 | Project=ACTIVE、Dataset、Feature、Outcome、Algorithm有効 | Execution群 | QUEUED | submit enabled |
| status更新 | Execution存在 | なし | 状態に従う | refresh |
| cancel | QUEUED / RUNNING | なし | CANCELLED | terminalではdisabled |
| retry | FAILED | なし | QUEUED | Snapshot変更不可 |
| 条件変更再実行 | terminal Execution | 新Execution | QUEUED | Prefill後に新規submit |

#### 6.4.6. Graph Candidates一覧

Discovery Graph ResultとGraph Versionを統合表示する。

行項目:

- checkbox
- candidate kind
- FIXED flag
- Source Result / Parent Graph
- Graph Type / Origin
- status
- designated outcome
- node / edge count
- summary / warning
- `グラフを確認/編集する`

#### 6.4.7. Graph確認・編集モーダル

表示:

- Graph Type
- Origin
- Source / Parent
- status
- designated outcome
- DAG / CPDAG / PAG可視化
- node一覧
- edge一覧とendpoint semantics
- provenance / warning
- edit rationale

状態別操作:

| 対象 | 表示 | 編集 | FIX | 子DRAFT |
|---|---|---|---|---|
| Discovery Result | read-only | 直接不可 | DISCOVERED版作成として可能 | DISCOVERED root確保後に可能 |
| DRAFT Graph Version | editable | 同一Version更新 | 可能 | 不要 |
| FIXED Graph Version | read-only | 直接不可 | 不可 | 可能 |

##### 6.4.7.1. Discovery Resultの採用

未編集で採用する場合、Result payloadと同一Graphを持つ`DISCOVERED` Graph Versionを作成する。

##### 6.4.7.2. Discovery Resultから編集

Algorithm Outputを直接変更しない。まず同一内容のDISCOVERED rootを確保し、そのFIXED版を親とするUSER_EDITEDまたはCONSTRAINT_ADJUSTED DRAFTを作成する。

##### 6.4.7.3. DRAFT編集

- edge追加 / 削除 / endpoint変更
- rationale更新
- designated outcome変更
- graph validation

同一DRAFT内の更新として扱う。

##### 6.4.7.4. FIX

FIXは新しいGraph Versionを作らず、対象DRAFTをFIXEDへ状態遷移させる。

#### 6.4.8. Graph Comparison

- 2件以上の選択でbuttonをenabledにする
- modalでcandidateごとのtabを表示する
- 各tabでGraphを可視化する
- summaryとしてnode / edge、Origin、Outcome、warningを表示する
- 比較可能な場合はedge add / remove / orientation changeを表示する
- 非互換な場合は個別表示を維持し、差分不能理由を示す
- 生JSONは主要表示としない

### 6.5. Inference Workspace

#### 6.5.1. 目的

FIXED Graph Versionと継承Outcomeを使用し、Identification、Data Eligibility、Estimation、Diagnostics、RefutationおよびSensitivityを実行する。

#### 6.5.2. ページ説明

IdentificationとData Eligibilityについて、利用者向け説明を常時表示する。

- Identification: Graphと仮定から、指定した因果効果が理論上識別できるかを確認する段階
- Data Eligibility: 実データが指定した推定を行うための型、欠測、sample size、overlap等を満たすかを確認する段階

#### 6.5.3. 入力支援

Analysis mode、Population、Comparator、Treatment、Analysis unit、Treatment time、Outcome window、Estimand、Strategy、Adjustment setおよびAssumptionsへtooltipと入力例を付与する。

#### 6.5.4. Outcome

Outcome入力欄を置かない。FIXED Graph選択時に`designated_outcome_node`をread-only表示する。

- Graph未選択: Outcome未表示
- Graph Outcome未指定: Identification disabled
- Graph / Dataset不整合: Identification disabled
- API受付: Causal Question Outcome一致を再検証

#### 6.5.5. Inference操作・状態対応

| 操作 | 前提 | 生成 | 操作後 | UI Gate |
|---|---|---|---|---|
| Identification | Project=ACTIVE、Dataset、FIXED Graph、Outcome有効 | Execution | QUEUED | 入力有効時のみ |
| Estimation | Identification許可、Eligibility Gate通過 | Execution群 | QUEUED | Gate理由表示 |
| WARN override | Eligibility=WARN、reason有 | Estimation Execution | QUEUED | reason必須 |
| Refutation | Treatment Effect Result存在 | Execution | QUEUED | source result選択必須 |
| Sensitivity | Treatment Effect Result存在 | Execution | QUEUED | source result選択必須 |

#### 6.5.6. 科学状態Gate

- `NOT_IDENTIFIED`: 通常Estimation disabled
- Eligibility `FAIL`: Estimation disabled
- Eligibility `WARN`: override reason required
- Diagnostics `FAIL`: Execution技術成功を維持し、警告表示

### 6.6. Results / Lineage Workspace

#### 6.6.1. 目的

Result、科学状態、判断理由、上流条件、Graph ProvenanceおよびArtifactを確認する。

#### 6.6.2. Result表示

- QUEUED / RUNNING: Execution状態のみ表示
- FAILED: 技術errorとlogを表示
- SUCCEEDED + scientific negative: Resultとして表示
- Artifact欠損: Resultは表示し、Artifact errorを分離表示

#### 6.6.3. Comparison

同一Project、同一Result Type、同一Estimand、同一Outcome Scaleおよび同一PopulationのResultを数値比較する。非互換Resultはmetadata比較のみ許可し理由を表示する。

#### 6.6.4. Annotation

- ACTIVE Project: 作成・更新可
- ARCHIVED Project: read-only
- ResultまたはGraph Versionの一方を対象とする

#### 6.6.5. Lineage

```text
Result
→ Execution
→ revision_context.base_execution_id [optional]
→ Input Result Chain
→ Dataset Version
→ Graph Version
→ Source Result / Parent Graph
→ Artifact
→ Annotation
```

## 7. 画面遷移と論理引渡し

| 遷移元 | 遷移先 | 前提 | 引渡し | 遷移先 |
|---|---|---|---|---|
| Management | Project / Data | ACTIVE Project選択 | project_id | Projectを再取得 |
| Project / Data | Discovery | Dataset選択 | project_id、dataset_version_id | schemaを取得 |
| Discovery | Inference | FIXED Graph選択 | project_id、dataset_version_id、graph_version_id | OutcomeをGraphから取得 |
| Discovery | Results | Graph / Result選択 | candidate IDs | Projectionを取得 |
| Inference | Results | Result選択 | result IDs | Result / Lineage取得 |
| Results | Discovery / Inference | 条件変更 | base_execution_id | Prefill後に新Execution作成 |

Entity全体をbrowser stateだけに保持せず、遷移先でAPIから正本を再取得する。

## 9. Worker基本設計

```text
QUEUED
→ Claim
→ Project ACTIVE / Snapshot整合確認
→ Dataset / Graph / Input Result解決
→ Operation dispatch
→ Scientific Core
→ Result / Artifact構築
→ Transaction確定
→ SUCCEEDED
```

受付後にProjectがARCHIVEDとなった場合、既にQUEUED / RUNNINGのExecutionを自動cancelするかはENH-E2で行わない。受付時点で有効だった不変Snapshotとして処理継続を許可する。新規受付だけを禁止する。

## 10. Scientific Core基本設計

ENH-E1の能力を維持する。

- Discovery: PC、GES、Graph Type / Endpoint Semantics
- Identification: RANDOMIZED、BACKDOOR
- Data Eligibility
- Estimation: ATE / ATT
- Diagnostics
- Refutation
- Sensitivity

OutcomeのDAG右端配置はFrontend layoutであり、Scientific CoreのGraph構造を変更しない。

## 11. CLI基本設計

CLIの科学contractは維持する。Web固有のProject管理画面およびmodalはCLIへ実装しない。

CLI manifestはdesignated outcomeを保持し、Web importを将来実装する場合に意味を失わない形式とする。

## 13. 基本設計上の受入れ条件

- Project Register & Managementが分析Workspaceから分離されている
- Project削除がARCHIVED状態遷移として定義されている
- 全主要操作に前提状態と操作後状態がある
- Feature / Outcome selectorの同期規則が定義されている
- Discovery ResultとGraph VersionをQuery Projectionで統合する
- Result、DRAFT Graph、FIXED Graphのmodal操作が区別されている
- FIXとVersion作成が区別されている
- Parent Graphの選択条件が定義されている
- Graph比較が2件以上かつ視覚表示である
- Inference OutcomeがGraph Versionから継承される
- UI GateとBackend validationが同一規則である
- ENH-E1 / E1a科学要件を維持する
