## 1. 実装方針

### 1.1 技術前提

- Python 3.12.x
- FastAPI等のASGI Web Framework
- Pydantic等の型付きSchema Validation
- SQLAlchemy等のORM / SQL Abstraction
- PostgreSQL
- Local Filesystem Artifact Store
- Web APIと別ProcessのWorker

### 1.2 実装原則

- Domain / ApplicationはWeb FrameworkとORM Modelへ直接依存しない
- Application ServiceはPortを介してPersistence、Artifact Store、Scientific Coreを利用する
- Scientific CoreはProduct Domain、DB Repository、Web API Schemaを参照しない
- 7 Entityを維持する
- ComparisonとLineageはQuery Modelとする
- Entity更新とArtifact File書込みの失敗補償を明示する
- 未決事項をCoding Agentが補完しない
- 実装から要件を変更しない

## 4. Snapshot詳細設計

### 4.1 Schema

```text
causal-analysis-spec/2
```

### 4.2 Canonicalization

1. 未知FieldをRejectする
2. Schema Versionを検証する
3. Operationに無関係なFieldをRejectする
4. Key順を固定する
5. UUID、日時、Enumを文字列へ正規化する
6. 非有限FloatをRejectする
7. Dataset / Graph Hash、Input Result IDを含める
8. Canonical JSONを生成する
9. SHA-256 Hashを生成する
10. Submit後の変更を禁止する
11. `causal-analysis-spec/2`の既存payloadを読取可能とする
12. `revision_context`、`scientific_warnings`等の追加任意Fieldはstrict allow-listへ明示追加し、その他の未知Field rejectを維持する

### 4.3 Validation Override

Data Eligibility `WARN`を継続する場合、以下を必須とする。

```json
{
  "reason": "Scientific justification",
  "actor": "user-id",
  "warning_codes": ["LIMITED_OVERLAP"]
}
```

### 4.4. ENH-E1a統合: Revised Execution

API受付の任意入力`base_execution_id`と`change_reason`を比較し、Snapshotの任意`revision_context`へ保存する。

```json
{
  "base_execution_id": "<id>",
  "base_snapshot_hash": "<sha256>",
  "revision_kind": "REVISED",
  "change_reason": "<required when changed>",
  "changed_dimensions": ["analysis_spec.causal_question.outcome"]
}
```

- 同一条件は`RERUN`、`changed_dimensions=[]`
- 条件差分がある場合は非空`change_reason`必須
- Actor / 時刻はExecutionの`requested_by` / `requested_at`
- 旧値は`base_execution_id`が指すSnapshot、新値は現Execution Snapshotから復元する
- Lineage edgeは`revision_context.base_execution_id`から導出

### 4.5. ENH-E1a統合: 探索後推論警告

CONFIRMATORY Estimation受付時、同一Project / Dataset Versionの先行Discoveryを検索し、Snapshotの`scientific_warnings`へ保存する。

```json
{
  "warning_code": "POST_SELECTION_INFERENCE_RISK",
  "message": "...",
  "source_discovery_execution_ids": ["<id>"],
  "dataset_version_id": "<id>",
  "rationale": "..."
}
```

- `source_discovery_execution_ids`は重複除去後の昇順とする
- WarningはExecution statusまたはScientific Statusを変更しない
- API response、prefill、Lineage、Web UIおよびCLI manifestは同じ保存済みpayloadを表示する
- 履歴を持たないローカルCLIは独自に先行Discoveryを推測しない

## 7. Scientific Core Adapter

### 7.1 Port

```python
class ScientificCorePort(Protocol):
    def run_discovery(...) -> list[ScientificResultDescriptor]: ...
    def run_identification(...) -> list[ScientificResultDescriptor]: ...
    def run_estimation(...) -> list[ScientificResultDescriptor]: ...
    def run_refutation(...) -> list[ScientificResultDescriptor]: ...
    def run_sensitivity(...) -> list[ScientificResultDescriptor]: ...
```

### 7.2 Discovery Adapter

- Algorithm Outputを保存する
- BackendがBackground Knowledgeを正式Supportする場合のみAlgorithm Inputへ渡す
- Supportしない場合はPost-hoc Graphを別Versionにする
- Graph Type、Endpoint、Backend Version、Warningを保持する

### 7.3 Identification Adapter

ENH-E1必須:

- RANDOMIZED
- BACKDOOR

Validation:

- DAG要件
- Treatment / Outcome Node
- Adjustment Column
- Treatment / Outcome混入
- Treatment Descendant
- Known Collider
- Back-door Path Blocking

CPDAG / PAGで一意判断できない場合は`REQUIRES_REVIEW`。

ENH-E1a統合規則:

- 全reasonを収集してからstatusを確定する
- 確定的入力不整合、DAG cycle、確定的識別条件違反を`REQUIRES_REVIEW`より優先する
- ColliderはTreatment–Outcome間のback-door path上のcolliderまたはその子孫として理由化する

### 7.4 Data Eligibility

Check Result:

```json
{
  "check_code": "LIMITED_OVERLAP",
  "status": "WARN",
  "message": "...",
  "evidence": {}
}
```

総合Status:

```text
FAIL > WARN > PASS
```

#### 7.4.1. ENH-E1a inferred types

Data Eligibility Result payloadへ次を保存する。

```json
{
  "inferred_types": {
    "treatment": {"type": "BINARY", "evidence": {}},
    "outcome": {"type": "CONTINUOUS", "evidence": {}}
  }
}
```

- Treatment: `BINARY | UNSUPPORTED`
- Outcome: `CONTINUOUS | BINARY | UNSUPPORTED`
- 外部library type objectを保存しない
- prerequisite不成立の後続checkは`SKIPPED_DUE_TO_PREREQUISITE`または`NOT_APPLICABLE`と根拠を保存する
- Estimation受付は保存済みIdentification ResultおよびData Eligibility Resultのみを根拠とする
- Estimatorの4軸、parameter、adjustment、diagnostics前提を`ScientificValidationService`の共通validatorで検証する

### 7.5 Estimation Adapter

- Input Identification Resultを検証する
- Estimator Capability
- inferred Treatment / Outcome Type
- prerequisite不成立時の`SKIPPED_DUE_TO_PREREQUISITE` / `NOT_APPLICABLE`
- Identification status precedence
- Graph designated outcome validation
- Project ACTIVE write guard Registryを参照する
- Treatment EffectとDiagnosticsを別Descriptorで返す
- 未対応OptionをRejectする

### 7.6 Refutation Adapter

必須Method:

- PLACEBO_TREATMENT
- DATA_SUBSET

### 7.7 Sensitivity Adapter

必須Dimension:

- ADJUSTMENT_SET
- PROPENSITY_CLIPPING

## 8. Worker詳細設計

### 8.1 Execution Claim

`FOR UPDATE SKIP LOCKED`等で1件をClaimし、同一Transactionで`RUNNING`へ遷移する。

### 8.2 Explicit Dispatch

```python
match execution.operation:
    case ExecutionOperation.DISCOVERY:
        outputs = core.run_discovery(...)
    case ExecutionOperation.IDENTIFICATION:
        outputs = core.run_identification(...)
    case ExecutionOperation.ESTIMATION:
        outputs = core.run_estimation(...)
    case ExecutionOperation.REFUTATION:
        outputs = core.run_refutation(...)
    case ExecutionOperation.SENSITIVITY:
        outputs = core.run_sensitivity(...)
    case _:
        raise UnsupportedExecutionOperationError(execution.operation)
```

### 8.3 ExecutionProcessor Sequence

1. Executionを再取得する
2. Cancel済みなら終了する
3. Dataset Artifactを取得しHashを検証する
4. Graphを必要に応じて取得する
5. Upstream Resultを必要に応じて取得する
6. Snapshot Hashを検証する
7. Scientific Inputへ変換する
8. Scientific Coreを呼ぶ
9. 1件以上のResult Descriptorを検証する
10. Artifact候補をTemporary領域へ書く
11. Artifact Storeへ保存する
12. Result群、Artifact Metadata、Execution Statusを1 Transactionで保存する
13. Temporary Fileを削除する

### 8.4 Failure Compensation

| Failure | 処理 |
|---|---|
| Input Artifact取得失敗 | `FAILED` |
| Scientific Core技術例外 | Log Artifact保存を試行し`FAILED` |
| Artifact Store保存失敗 | Resultを保存せず`FAILED` |
| Artifact保存後DB失敗 | Orphan Cleanup対象、`FAILED` |
| Scientific Negative Outcome | Result保存、`SUCCEEDED` |
| Cancel要求 | Safe Pointで`CANCELLED` |

## 9. Persistence詳細設計

### 9.1 Migration対象

- `execution.input_result_id`
- `execution.snapshot_schema_version`
- Execution Operation Check Constraint
- Result Type Check Constraint
- Scientific Status Check Constraint
- `graph_version.source_result_id` Nullable化
- `graph_version.graph_origin`
- `graph_version.provenance_json`
- Artifact Type拡張
- FK Index

### 9.2 Migration方針

ENH-E1aの`revision_context`、`scientific_warnings`およびinferred typesは既存JSONへ保存するためDB migration不要である。

ENH-E2では`product_graph_version.designated_outcome_node`をnullable追加する。既存値を推測してbackfillしない。

### 9.3 Project Archive

既存`product_project.status`を使用し、新しい削除flagまたはdeleted tableを追加しない。

### 9.4 Query Projection

Graph Candidate / Comparison用Tableを追加しない。ResultおよびGraph Version repositoryから要求時に構築する。

### 9.5 Migration適用順序

- 空DBへのUpgradeを必須とする
- 旧Metadata DBデータ保持を要件としない
- 旧Run / Attempt互換を追加しない
- Dual-writeを行わない
- DowngradeはRepository規約に従う

## 18. Graph Edit Lifecycle詳細設計

### 18.1. Create Draft from Candidate

Discovery Resultの場合:

1. source Result検証
2. 同一content hashのDISCOVERED Graph Versionを検索
3. なければResultと同一内容のDISCOVERED Graph Versionを作成してFIXED
4. rootを親とするchild DRAFTを作成

FIXED Graph Versionの場合:

1. parent存在 / Project / FIXED検証
2. Graph DocumentとOutcomeをcopy
3. USER_EDITEDまたはCONSTRAINT_ADJUSTED child DRAFT作成

### 18.2. Update DRAFT

- optimistic concurrency用に`content_hash`またはversion tokenを使用する
- FIXEDなら409
- invalid endpoint semanticsなら422
- outcomeがnodeにない場合422

### 18.3. FIX

1. DRAFT取得
2. Graph validation
3. Outcome validation
4. rationale validation
5. content hash再計算
6. status=FIXED
7. commit
