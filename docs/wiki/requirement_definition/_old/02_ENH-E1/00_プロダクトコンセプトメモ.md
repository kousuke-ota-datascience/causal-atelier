## 1. 文書の目的

本書は、Ariadneが解決する問題、提供する価値、初期実装の対象範囲および設計原則を定義する。

初期版の目的は、分析管理機能を網羅的に実装することではない。次の価値仮説を、利用者が検証可能な最小構成で確かめることである。

> 複数の因果探索・因果推論結果を比較し、採用した結果について、使用データ、Graph、アルゴリズム、パラメータおよび判断理由まで遡れることは、分析者の判断品質と再現性を改善するか。

## 2. プロダクトの一文定義

> **Ariadneは、前処理済みデータに対してGraphを探索・登録し、識別可能性、データ適格性、因果効果、診断、反証および感度を段階的に評価し、その条件・結果・判断理由を一つの分析来歴として確認できるワークスペースである。**

短く表現すると、次のとおりである。

> **何を変えて試し、何が変わり、なぜその結果を採用したかを残す。**

## 3. 初期版が解決する問題

Notebook、CLI、ファイル名および個別の実験追跡だけでは、次の情報が分散しやすい。

1. どの前処理済みデータを使ったか
2. どの因果探索アルゴリズムとパラメータを使ったか
3. 複数のGraph結果にどのような差があったか
4. どのGraphを推論入力として採用したか
5. なぜそのGraphを採用・修正したか
6. treatment、outcome、estimandおよび調整集合は何か
7. どの推定器を使用し、推定結果とdiagnosticsがどう異なったか
8. 数値結果を採用できない理由は何か
9. 結果からデータ、Graph、設定、コードおよびArtifactへ遡れるか

初期版では、これらを少数の正本Entityと4つの作業Workspaceで管理する。

## 4. 対象利用者

### 4.1 主利用者: Analyst

基本的な統計・因果推論の知識を持ち、Python、NotebookまたはCLIで分析している利用者。

初期版では、非専門家へ因果推論を自動化することを目的としない。

### 4.2 参照利用者: Viewer / Reviewer

Analystが残したResultと来歴を読み、結果の採用可能性を確認する利用者。

初期版では独立した承認ワークフローやレビューEntityを設けず、Results / Lineage Workspaceのread-only利用で検証する。

## 5. 対象利用場面

### 5.1 Golden Path: 売上改善

例:

- クーポン配布と売上の因果構造候補を探索する
- PC、GES等の結果を比較する
- PCのalphaを変更し、Graph構造の感度を確認する
- 採用Graphを用いて、クーポン配布のATEまたはATTを推定する
- 複数推定器の推定値、信頼区間、overlapおよびbalanceを比較する

### 5.2 Transfer Case: 退職者抑制

初期版の構造を人事データへ適用し、次を確認する。

- 予測因子と因果因子を混同しないか
- 介入可能変数と不変属性を区別できるか
- 機微属性を分析条件として明示できるか

生存時間分析、time-varying confoundingおよび自動的な対象者選定は初期対象外とする。

### 5.3 Transfer Case: 従業員エンゲージメント向上

初期版の構造を用いて、変数をOutcome、Mediator、Confounder等として扱う際の実務上の理解可能性を確認する。

階層モデル、反復測定および尺度モデルは初期対象外とする。

## 6. ENH-E1統合後の分析サイクル

```text
Projectの目的・分析メモ
  ↓
前処理済みDataset Versionを登録
  ↓
因果探索を実行、またはUser-defined / Imported Graphを登録
  ↓
Graph結果・Graph provenanceを比較
  ↓
採用Graph Versionを選択・必要に応じて修正・固定
  ↓
Research Context / Causal Question / Causal DesignをExecution Snapshotへ固定
  ↓
Identificationを実行
  ├─ IDENTIFIED
  ├─ NOT_IDENTIFIED
  ├─ PARTIALLY_IDENTIFIED
  └─ REQUIRES_REVIEW
  ↓
Data Eligibilityを確認
  ├─ PASS
  ├─ WARN（理由付きoverride可）
  └─ FAIL
  ↓
許可された場合のみ、複数推定器でATE / ATTを推定
  ↓
Treatment EffectとDiagnosticsを分離して比較
  ↓
Refutation / Sensitivityを実行
  ↓
採用結果、判断理由、仮定および限界をAnnotationへ記録
  ↓
ResultからIdentification、Dataset、Graph、実行条件およびArtifactへ遡る
```

Discoveryは必須前段ではない。User-definedまたはImported Graph VersionからIdentificationを開始できる。
## 7. 設計原則

### 7.1 比較を中心に設計する

Ariadneの中心操作は単一Executionの閲覧ではなく、複数Execution / Resultの比較である。

比較では、少なくとも次を分けて表示する。

```text
同一条件
変更条件
結果差分
```

### 7.2 分析来歴を不変snapshotで保持する

初期版では、Research Context、Experiment、Analysis DefinitionおよびExecution Planを独立Resourceにしない。

Executionが次の不変snapshotを保持する。

- objective / question memo
- 分析方針の選定理由
- 使用Dataset Version
- operation
- algorithm / estimator
- parameter
- Causal Design
- 使用Graph Version
- code / runtime version

これにより、問いに相当する文脈から成果物までの主要な来歴を保持する。

### 7.3 概念、Entity、テーブルおよび画面を分離する

```text
意味論上区別する概念
≠ 独立Entity
≠ 独立テーブル
≠ 独立画面
```

初期版では、利用者の作業単位に合わせて画面を統合する。

### 7.4 因果探索結果のGraph semanticsを保持する

PCやGES等の出力を一律にDAGとして扱わず、Graph種別およびendpoint semanticsを保持して表示する。

次を区別する。

- Algorithm Output Graph
- Selected / Edited Graph Version
- Estimation Input Graph Version

### 7.5 数値を返せない状態を分析結果として扱う

次は技術障害と区別する。

- `NOT_IDENTIFIED`
- `INSUFFICIENT_OVERLAP`
- `INSUFFICIENT_SAMPLE`
- `ESTIMATION_UNRELIABLE`

初期版は、無理にATE/ATTを返さず、理由をResultとして保存する。

### 7.6 ResultとArtifactを分離する

- Result: Graph構造、効果推定値、diagnostics等の論理結果
- Artifact: JSON、CSV、画像、report、manifest等の物理生成物

### 7.7 計算条件の変更は別Executionとする

Algorithm、parameter、Dataset Version、Graph VersionまたはEstimatorを変更した利用者再実行は別Executionである。

技術的retryは同じExecutionとして扱う。ただし、初期版ではStage / Attemptを独立Entityにせず、Executionのretry情報として保持する。

### 7.8 Research Contextは段階的かつフラットに整理する

分析開始時に、完成したResearch Questionや階層構造を必須としない。初期版では、Research Contextに相当する目的、問題意識および問いを、ProjectメモまたはExecution snapshotとしてフラットに保持する。

将来、Research Contextを独立管理する場合も、正本はフラットなContextと任意のrelationを基本とする。relationの例は次のとおりである。

- `REFINES`
- `DERIVED_FROM`
- `SUPERSEDES`
- `RELATED_TO`

ツリー表示が必要な場合は、これらのrelationから生成するProjectionとして扱う。

### 7.9 要件定義書正本原則

要件定義書は常にシステムの正本である。

設計書、実装指示書、ソースコード、DBスキーマ、API、UIおよびテストは、承認済み要件定義書から一方向に導出する。

実装調査で不足または矛盾が判明した場合は、実装を停止し、要件変更提案、承認、要件定義書更新、下位設計更新、トレーサビリティ再確認の順で処理する。

## 8. ENH-E1スコープ

### 8.1 MUST

- Project作成と目的メモ
- 前処理済みDataset Versionの登録
- Dataset previewと基本schema確認
- 複数因果探索Execution
- User-defined / Imported Graph Versionの登録
- Algorithm Output、Constraint Adjusted、User Edited Graphの区別
- DAG / CPDAG / PAGおよびendpoint semanticsの保持
- Algorithm / parameter差分とGraph差分の比較
- Graph Versionの選択・簡易修正・固定
- Research Context、Causal Question、Causal Designの構造化Snapshot
- `EXPLORATORY` / `CONFIRMATORY`の区別
- Identification Execution
- Data Eligibility Result
- Estimation前Validation Gate
- 二値TreatmentのATE / ATT
- 複数Estimatorの実行・比較
- Treatment EffectとDiagnosticsの分離
- Placebo Treatment / Data Subset Refutation
- Adjustment Set / Propensity Clipping Sensitivity
- 科学的に採用できないResultの表示
- ResultからIdentification、Dataset、Graph、algorithm、parameter、codeおよびArtifactへの遡及
- 採用理由、仮定および限界のメモ
- Synthetic / Semi-synthetic Scientific Benchmark

### 8.2 SHOULD

- Dataset Versionを変更した再評価
- read-only共有
- portable manifest / result export
- Graphの禁止edge、必須edge、時間順序制約
- Primary Estimand / Primary Outcomeの固定
- Random Common Cause / Bootstrap Refutation
- Outcome Model / Sample Inclusion Rule Sensitivity

### 8.3 ENH-E1対象外

- Research Contextの独立Resource / Version
- Experimentの独立Workspace
- Analysis Definitionの独立Resource
- Interpretation / Claimの正式なVersion管理
- Comparisonの保存Resource
- 汎用Lineage Relation Entity
- Research Contextの階層編集UI
- 独立したレビュー・承認ワークフロー
- Stage Execution / Stage Attemptの詳細管理
- 詳細なRBAC
- 連続Treatment
- CATE / HTE
- 時系列・生存時間・反復介入
- IV、DiD、RDD、Synthetic Control
- policy optimization
- Monitoring / effect drift
## 9. ENH-E1の成功条件

Analystが次を一連の操作で完了できた場合、ENH-E1の価値仮説を支持する。

1. 前処理済みデータを登録する
2. 複数の探索条件を実行するか、Graphを直接登録する
3. Graph差分とprovenanceを確認して採用Graphを決める
4. Causal Question / Designを固定してIdentificationを実行する
5. `NOT_IDENTIFIED`を正常な分析結果として確認できる
6. Data Eligibilityの`PASS / WARN / FAIL`を確認できる
7. 許可されたIdentification Resultを複数推定器で再利用する
8. Treatment EffectとDiagnosticsを分離して比較する
9. Refutation / Sensitivityを確認する
10. 採用または不採用の理由、仮定、限界を記録する
11. 後から、使用データ、Graph、Identification、推定条件およびArtifactを復元する
## 10. 将来構想との関係

ENH-E1は、科学的方法論の基礎段階を7 EntityとExecution Snapshotへ再写像する。

独立したライフサイクル、検索、共有、承認、再利用またはVersion差分の必要性が利用実績で確認された概念だけを、将来独立Resourceへ昇格させる。

候補は次のとおりである。

- Research Context
- Experiment
- Analysis Definition Version
- Interpretation / Claim
- Comparison
- Lineage Relation
- Stage Execution / Stage Attempt

分析方式の拡張候補は次のとおりである。

- ENH-E2: 連続Treatment、CATE / HTE、DML、Causal Forest
- ENH-E3: IV、DiD、RDD、Synthetic Control、時系列、生存時間、Mediation
- ENH-E4: Policy、Monitoring、正式Review / Approval

将来構想を理由としてENH-E1へEntity、Table、Workflowまたは互換層を先行追加してはならない。
