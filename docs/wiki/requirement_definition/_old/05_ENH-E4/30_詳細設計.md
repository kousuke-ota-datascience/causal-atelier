## 1. 実装原則

- DomainはFramework / ORM / external analytical objectへ依存しない
- Application ServiceはUnit of WorkとPortを利用する
- Scientific / ML libraryはAdapterへ隔離する
- すべてのsnapshotはstrict schema、canonical JSON、hashを持つ
- Runnerはpure input / output contractに近付け、DB transactionを直接操作しない
- Workerがtransaction、status、Artifact commitを制御する
- Product packageから移行用moduleまたは外部分析libraryへの直接importを禁止する

## 5. Canonicalization Algorithm

```python
def canonical_bytes(schema, payload):
    schema.validate(payload, reject_unknown=True)
    normalized = schema.normalize(payload)
    reject_non_finite_float(normalized)
    reject_external_objects(normalized)
    return json.dumps(
        normalized,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    ).encode("utf-8")
```

hashは`sha256(canonical_bytes)`。ID、timestamp等のhash除外FieldをSchemaで明示する。

## 11. Generic Executor Sequence

```text
canonical lifecycle/application service claims Execution and provides an owned workflow context
  ↓
load immutable Plan and snapshots
  ↓
validate runner capability fingerprint
  ↓
canonical lifecycle/application service marks Execution RUNNING; GenericExecutor performs workflow execution within the owned context
  ↓
for each ready Stage:
    resolve input bindings
    create / increment attempt
    mark RUNNING
    runner.validate
    runner.run to temporary outputs
    validate Result / Artifact schemas
    return validated temporary outcomes; canonical lifecycle/application service commits metadata and promotes artifacts
    mark SUCCEEDED or FAILED
  ↓
if required stage failed: canonical lifecycle/application service commits Execution FAILED
elif cancelled: canonical lifecycle/application service commits Execution CANCELLED
else: canonical lifecycle/application service commits Execution SUCCEEDED
```

### 11.1. Transaction Boundary

- Stage status RUNNING transaction
- Runner computation outside long DB transaction
- Result / Artifact metadata / Lineage / Stage successを一つのUnit of Workでcommit
- object promotionはtwo-phase相当のcompensationを持つ

### 11.2. Retry

- retryable error codeのみ自動または手動retry可能
- attemptごとのerror、worker、timestampsを保持
- random seedとinput snapshotを変更しない
- code versionを変更するretryはREVISED Executionとする

### 13.3. Identification Status

- 全reasonを収集してからstatusを決定する
- 確定的input mismatch、DAG cycle、識別条件違反は`REQUIRES_REVIEW`より優先する
- `IDENTIFIED | NOT_IDENTIFIED | PARTIALLY_IDENTIFIED | REQUIRES_REVIEW`
- collider判定はback-door path上のcolliderまたはその子孫へ限定する

### 13.4. Data Eligibility

検査:

- treatment inferred type: BINARY / UNSUPPORTED
- outcome inferred type: CONTINUOUS / BINARY / UNSUPPORTED
- missingness
- sample size
- post-treatment candidate
- overlap

外部dtype objectを保存しない。前提不成立Stageは`SKIPPED_DUE_TO_PREREQUISITE`またはResult上の`NOT_APPLICABLE`で表す。

### 13.5. Estimator Gate

保存済みIdentification ResultとData Eligibility Resultのみを根拠とする。UI入力またはclient申告でgateを迂回しない。WARN overrideはreason、actor、warning codesを必須とする。

### 13.6. Revised Execution

- canonical snapshot同一: `RERUN`
- 差分あり: `REVISED`
- REVISEDは非空`change_reason`
- `changed_dimensions`をcanonical diffから決定論的生成
- `base_execution_id`でLineage edge生成

### 13.7. Post-discovery Warning

CONFIRMATORY Estimation受付時に、同一Projectかつ同一Dataset Versionの先行Discoveryを検索する。

- source execution IDsを重複除去して昇順保存
- warningはExecution成否またはscientific statusを変更しない
- API、prefill、Lineage、UIは同一保存payloadを表示
- CLIが独自推測しない

## 14. Predictive Capability

### 14.1. Prediction Question

必須:

- prediction_unit
- target
- prediction_time
- horizon
- intended_use
- deployment_population

`target`とfeatureは同一列を許可しない。

### 14.2. Split Runner

outputはrow indexまたはstable row identifierのpartition Artifactとする。

検証:

- train / validation / test intersection = empty
- unionが対象populationと整合
- group strategyではgroup intersection = empty
- time strategyでは`max(train_time) < min(validation_time) <= max(validation_time) < min(test_time)`等のpolicy
- stratifyはclassificationのみ
- class count不足をwarning / reject

### 14.3. Leakage Validator

`FeatureAvailability`:

```json
{
  "column": "purchase_after_30d",
  "available_at": "OUTCOME_WINDOW_END",
  "allowed": false
}
```

Rule:

- target derivative禁止
- prediction time後のfeature禁止
- split key由来の直接識別子はpolicyでwarning / reject
- preprocessing statisticを全dataから計算しない
- test metricをtuning objectiveへ渡さない

### 14.4. Prepare Runner

- train partitionでfitするPipeline objectを定義
- validation / testへtransformのみ適用
- fitted preprocessorをArtifact化
- output feature schemaとfeature orderを固定

### 14.5. Train Runner

Input:

- train partition
- validation partitionまたはCV folds
- preprocessor definition
- model spec
- seed

Output:

- fitted model Artifact
- fitted preprocessor Artifact
- training history
- selected hyperparameters
- validation metric

Model objectはpickle等の物理Artifactとし、Result JSONにはlibrary-neutral descriptorを保存する。

### 14.6. Evaluate Runner

- frozen model / preprocessorをload
- untouched test partitionに一度適用
- prediction Artifactを保存
- classification: ROC-AUC、PR-AUC、log loss、Brier、threshold metrics、calibration
- regression: MAE、RMSE、R²、residual summary
- metricにはsample countとevaluation populationを含める

### 14.7. Explain Runner

- explanation datasetとsamplingを明示
- global feature importance
- optional local explanations
- method、background data、model output scaleを保存
- Result labelは`PREDICTIVE_EXPLANATION_RESULT`
- 因果用語を使用しない

## 19. Persistence Mapping

主要Table候補:

- `product_research_context_version`
- `product_dataset_version`
- `product_analysis_view`
- `product_analysis_specification`
- `product_execution_plan`
- `product_execution`
- `product_stage_execution`
- `product_result`
- `product_artifact`
- `product_graph_version`
- `product_annotation`
- `product_lineage_edge`

Persistence rule:

1. Immutable Resourceは更新APIを持たず、新Versionまたは新Resourceを作る。
2. Stateful Resourceのstatus transitionはoptimistic lockまたはrow lockで直列化する。
3. Execution、StageExecution、Result、Artifact metadataおよびLineageのcommit境界をUnit of Workで定義する。
4. JSON payloadは保存前にSchema validation、canonicalizationおよびhash生成を行う。
5. Foreign keyで表現できる所有関係はcolumnを正本とし、横断関係のみLineageEdgeへ保存する。
6. Projectを跨ぐforeign keyおよびLineageEdgeを拒否する。
7. Soft delete対象とimmutable audit recordを区別し、Resultの物理削除はretention policyに従う。

## 19.1. ENH-E4 lineage writer and projection contract

Relation authority is selected before persistence or projection.

- If a relation is classified TYPED_STRUCTURAL in the logical-data allowlist, its typed structural writer is authoritative. A generic authoritative write for the same semantic relation is rejected or not performed.
- If a relation is classified GENERIC_ONLY, the generic-only lineage writer may persist the relation as the authority. The writer validates the approved semantic source/target class and does not reinterpret a structural relation as generic-only.
- Family workflow services do not dual-write a TYPED_STRUCTURAL relation to a generic LineageEdge merely because a current generic edge name such as USED_INPUT, GENERATED, DERIVED_FROM, or REVISED_FROM exists.
- Closure/traversal reads the typed structural authorities and generic-only authorities and returns a projection. It is not a third authority, and overwrite/deduplication during projection does not resolve an underlying authority conflict.
- Export may emit synthetic or derived relation representations and should preserve the source classification TYPED_STRUCTURAL or GENERIC_ONLY. Export output is not persistence authority.

## ENH-E4 approved detailed contract delta

| Area | Approved contract |
|---|---|
| Execution identity | 一つのcanonical persistent identity。family/typeはworkflow discriminator。 |
| State / mutation | 共通state transition、retryはsame ID/new attempt、rerun/reviseはnew ID、cancelはterminal/partial-output policyを明示。 |
| Claim / lease | 一つのcanonical repository/serviceがatomic ownershipを取得。 |
| Stage | 全canonical Executionにpersistent StageExecution、runner internalsから独立したstate/attempt query。 |
| GenericExecutor | claim、commit、retry、canonical Result/Artifact persistenceをしない。 |
| Result / Artifact | ExecutionResult/StageResultを明示し、one metadata ownershipとArtifactStorePortを分離。 |
| Lineage | typed structuralまたはgeneric-only。generic edgeはallowlist、scope、endpoint、uniqueness、deletionを検証。closure/exportはprojection。 |
| Legacy / science | legacy runtime/orchestrationをProduct authorityにせず、shared scientific implementationは保持。 |
| Bootstrap | `alembic_product.ini`→`product_migrations`。root legacy migrationはhistory-only。 |
| Compatibility / CLI | external compatibilityは別decision、utility CLIは第二persistent lifecycleを作らない。 |
