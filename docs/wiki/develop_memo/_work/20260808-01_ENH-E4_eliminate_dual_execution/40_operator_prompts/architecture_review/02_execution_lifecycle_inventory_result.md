## 3. Lifecycle Unit Details

### E4-LC-001 — Causal Product Execution

#### Purpose / User-facing Concept

Web/API causal operations: `DISCOVERY`, `IDENTIFICATION`, `ESTIMATION`, `REFUTATION`, and `SENSITIVITY`. The endpoint accepts a batch of variants and returns newly created execution IDs (`src/ariadne/interfaces/web_api/routers/executions.py:54-98`).

#### Entry Points

`POST /api/v1/projects/{project_id}/execution-batches` submits; generic product cancel/retry endpoints are at `src/ariadne/interfaces/web_api/routers/executions.py:124-131`.

#### Identity

`Execution.execution_id` is generated by `uuid.uuid4()` (`src/ariadne/product/domain/execution.py:18-24`). `batch_key` is separately generated by `ExecutionService` once per submitted batch (`src/ariadne/product/application/execution_service.py:86-88`). The API exposes both (`src/ariadne/interfaces/web_api/routers/executions.py:30-50,86-93`). `input_result_id` is an upstream Result relation for operations that require it; `base_execution_id` is not a column on the entity but is embedded in `analysis_spec_json["revision_context"]` (`execution_service.py:156-162,317-365`).

#### Domain Entity

`ariadne.product.domain.execution.Execution` contains identity, operation, input snapshot, status, retry count, timestamps, and transition methods (`src/ariadne/product/domain/execution.py:22-47,83-114`).

#### Persistence

`ExecutionService` constructs entities and calls `uow.executions.add_many` (`src/ariadne/product/application/execution_service.py:190-213`). `SqlUnitOfWork.executions` returns `SqlExecutionRepository` (`src/ariadne/product/persistence/unit_of_work.py:18-47`), which maps the domain entity to `ExecutionOrm` and persists it to `product_execution` (`src/ariadne/product/persistence/repositories.py:140-196,354-393`; `src/ariadne/product/persistence/orm_models.py:118-168`). The physical primary key is `product_execution.execution_id` (`product_migrations/versions/20260805_product_0001_baseline.py:46-86`; current operation/input constraints are extended by `20260806_product_0002_enh_e1.py:18-70`).

#### Initial Creation

Initial state is `QUEUED` by the domain default (`execution.py:41`) and ORM/schema default (`orm_models.py:140-141,156-159`). `create_execution_batch` validates inputs, constructs one entity per variant, adds all entities, and commits (`execution_service.py:120-213`).

#### State Machine

The explicit domain transitions are:

| From | Trigger | To | Symbol | Transaction Boundary | Evidence |
|---|---|---|---|---|---|
| `QUEUED` | worker claim | `RUNNING` | `SqlExecutionRepository.claim_next` | claim mutation is flushed; caller commits | `src/ariadne/product/persistence/repositories.py:372-387`; `src/ariadne/interfaces/worker/runner.py:73-81` |

#### Worker Claim

`SqlExecutionRepository.claim_next` selects status `QUEUED`, orders by `requested_at`, uses `FOR UPDATE SKIP LOCKED`, sets `RUNNING`, `started_at`, and a worker token, then flushes. The enclosing worker UoW commits before processing (`repositories.py:372-387`; `runner.py:73-81`). No lease expiry or heartbeat field is present on `ExecutionOrm`; only `_worker_token` is mapped (`orm_models.py:140-148`).

#### Processing Boundary

`ExecutionProcessor.process` verifies that the claimed row is still `RUNNING`, then `_dispatch_generic` builds a causal plan, registers causal runners, and invokes `GenericExecutor.execute` (`src/ariadne/interfaces/worker/execution_processor.py:40-64,180-215`).

#### GenericExecutor Relationship

The executor receives an already existing execution ID and plan; it validates and sequences stages, resolves bindings, invokes runners, and returns an outcome. It does not create or persist the product Execution (`src/ariadne/product/workflow/executor.py:29-56,57-127`).

#### Stage Lifecycle

No product ORM stage rows are created by the causal submission or processor path. `CausalPlanner` and `GenericExecutor` create/use in-memory `StageExecution` domain objects (`execution_processor.py:189-215`; `src/ariadne/product/domain/stage_execution.py:24-73`). Therefore persistent causal stage table: `NONE_CONFIRMED`.

#### Cancellation

Cancellation is immediate at the product row level: `QUEUED` or `RUNNING` becomes `CANCELLED` in `request_cancel`. During processing, `_is_cancelled` reads the row and causes the processor to stop at its cancellation checks (`execution.py:102-105`; `execution_processor.py:92-107,275-287`). No intermediate state or confirmed interruption of an already-running scientific function is present in this static path.

#### Retry

Retry is supported only from `FAILED`. It reuses the same row and `execution_id`, resets timestamps/error, increments `retry_count`, and returns to `QUEUED` (`execution.py:107-114`; `execution_service.py:259-270`). It does not create a new row or new ID.

#### Rerun

No separate causal rerun endpoint or service method was confirmed. Causal batch submission can accept `base_execution_id` and records a `RERUN` or `REVISED` context in the new execution snapshot when the batch is submitted (`execution_service.py:156-162,317-365`). The new execution is generated by the normal constructor path and therefore has a new ID (`execution.py:18-24,190-210`).

#### Revise

No separate causal revise endpoint was confirmed. The generic batch path can record `revision_kind="REVISED"` when a base execution and changed conditions are supplied (`execution_service.py:352-364`).

#### Failure Handling

Scientific descriptors are converted to product `Result` objects, artifacts are stored, then both are persisted and the Execution is marked succeeded in one UoW (`execution_processor.py:109-171`). Exceptions clean stored artifact keys and mark a still-running Execution failed (`execution_processor.py:172-178,280-287`).

#### Terminal Completion

Terminal statuses are `SUCCEEDED`, `FAILED`, and `CANCELLED` by enum/table constraint. Product result rows reference `product_execution.execution_id` (`src/ariadne/product/persistence/orm_models.py:171-182`; `product_migrations/versions/20260805_product_0001_baseline.py:88-102`).

#### Result Linkage Boundary

`ExecutionProcessor` creates Result IDs through `Result` construction and persists them with the execution state update; `ResultOrm.execution_id` is the direct foreign key (`execution_processor.py:109-130,159-171`; `orm_models.py:171-182`). Detailed Result/Artifact lifecycle is outside this phase.

#### Transaction Boundaries

Submission, claim, cancel, retry, completion, and failure each have explicit commit points. Claim is committed before scientific processing; completion couples product Result/Artifact metadata writes with terminal state in one UoW. Artifact-store writes occur before the database transaction and are compensated on persistence failure (`execution_processor.py:133-178`).

Primary evidence: `src/ariadne/product/domain/execution.py:22-114`; `src/ariadne/product/application/execution_service.py:67-270`; `src/ariadne/product/persistence/repositories.py:354-393`; `src/ariadne/product/persistence/orm_models.py:118-182`; `src/ariadne/interfaces/worker/execution_processor.py:40-215,280-287`.

#### Stage Lifecycle

Persistent `FamilyStageExecutionOrm` rows are created per plan stage (`predictive_workflow_service.py:211-222`). In-memory `StageExecution` state and attempts are projected back into rows by `_write_stage_state` (`predictive_workflow_service.py:490-499,1116-1135`). Stage statuses include `PENDING`, `READY`, `RUNNING`, `SUCCEEDED`, `FAILED`, and `SKIPPED_DUE_TO_PREREQUISITE` (`src/ariadne/product/domain/enums.py:29-35`; `orm_models.py:474-493`). Retry resets all stages to `PENDING` and clears attempt/binding data (`predictive_workflow_service.py:662-671`).

#### Cancellation

Cancel is immediate at the execution row: only `QUEUED` or `RUNNING` is accepted; row becomes `CANCELLED`, lease/token are cleared, and pending/ready stages become `SKIPPED_DUE_TO_PREREQUISITE` (`predictive_workflow_service.py:612-628`). During GenericExecutor processing, the `cancelled` callback checks for execution `CANCELLED` or worker-token mismatch (`predictive_workflow_service.py:323-333`), so static evidence confirms cooperative observation at executor checks, not interruption of an already-running scientific call.

#### Retry

Retry is allowed only from `FAILED`; it reuses the same row and ID, increments `retry_count`, removes family Results/Artifacts and related lineage, clears error/timestamps/worker fields, resets all stage rows to `PENDING`, commits, then deletes physical artifact objects (`predictive_workflow_service.py:630-676`).

#### Rerun

Rerun is allowed from `SUCCEEDED`, `FAILED`, or `CANCELLED`. It creates a new Execution ID using the existing specification, plan, and seed, passes `base_execution_id`, and records `revision_kind="RERUN"` (`predictive_workflow_service.py:678-694`). It does not reuse the source row.

#### Revise

Revise is allowed from `SUCCEEDED`, `FAILED`, or `CANCELLED`. It creates a new plan for a supplied specification, then creates a new Execution with `base_execution_id` and `revision_kind="REVISED"` (`predictive_workflow_service.py:696-718`). This differs from rerun in plan/specification selection.

#### Failure Handling and Terminal Completion

On normal executor completion, each stage is projected, family Results/Artifacts and lineage are written, execution status is set to outcome status, lease/token are cleared, and the session commits (`predictive_workflow_service.py:490-499`). On exception, stored objects are deleted and the execution/stage rows are marked failed in a separate session (`predictive_workflow_service.py:500-540`).

#### Result Linkage Boundary

Family Result rows reference both `execution_id` and `stage_execution_id`; Family Artifact rows reference execution, stage, and optionally Result (`orm_models.py:496-535`). The service writes these rows before terminal state commit (`predictive_workflow_service.py:355-499`).

#### Transaction Boundaries

Plan creation, submission, claim, completion, failure handling, cancel, and retry have separate direct-session transactions. Rerun/revise perform a source-state check in one session and create the new row in later transaction(s); no single transaction spans the precondition read and new submission.

### E4-LC-005 — Legacy Web Execution

#### Purpose / User-facing Concept

Legacy Web/API execution of configured pipeline stages, including dry-run/validation-only modes and asynchronous execution.

#### Entry Points

Legacy API root and execution router are code-level candidates from Phase 01. The router creates an Execution through legacy `ExecutionService.create` (`src/ariadne/legacy/interfaces/api/routers/executions.py:33-60`; `src/ariadne/legacy/application/run_execution/services.py:718-865`).

#### Identity

`ariadne.legacy.domain.metadata.Execution.id` is the primary key, generated by `new_id`; it has an optional self-FK `retry_of_execution_id`, idempotency key, and MLflow IDs (`src/ariadne/legacy/domain/metadata.py:561-621`). The observed retry implementation mutates the same row and does not create a new ID (`legacy/application/run_execution/services.py:899-941`).

#### Persistence

Legacy `Execution` maps to physical table `execution`, `ExecutionPlanRecord` to `execution_plan`, `StageExecution` to `stage_execution`, and `StageAttempt` to `stage_attempt` (`legacy/domain/metadata.py:561-696`). Creation writes the execution, plan, stages, dependencies, validation rows, events, and outbox event (`legacy/application/run_execution/services.py:773-865`). The legacy migration defines the corresponding structures, with historical `run` names renamed by `migrations/versions/20260803_0003_rename_run_to_execution.py:35-70`.

#### Initial Creation and State Machine

Creation chooses terminal `FAILED`/`SUCCEEDED` for `DRY_RUN` or `VALIDATE_ONLY`, otherwise `QUEUED` (`legacy/application/run_execution/services.py:765-781`). Worker processing observes terminal states, handles `CANCEL_REQUESTED`, sets `VALIDATING`, then `RUNNING`, and completes `SUCCEEDED` or `FAILED` (`src/ariadne/legacy/workers/executor.py:172-198,278-298`). The legacy API writes `CANCEL_REQUESTED` and emits a `CANCEL_EXECUTION` outbox event (`legacy/interfaces/api/routers/executions.py:104-138`).

#### Worker Claim

The legacy worker claims `OutboxEvent` rows whose `published_at` is null and whose claim is absent/stale, orders by `created_at`, uses `FOR UPDATE SKIP LOCKED`, and records `claimed_at`/`claimed_by` (`src/ariadne/legacy/workers/state_management.py:21-80`). The worker then dispatches `EXECUTE_EXECUTION` or `CANCEL_EXECUTION` (`src/ariadne/legacy/workers/executor.py:154-170`). Stage attempts have lease fields and are marked `LOST` when stale attempts are found (`state_management.py:83-135`); no heartbeat update method was confirmed.

#### Processing / Stage Lifecycle

Legacy stages are persistent and processed in ordinal order. Stage attempts are created, stage start/success/failure and events are committed at separate boundaries (`legacy/workers/executor.py:199-250,251-293`). The legacy pipeline executor is a distinct in-memory stage runner dispatcher (`src/ariadne/legacy/application/pipeline/execution.py:37-74`), not the product `GenericExecutor`.

#### Cancellation

Legacy cancellation is two-step: API mutation to `CANCEL_REQUESTED`, then outbox dispatch/worker observation; `_finish_cancelled` sets execution `CANCELLED` and unfinished stages `CANCELLED` (`legacy/interfaces/api/routers/executions.py:104-138`; `src/ariadne/legacy/workers/state_management.py:137-148`).

#### Retry / Rerun / Revise

Legacy retry is allowed from `FAILED` or `CANCELLED`, reuses the same execution row/ID, resets failed-or-later stages to `QUEUED`, clears execution error/timestamps/cancel request, and emits a new execute outbox event (`legacy/application/run_execution/services.py:899-941`). No repository-local named rerun or revise operation was confirmed.

#### Result Linkage Boundary

Legacy Result models are linked through stage execution and artifact relations in the legacy metadata model; full result/artifact lifecycle is outside this phase. The execution/stage/attempt persistence boundary is confirmed by `legacy/domain/metadata.py:635-696,789-858`.

#### Transaction Boundaries

Legacy creation is built in the API session and committed by the caller context; outbox claim and dispatch use distinct sessions. Worker execution commits execution start, stage start, stage success, and terminal/failure updates at separate points (`legacy/workers/executor.py:194-198,225-250,278-293`; `state_management.py:33-60`).

### Mandatory Explicit Answers

#### A. Does the active Product runtime have exactly one persistent Execution lifecycle model?

**NO.** Product has `product_execution`/`ExecutionOrm` and `product_family_execution`/`FamilyExecutionOrm` as distinct persistent entities and tables (`E4-OBS-015`, `E4-OBS-018`, `E4-OBS-032`).

#### B. Do Causal, Exploratory, and Predictive executions persist through the same Execution entity/repository/table?

**NO.** Causal uses the domain `Execution`, `SqlExecutionRepository`, and `product_execution`; exploratory and predictive use `FamilyExecutionOrm`, direct service sessions, and `product_family_execution` (`E4-OBS-015`, `E4-OBS-018`). Exploratory and predictive are partially shared with each other.

#### C. Do Causal, Exploratory, and Predictive executions share the same state-transition implementation?

**NO.** Causal uses explicit domain transition methods and a repository claim; exploratory and predictive assign family row states in separate services with different claim/mutation behavior (`E4-OBS-014`, `E4-OBS-020`, `E4-OBS-024`).

#### D. Do Causal, Exploratory, and Predictive executions share the same worker claim mechanism?

**NO.** They use `SqlExecutionRepository.claim_next`, `ExploratoryWorkspaceService.claim_next`, and `PredictiveWorkflowService.claim_next`, respectively (`E4-OBS-016`, `E4-OBS-020`, `E4-OBS-023`).

#### E. Does GenericExecutor own the persistent Execution lifecycle?

**NO.** It receives an existing ID, performs in-memory plan/stage sequencing and runner invocation, and has no persistence, claim, or commit logic (`E4-OBS-026`; E4-INF-009).

#### F. Does the standalone CLI create or participate in the persistent Web/API Product Execution lifecycle?

**NO.** The CLI calls `ScientificCoreAdapter` and writes a local manifest; no Product Execution row, worker claim, Product Result, or Product Artifact persistence was confirmed (`E4-OBS-027`; E4-INF-010).

#### G. Is the legacy Execution lifecycle structurally identical to any active Product Execution lifecycle?

**NO.** Legacy uses a separate `execution` table/entity, outbox claim, persistent stage/attempt tables, and intermediate cancellation/validation states (`E4-OBS-028`–`E4-OBS-031`; E4-INF-011). `NO` does not imply deletion or operational irrelevance.
