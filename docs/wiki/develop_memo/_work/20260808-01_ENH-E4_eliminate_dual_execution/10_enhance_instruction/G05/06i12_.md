## 3. Canonical revise contract

Predictive reviseは:

```text
base canonical Predictive Execution
        ↓
scientific conditionを明示的に変更
        ↓
new canonical Execution
        ↓
new persistent StageExecution set
```

として成立させる。

必須:

```text
new execution_id != base execution_id

base_execution_id
    = original canonical Execution ID

analysis_family
    = PREDICTIVE

revision_kind
    = REVISED

change_reason
    = explicit non-empty human/audit reason

changed scientific conditions
    = canonical snapshotへtruthfully reflected
```

---

## 4. RERUNとの違いを明確にする

C3aで成立したrerun:

```text
same scientific conditions
revision_kind = RERUN
change_reason = NONE
```

に対し、reviseは:

```text
changed scientific conditions
revision_kind = REVISED
change_reason = required
```

である。

禁止:

```text
条件を変えていないのにREVISEDを強制する

条件を変えたのにRERUNとして保存する

revision_kindだけservice側で上書きして
canonical comparisonを回避する
```

---

## 5. Explicit change_reason

scientific conditionが変更されたExecutionには明示的なchange reasonを保持する。

API request surfaceにまだ存在しない場合は、minimal extensionとして:

```text
change_reason: str
```

を追加する。

Required validation:

```text
None            -> reject
""              -> reject
whitespace only -> reject
non-empty       -> accept
```

service側で以下のような理由を捏造してはならない。

```text
"Predictive revise"
"User requested revise"
"Revised execution"
```

実際の変更理由はcallerから明示的に受け取る。

---

## 6. Scientific condition change

revise testでは最低1つ、実際にscientific conditionを変更する。

候補はactual Predictive contract上妥当なものを選ぶ。

例:

```text
AnalysisSpecification change
model / estimator change
model parameter change
approved predictive configuration change
seed change only if immutable-spec contractと整合する
```

ただし、Predictive specificationがimmutableである場合は既存fixed Specification自体を書き換えない。

必要なら:

```text
new fixed AnalysisSpecification
new ExecutionPlan
```

を正規Product workflowで作る。

変更を実現するためにDB rowを直接改竄しない。
