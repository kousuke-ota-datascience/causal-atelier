## 1. 文書の目的

本書は、Ariadneが解決する問題、対象利用者、提供価値、主要Capability、分析ライフサイクルおよびプロダクト境界を定義する。

Ariadneは、単にアルゴリズムを実行する分析ツールではない。Research Topicに対して、何を知ろうとしたか、どのデータを用いたか、どの分析条件を固定したか、何を実行したか、どの結果を採用したかを一つの来歴として保持する分析ワークスペースである。

## 2. プロダクトの一文定義

> **Ariadneは、Research Topicに紐づくResearch ContextとDataset Versionを共有基盤とし、探索・可視化、因果分析および予測分析を実行し、その条件、結果、判断理由および相互関係を追跡可能にする分析ワークスペースである。**

短く表現すると、次のとおりである。

> **問い、データ、分析、結果、判断を切り離さずに残す。**

## 3. 解決する問題

Notebook、CLI、BI画面、実験管理ツールおよび個別のファイル管理だけでは、次の情報が分散しやすい。

1. 分析がどのResearch Topic、問題意識、意思決定および仮説に基づくか
2. どのDataset Version、対象母集団、列、期間および加工条件を使用したか
3. 探索的な観察と確認的な結論を区別できるか
4. 可視化から生成された仮説が、どの因果質問または予測課題へ接続したか
5. 因果分析におけるGraph、識別仮定、調整集合、推定器および診断は何か
6. 予測分析におけるtarget、feature、予測時点、split、model、metricおよびtest isolationは何か
7. 予測モデルの説明と因果効果を混同していないか
8. 条件を変えた再実行で何が変わり、結果がどう変化したか
9. 技術的成功と、科学的・統計的に採用可能な結果を区別できるか
10. ResultからResearch Context、Dataset、Analysis View、Specification、Execution、Artifactおよびcode versionへ遡れるか
11. 同じResearch Topicに対する探索、因果、予測の成果を横断して確認できるか
12. 第三者が分析の根拠、限界および判断理由を再検証できるか

Ariadneは、これらをProject境界、型付き分析仕様、不変Execution Plan、Family別ResultおよびLineageとして統合する。

## 4. 対象利用者

### 4.1. Analyst

表形式データを用いて、探索的データ分析、統計的可視化、因果分析または予測モデリングを行う利用者である。Pythonや統計・機械学習の基礎知識を前提とするが、すべての操作をNotebookへ依存させない。

### 4.2. Reviewer / Viewer

分析結果、条件、診断、警告、判断理由およびLineageをread-onlyで確認する利用者である。結果の妥当性を自動承認するのではなく、追跡可能な根拠を提供する。

### 4.3. Operator

実行環境、Worker、Metadata DB、Artifact Store、認証、監視、バックアップおよび保持期間を管理する利用者である。

## 5. 対象となる意思決定

Ariadneは、次の三種類の問いを同一Research Topic内で分離して扱う。

| 問いの種類 | 代表的な問い | 主な成果 |
| --- | --- | --- |
| 探索・可視化 | データにどのような分布、欠損、関連、群差または時系列構造が見えるか | Profile、集計、Chart、探索的観察、Analysis View候補 |
| 因果分析 | 介入Xを行った場合、結果Yはどう変化するか | Graph、Identification、Data Eligibility、Treatment Effect、Diagnostics、Refutation、Sensitivity |
| 予測分析 | 時点Tで利用可能な情報から、将来Yをどの程度予測できるか | Model、Prediction、Metric、Calibration、Error Analysis、Predictive Explanation |

三者は相互に参照できるが、意味論を統合しない。相関、予測重要度またはSHAP値を因果効果として表示してはならない。

## 6. 提供価値

### 6.1. Research Contextを分析実行から分離しない

Project内のResearch Contextを分析仕様へ結び付け、Execution時点のContextを不変snapshotとして保持する。これにより、結果が「何のための分析であったか」を失わない。

### 6.2. 一つのDatasetを複数の分析目的へ安全に再利用する

Dataset Versionは共有証拠資源として登録する。Family固有の対象行、列、filter、派生列、欠測処理および時間cutoffはAnalysis Viewで明示し、元データを暗黙に上書きしない。

### 6.3. 探索から分析課題への遷移を記録する

保存したChart、集計または探索的観察から、Causal Analysis SpecificationまたはPredictive Analysis Specificationのdraftを作成できる。探索後に作られた確認的分析には、探索起点であることをLineageおよび警告で保持する。

### 6.4. 分析Familyごとの妥当性契約を強制する

因果分析では識別、適格性および推定gateを、予測分析ではleakage、split、test isolationおよびmetric整合をBackendで検証する。UI上の入力補助だけを妥当性保証としない。

### 6.5. 再実行と条件変更を比較可能にする

同一条件の技術的再試行と、分析条件を変更した改訂実行を区別する。変更dimensionを決定論的に生成し、比較画面で共通条件、変更条件および結果差分を表示する。

### 6.6. 結果と判断を一つのLineageに接続する

Result、Artifact、Annotationおよび採用判断から、上流のResearch Context、Dataset Version、Analysis View、Specification、Plan、Stage、code versionへ遡れる。

## 7. 主要Capability

### 7.1. Project / Research Context

- Research Topic、Problem Statement、Research Question、Significance、Hypothesis、Decision Contextの管理
- Contextの版管理およびrelation管理
- Project単位の権限、archiveおよびLineage境界

### 7.2. Data / Analysis View

- CSV / Parquet Dataset Versionの不変登録
- schema、hash、行列数、欠損、基本profileの保存
- filter、column selection、derived column、missing-value policy、time cutoffの型付き定義
- Family別の列役割をDataset自体へ固定しない

### 7.3. Explore & Visualize

- Dataset overview、column profile、missingness、distribution、group comparison、bivariate relation、time trend
- 保存可能なChart SpecificationとResult
- 探索結果から分析draftを生成する導線

### 7.4. Causal Analysis

- DiscoveryまたはUser-defined / Imported Graph
- Graph semantics、比較、編集、固定
- Causal Question、Causal Design、Identification
- Data Eligibility、Estimation Gate、ATE / ATT
- Diagnostics、Refutation、Sensitivity

### 7.5. Predictive Analysis

- 表形式Binary ClassificationおよびRegression
- Prediction Question、Feature Availability、Split Strategy
- preprocessing、training、evaluation、error analysis、explanation
- test set isolation、group / temporal leakage防止

### 7.6. Generic Workflow

- Analysis Family別Planner
- versioned Stage TypeとRunner Registry
- 不変Execution PlanとStage dependency
- Generic Executor、retry、cancel、Attempt、Artifact binding

### 7.7. Results / Comparison / Lineage

- Family別Result Schema
- 同種Result比較
- Research Topic単位の横断summary
- 明示的なcross-analysis relation
- Annotation、Export、Manifest

## 8. 統合分析ライフサイクル

```text
Project / Research Topicを作成
  ↓
Research Contextを記述・固定
  ↓
Dataset Versionを登録
  ↓
Explore & Visualizeで品質・分布・関連構造を確認
  ↓
必要に応じてAnalysis Viewを保存
  ↓
分析課題を選択
  ├─ Causal Analysis Specification
  └─ Predictive Analysis Specification
  ↓
Family別PlannerがExecution Planを生成
  ↓
Plan validationとFamily固有validation
  ↓
Stageを依存順に実行
  ↓
Result / Artifact / Diagnosticsを保存
  ↓
同種分析を比較し、条件差分を確認
  ↓
探索・因果・予測の関係をLineageで確認
  ↓
採用理由、仮定、限界および意思決定をAnnotationへ記録
```

探索・因果・予測は必ず直列に実施するものではない。Dataset Version、Research Contextおよび明示的Lineageを共有しつつ、それぞれ独立したAnalysis SpecificationとExecutionを持つ。

## 9. Project Workspace

Projectを開いた画面は、route-backed tabsとして次を提供する。

1. `Research Context`
2. `Data`
3. `Explore & Visualize`
4. `Causal Analysis`
5. `Predictive Analysis`
6. `Results & Lineage`

各タブは独立URLを持ち、deep link、reload、browser back、権限制御およびE2E testを可能にする。

## 10. 分析意味論の境界

### 10.1. Exploratory Finding

探索的な可視化、相関、群差またはclusterは仮説生成の材料であり、確認的結論ではない。探索結果を根拠に同じデータで確認的分析を行う場合、その来歴を隠さない。

### 10.2. Predictive Explanation

Feature importance、partial dependence、SHAP等はモデル挙動の説明であり、変数の因果効果ではない。UI、API、Exportで`Predictive Explanation`と明記する。

### 10.3. Causal Result

Treatment Effectは、Causal Question、Graph、Identification Strategy、Adjustment Set、Assumptions、Data EligibilityおよびDiagnosticsと一体で表示する。数値だけを切り離して採用可能と見せない。

### 10.4. Technical StatusとAnalytical Status

Executionの`SUCCEEDED`は処理が完了したことを示す。Resultのscientific / analytical statusは、結果を採用できることを自動的には意味しない。両者を別フィールド、別表示とする。

## 11. 設計原則

1. **Research Topic中心**: DatasetやAlgorithmを最上位の業務境界にしない。
2. **自己完結した正本**: 要件・設計は現行完成形として記述する。
3. **不変Version**: Dataset、Context、Analysis View、Specification、Plan、Resultは実行後に上書きしない。
4. **Family分離**: Explore、Causal、Predictiveは共通基盤を利用するが、validationとResult意味論を共有しすぎない。
5. **Backend enforcement**: 科学・統計・状態遷移の制約はBackendで強制する。
6. **比較中心**: 条件差分と結果差分を同時に示す。
7. **Lineage by construction**: 後付け推測ではなく、Command受付時に参照関係を保存する。
8. **ResultとArtifactの分離**: 論理結果と物理ファイルを区別する。
9. **可視化の用途分離**: データ探索用可視化はExploreへ、分析結果可視化は各Familyへ置く。
10. **段階的拡張**: 新しい分析FamilyはPlanner、Schema、Runner、Result、Validationを一組として追加する。

## 12. プロダクト境界

### 12.1. 対象

- 前処理可能な表形式データ
- 単一Project内の複数Dataset Version
- 探索的可視化
- 因果探索・因果効果推定
- 表形式Binary Classification / Regression
- Batch execution
- Result比較、Lineage、Annotation、Export

### 12.2. 対象外

- 汎用BIダッシュボードビルダー
- 任意SQL実行環境
- Streaming / online prediction serving
- Feature Store、Model Registry、MLOps監視一式
- 画像、音声、自然言語の学習基盤
- 自動的な因果識別証明
- SHAP等からの因果解釈自動生成
- 自動意思決定または自動施策配信
- 無制限なAutoML探索
- 複数Projectを跨ぐデータ共有

## 13. 成功指標

ENH-E3の価値は、単に三つのタブが存在することではなく、次で評価する。

- 一つのResearch Topicから探索、因果、予測の各分析を開始できる
- 各分析が同一Dataset Versionまたは明示的に派生したAnalysis Viewを参照する
- すべてのResultが再現に必要なsnapshotとversionを保持する
- 探索結果から作成された分析draftの出所を追跡できる
- 因果結果と予測結果が意味的に混同されない
- 予測評価でtest leakageをBackendが拒否できる
- 因果推定でIdentification / Eligibility gateをBackendが拒否できる
- ReviewerがAriadne内のResult、Artifact、AnnotationおよびLineageから結果の根拠へ遡れる

## 14. 用語

| 用語 | 定義 |
| --- | --- |
| Research Topic | Projectが扱う一つの問題領域または意思決定テーマ |
| Research Context | Problem Statement、Question、Significance、Hypothesis、Decision Context等の分析文脈 |
| Dataset Version | hashとschemaを固定した不変の入力データ |
| Analysis View | Dataset Versionからの行・列・加工・時間条件を型付きで表す不変仕様 |
| Analysis Family | EXPLORATORY、CAUSAL、PREDICTIVEの分析意味論区分 |
| Analysis Specification | Family固有の問い、方法、仮定、評価基準を固定した仕様 |
| Execution Plan | 実行するStage、依存関係、input/output契約を固定した不変計画 |
| Result | 分析上の意味を持つ型付き論理結果 |
| Artifact | ResultまたはExecutionが生成した物理ファイル |
| Lineage | Resource間の生成、参照、派生、改訂関係 |
