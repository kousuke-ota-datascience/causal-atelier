# Ariadne / ENH-E4 設計書改定記録

## 1. 改定対象
snapshot `21_論理データ設計.md`、`22_プロダクト基本設計.md`、`23_API・インターフェース設計.md`、`30_詳細設計.md`。baselineは `docs/wiki/requirement_definition/` の対応文書である。

## 2. 改定概要
Phase 06 E4-ADR-001〜012を、runtime boundary、canonical Execution、Stage、Result/Artifact、Lineage、legacy、migration、CLIのtarget contractとして反映した。これは設計materializationであり、production code/schema/migrationの実装完了を意味しない。

## 3. 主要設計差分
| Design Area | Before | After | Reason |
|---|---|---|---|
| Runtime boundary | Product/legacyの入口が併存 | Product API/workerがcanonical、legacyは非canonical | ADR-001/009 |
| Canonical Execution | Causal/Family authority | 一つのpersistent aggregate、family/type discriminator | ADR-002 |
| Identity / mutation | family別state/retry差異 | 共通identity、retry/rerun/revise/cancel contract | ADR-003 |
| Claim / lease | claim実装が複数 | canonical repository/serviceがatomic ownership | ADR-002/003 |
| StageExecution | workflow間で非対称 | 全canonical workflowにpersistent child | ADR-004 |
| GenericExecutor | runner内の抽象が混在 | workflow infrastructure、lifecycle ownerではない | ADR-005 |
| Result / Artifact | ownershipとsemantic levelが混在 | ExecutionResult/StageResult、one metadata owner、ArtifactStorePort | ADR-006/007 |
| Lineage | typed/derived/genericが重複 | typed structuralまたはgeneric-onlyの排他的authority | ADR-008 |
| Legacy / science | runtimeとshared moduleの依存境界 | orchestration retire/archive、shared capability retain | ADR-009 |
| Migration / bootstrap | root chainの歴史的混在 | Product-only clean bootstrap、legacy chain history-only | ADR-010 |
| CLI | utilityとauditable analysisの境界不明 | low-level utilityはpersistent lifecycle外 | ADR-011 |
| Compatibility terminology | legacy namingをarchitectureと解釈し得る | explicit evidenceなしにrename/authority化しない | ADR-012 |

## 4. Architecture / Data / API影響
### Architecture
one canonical Product lifecycle authority。Causal/Exploratory/Predictiveはworkflow semanticsであり、別persistent lifecycleではない。worker claimも一つのauthorityに集約する。

### Data
Execution→StageExecution、Execution→Result、StageExecution→StageResult、Result→Artifactのownershipをsemantic contractとして定義する。ResultはExecutionResult/StageResultを宣言し、Artifact metadataとphysical locatorを分離する。typed structural lineageとgeneric-only lineageのallowlistを分ける。exact cardinalityが未確定の箇所はIMPLEMENTATION_DETAIL_WITHIN_APPROVED_CONTRACTとする。

### API
既存endpointのrenameは決めない。user-visible Product analysisはcanonical Executionを作り、retry/rerun/revise/cancel、Result/Artifact referenceはcanonical semantic identityを使う。low-level standalone scientific CLIはpersistent audit APIではない。

### Worker
canonical Execution repository/serviceがclaim/lease/state transitionのboundaryとなる。family workflow adapterはrunner内部の実行を担当し、GenericExecutorはcanonical lifecycle、Result/Artifact metadataをcommitしない。

### CLI
utility CLIは別のpersistent Product lifecycleを作らない。user-visibleでauditが必要なCLIはcanonical Executionへsubmitする。

## 5. Migration / Compatibility
Database decision recordに基づき、pre-productionの現状ではProduct-only clean rebuildを採用する。canonical chainは `alembic_product.ini` → `product_migrations`、root legacy migrationはhistory-onlyでProduct bootstrapから呼ばない。historical application-data migrationは不要と承認されたが、これは現在のretention evidenceに基づく条件付き判断であり、一般的なdata destruction許可ではない。external legacy compatibilityはENH-E4の既定scope外だが、外部consumer不存在は証明されていないためlegacy source/runtime removal前に別decisionを要する。shared scientific capabilityは保持する。

## 6. 未解決事項
E4-UNK-009、012、014〜029は後続Gateで扱うimplementation/compatibility unknownである。外部consumer、retention、object backend/GC、retry/output、lineage export等を推測で補完しない。G01でcontract review可能なtargetは固定し、G01を本書でPASS判定しない。
