# 01-05 wk03｜差別化仮説 発散版02

## 1. 結論仮説

`wk02`で挙げたEvidence-first、Answerability、No-Go等は、分析PoCの設計原則としては妥当である。しかし、**「なぜ数多あるコンサル / SIer / AIベンダ / データサイエンス会社ではなく当チームなのか」への回答としては決め手に欠ける**。

理由は、競合各社も「業務起点」「意思決定への接続」「適切な技術選定」「PoCから本番化」「データとAIによる価値創出」等を既に主要価値として掲げているためである。

したがって、Why Usを考える際には、Capabilityの差を探すだけではなく、**各競合がどの局面で、何を最適化する事業者なのか**を整理し、当チーム自身の競争カテゴリーを再定義する必要がある。

本検討で最も有力と考える方向性は、当チームを「もう一つのAIベンダ / コンサル」と定義するのではなく、以下のような**本番投資前の分析R&D / Evidence Gate**として位置づけることである。

> **本番導入を前提にAIを売るのではなく、大きな投資を行う前に「この意思決定はデータで本当に改善できるのか」を専門家が検証する。**
>
> **予測・因果のPoCを通じて、Go / No-Goだけでなく、本番化する場合に必要なデータ・性能・前提・実装条件まで明らかにする。**

このポジショニングが成立するなら、コンサル、SIer、AIベンダの強みと正面衝突せず、むしろ**それらの本格導入前に置く独立した専門工程**として差別化できる可能性がある。

ただし、これは現時点では仮説である。特に「本番実装・製品販売から独立して評価できる」「シニアなデータサイエンティストが問いの定義から実装・解釈まで直接担当する」等を訴求する場合は、当チームの実際の体制・契約・案件運営がその主張を満たすか確認が必要である。

---

## 2. なぜwk02では決め手に欠けたのか

### 2.1. 競合も同じ言葉を使える

`wk02`では、以下を有力候補とした。

- Evidence-first
- Answerability / Identifiability
- Decision-oriented PoC
- No-Goを成果にする
- Business Questionから設計する
- Predictive / Causalを適切に使い分ける
- Scientific Validityを重視する

いずれも重要である。しかし、高品質な競合であれば類似した説明は可能である。

例えば、実際に競合各社は公式情報で以下を掲げている。

- Deloitteは、企業価値を起点とし、戦略と実装を接続し、AIを構想から実装・定着まで支援すると説明している。
- Accentureは、ビジネスニーズに応じたAI活用、データ戦略、業務変革、スケールまでを提供している。
- NTT DATAは、AI ConsultingからPilot、Full-scale Deployment、Integration、Managed ServicesまでEnd-to-Endで支援すると説明している。
- Palantirは、「Start with the decision」と明示し、データ・ロジック・Actionを業務意思決定へ直接接続することを製品思想の中心に置いている。
- BrainPadは、「正しい問い」の見極め、データ活用コンサルティング、分析・アルゴリズム開発、システム構築、施策効果測定までを訴求している。

つまり、**「我々は業務起点」「我々は意思決定につなげる」という主張だけでは、競合との差ではなく市場参加資格を説明しているにすぎない**。

### 2.2. 「できること」ではなく「どこで勝つ会社か」を決める必要がある

総合コンサルも、SIerも、AIベンダも、データサイエンス専業も、高度な人材を持ち、案件次第では予測・因果・統計・機械学習を扱える。

従って、個々のCapabilityについて「他社にできないこと」を探すと、ほぼ必ず反例が見つかる。

差別化の糸口はむしろ、以下にある。

> **競合が最も得意な案件・商流・価値提供は何か。**
>
> **その強みゆえに、相対的に最適化されにくい局面はどこか。**
>
> **当チームは、その局面に特化した専門機能として成立できないか。**

## 3. 競合の立場から見た「自社を選ぶ理由」

以下は、競合各社の公式なサービス説明を参考に、各競合類型のRight to Winを抽象化したものである。

### 3.1. 総合コンサルティングファーム

#### 彼らの立場からの強み

> **経営課題から入り、業界知見・戦略・業務・テクノロジー・組織変革を束ね、企業全体のTransformationを動かせる。**

構造的な強み：

- 経営層・事業責任者との接点
- Industry Knowledge
- 戦略策定、Business Case、KPI、Operating Model
- 部門横断のStakeholder Alignment
- Change Management / 人材・組織変革
- Strategy / Technology / Operations等の多職種を束ねる能力
- Global / Cross-industryの事例・Benchmark
- 大規模Transformation ProgramのPMO
- Technology Allianceを含む広いSolution Portfolio

#### 顧客がコンサルを選ぶ合理的理由

- 問題が分析だけでなく、戦略・組織・業務プロセスまでまたがっている。
- 経営レベルで変革テーマを定義したい。
- 多数のStakeholderを巻き込む必要がある。
- AI導入を企業全体のTransformationへ接続したい。

#### 当チームがここで正面衝突すべきでない理由

「Business-first」「経営接続」「業務変革」を主差別化にすると、総合コンサルの最も得意な競争軸で戦うことになる。

当チームの勝ち筋があるとすれば、より限定された**分析上の不確実性を解く専門工程**である可能性が高い。

---

### 3.2. SIer / IT Service Provider

#### 彼らの立場からの強み

> **PoCを動くシステムへ変え、既存ITへ統合し、安全・安定的に運用できる。**

構造的な強み：

- Enterprise Architecture
- 既存システムとのIntegration
- Cloud / Network / Security
- Data Platform
- 大規模開発
- Testing / Migration / Release Management
- Governance / Compliance
- Managed Services / Operation
- SLA / Support
- 長期間にわたる顧客IT環境の理解
- 大人数のDelivery Capacity

#### 顧客がSIerを選ぶ合理的理由

- PoCではなく本番システムが必要。
- 既存基幹システムとの接続が重要。
- Security / Governance / SLAが重要。
- 構築後の運用保守まで任せたい。

#### 当チームがここで正面衝突すべきでない理由

「PoCから本番まで一気通貫」「End-to-End」を主差別化にすると、SIerの強みと競合する。

逆に、本番開発前に**何を本番化すべきか、どの性能・データ条件なら投資に値するかを確定する工程**であれば補完関係を作れる。

---

### 3.3. AI Product / Platform Vendor

#### 彼らの立場からの強み

> **再利用可能なSoftware / Platform / IPによって、AIを短期間で業務へ組み込み、継続利用・Scaleできる。**

構造的な強み：

- Productized Capability
- Reusable Components
- UI / Workflow
- Deployment / Monitoring
- Security / Governance
- AI Model / Agent Integration
- 継続的なSoftware Update
- 多数顧客へ展開することによる学習効果
- Platform上での開発速度
- 標準化によるCost Efficiency

Palantirのように、単なるモデル提供ではなく「Decision → Data / Logic → Action → Operational Workflow」までを製品として実装するベンダも存在する。

#### 顧客がAI Vendorを選ぶ合理的理由

- 解くべき課題が比較的明確である。
- 製品Capabilityと課題がFitする。
- 短期間でOperationalizeしたい。
- 継続利用可能なPlatformが欲しい。

#### 当チームがここで正面衝突すべきでない理由

「意思決定につなげる」「柔軟なAI」「高度なアルゴリズム」を主張しても、Platform Vendor側も同様に訴求できる。

当チームが異なる価値を出すなら、**特定Platformへ載せる前の、非定型・高不確実な分析R&D**が候補となる。

---

### 3.4. データサイエンス / Analytics専門会社

#### 彼らの立場からの強み

> **多数のデータサイエンティストと蓄積された案件知見を活かし、分析・データ基盤・アルゴリズム・活用支援を専門的に提供できる。**

構造的な強み：

- データ分析専門人材の集積
- 多数案件から蓄積されたKnow-how
- Prediction / Optimization / Marketing Analytics等の幅広い分析経験
- Analytics + Engineeringの組合せ
- Vendor-neutralなTechnology Selectionを掲げる会社もある
- データ活用組織の育成まで支援できる会社もある
- 業界・ユースケース別の豊富な実績

#### 顧客がデータサイエンス専門会社を選ぶ合理的理由

- 社内に専門人材が不足している。
- 幅広い分析テーマへ継続的に対応してほしい。
- データ基盤から活用まで専門会社に任せたい。
- 実績豊富な分析チームを利用したい。

#### 当チームにとって最も近い競合

この類型は当チームとの距離が最も近い。

「データサイエンスに強い」「正しい問いを考える」「Vendor-neutral」「分析と業務をつなぐ」だけでは、十分な差別化にならない。

したがって最終的なWhy Usでは、**単なるデータ分析専門会社よりさらに狭い専門ポジション**を定義する必要がある。

---

### 3.5. 顧客の内製チーム

#### 内製の構造的な強み

> **自社業務・データ・政治的制約・意思決定プロセスを最も深く理解している。**

- Domain Knowledge
- Data Generating Processへの理解
- データアクセス
- 現場との関係性
- 長期的な運用継続性
- 分析結果からActionまでの距離が短い
- ナレッジが社内に残る

#### 外部チームが内製に勝ちにくい領域

外部チームが「業務理解」を最大の差別化として主張するのは難しい。

外部利用の合理性は、社内にない**専門方法論、第三者視点、短期的な追加Capacity、難易度の高い分析設計**等に置く必要がある。

## 4. 競合比較から見えるWhite Space

各競合の強みを並べると以下となる。

| 類型 | 最も強い競争軸 | 主に最適化するもの |
|---|---|---|
| 総合コンサル | Strategy / Transformation / Alignment | 企業変革を動かす |
| SIer | Integration / Production / Operation | 安全・安定的に本番稼働させる |
| AI Vendor | Product / Platform / Scale | AI機能を速く繰り返し展開する |
| Analytics専門会社 | Data Science Expertise / Breadth | 多様なデータ活用を専門的に支援する |
| 内製 | Domain Context / Continuity | 自社固有の知識を継続活用する |

ここで空白になり得るのが、以下の工程である。

```text
Business / Decision Problem
          ↓
   【分析上の不確実性】
   ・そもそも予測可能か？
   ・施策効果を識別可能か？
   ・どのデータが必要か？
   ・どの程度の性能なら業務価値があるか？
   ・本番投資に進むべきか？
          ↓
       PoC / Evidence
          ↓
   Go / No-Go / Redesign
          ↓
────────────────────────────
ここから先は、本番Transformation / System / Platform
────────────────────────────
          ↓
Consulting / SIer / AI Vendor / 内製
```

すなわち、**「本番実装を行う能力」ではなく、「本番実装へ投資すべき状態かを見極める能力」**をサービスカテゴリーとして明確にする。

この考え方では、競合の強みがそのまま当チームの存在理由になる。

- 大手コンサルのTransformationは強力だからこそ、その前に分析上の勝算を確認する価値がある。
- SIerの本番構築は大規模だからこそ、その前に実装すべきモデル・必要性能・データ条件を確定する価値がある。
- AI PlatformはScaleに強いからこそ、そのPlatformへ載せる価値があるユースケースかを先に検証する価値がある。
- 内製チームはDomain Knowledgeに強いからこそ、外部の専門家を一時的なAnalytical R&D機能として利用できる。

## 5. 新しい差別化仮説

### 仮説A｜「AIを導入する会社」ではなく「AI / 分析へ投資すべきかを検証する会社」

**主張案**

> **本番投資の前に、その意思決定をデータで改善できるかを検証する。**

従来のWhy Usとの違い：

- 「業務につなげます」ではない。
- 「高度な分析ができます」でもない。
- **本番投資の判断そのものを支援する専門工程**と定義する。

顧客価値：

- 大規模AI / IT投資の前に勝算を確認できる。
- PoCが単なるDemoではなくInvestment Gateになる。
- 分析価値が確認できなければ早期に止められる。

模倣困難性の源泉候補：

- 本番開発・Platform販売を主収益とする事業者とは、PoCの目的関数が異なり得る。
- 当チームがPoC自体を独立したサービスとして成立させられるなら構造的な差になる。

**現時点の評価：最有力**

---

### 仮説B｜「分析受託」ではなく「Analytical R&D機能の外部化」

**主張案**

> **社内でまだ解き方が決まっていない難しい定量課題に対し、期間限定の分析R&Dチームとして入る。**

対象となる案件：

- 既製Solutionへそのまま載らない。
- KPIは重要だが分析方法が定まっていない。
- Prediction / Causal / Experimental Design等を比較する必要がある。
- 研究的な探索と業務判断の双方が必要。

顧客価値：

- 常設で専門人材を採用せず、高難度テーマだけ外部専門家を利用できる。
- Product FitではなくQuestion Fitで分析を構成できる。

競合との違い：

- ConsultingよりHands-on Analytical Workに深く入る。
- SIerより前段に位置する。
- Product Vendorより非定型問題に対応する。
- 内製DSの専門拡張として使える。

**現時点の評価：有力**

---

### 仮説C｜実装Vendorから独立した「Analytical Design Authority」

**主張案**

> **PoCで分析仕様と成立条件を確定し、その後の本番実装先を縛らない。**

PoC成果として以下を明示する。

- Analysis Question
- Target / Estimand
- 必要データ
- Validation Design
- Performance Requirement
- Assumptions / Limitations
- Failure Condition
- Decision Rule
- 本番化時の技術要件

顧客価値：

- PoC実施VendorへのLock-inを下げられる。
- 本番実装をSIer、AI Vendor、内製のどこへ渡しても、分析上の要件を保持できる。
- 本番RFP / 要件定義の入力として利用できる。

構造的差別化：

- 本番開発を主な後続売上とするVendorでは、PoC成果を完全にPortableにするインセンティブが弱い可能性がある。

留保：

- 当チームが実際にPortableな成果物を提供できることが前提。

**現時点の評価：最有力候補**

---

### 仮説D｜「シニア専門家が提案し、別チームが作る」構造を持たない

**主張案**

> **問いを設計したデータサイエンティスト自身が、実装・検証・解釈まで一貫して担当する。**

差別化の背景：

大規模Professional Serviceでは、営業 / Strategy / Senior Expert / Delivery / Engineeringの役割分担が強みである一方、分析上の微妙な前提がHandoff時に失われるリスクがある。

小規模専門チームであれば、同一人物または密な少人数チームが以下を連続して扱える可能性がある。

```text
Business Question
      ↓
Analysis Question
      ↓
Research / Validation Design
      ↓
Coding / Modeling
      ↓
Diagnostics
      ↓
Interpretation
      ↓
顧客説明
```

顧客価値：

- 「提案時の専門家と実際に分析する人が違う」問題を避ける。
- Assumptionやデータの違和感を分析設計へ即座に戻せる。
- 高難度案件でコミュニケーションLossを減らせる。

**重要な留保**

これは実際の当チームDelivery Modelがそうなっている場合にのみ使える。事実確認が必須。

**成立するなら非常に強い候補。**

---

### 仮説E｜Standard Solutionでは解けない「非定型の分析問題」に特化する

**主張案**

> **既製AIや標準分析メニューでは答えにくい、企業固有の問いをスクラッチで検証する。**

例：

- 特殊なOutcome定義
- 複雑なTreatment / Intervention
- 観測データでの因果効果
- 小標本・Rare Event
- 特殊なBusiness Costを考慮したPrediction
- 複数の予測 / 因果情報を組み合わせたDecision

顧客価値：

- 課題を製品Capabilityへ無理に合わせる必要がない。
- 「SaaSで解ける問題」ではなく「まだSolutionが定まっていない問題」を相談できる。

競合との違い：

- AI VendorのProductization / Standardizationという強みの裏側を狙う。

留保：

- 市場を狭くするPositioningである。
- スクラッチ開発コストとのTrade-offを説明する必要がある。

**現時点の評価：有力な補助軸**

---

### 仮説F｜Predictive / Causalを「AI技術」ではなくInvestment Evidenceとして扱う

**主張案**

> **予測精度や因果効果を作ることではなく、その情報が投資判断を変えるかを検証する。**

差別化ポイント：

- AI Model Developmentを目的にしない。
- Causal Effect Estimationを目的にしない。
- Analysis Outputを、Investment / Business DecisionのEvidenceとして扱う。

例：

```text
需要予測モデル
  ↓
十分な予測性能があるか
  ↓
発注量を変えた場合の業務価値があるか
  ↓
本番システムへ投資するか
```

```text
施策効果推定
  ↓
効果を主張できる条件が成立するか
  ↓
施策配分を変える根拠になるか
  ↓
施策投資を変更するか
```

これは仮説AのScientific / Analytical側の裏付けとして有効。

---

### 仮説G｜「No-Goを言える」ではなく「本番化を売らないからGateを厳格にできる」

`wk02`のNo-Go仮説を一段深くする。

弱い表現：

> 当チームはNo-Goも正直に言います。

これは倫理訴求であり弱い。

強い構造仮説：

> **PoCの目的を本番案件の獲得ではなく、本番投資の可否判定として契約・成果物上明示する。**

その結果として、

- Go
- Conditional Go
- Additional Validation
- Additional Data
- Redesign
- No-Go

を同列の正常なPoC Outcomeとして扱う。

これが実際のService Designとして制度化されていれば、単なる「誠実さ」ではなく構造的差別化となる。

---

### 仮説H｜本番化を前提にしないSmall-Bet型PoC

**主張案**

> **最初から大規模Transformationを構想せず、最小のEvidenceで投資判断できる単位まで課題を切る。**

顧客価値：

- Initial Commitmentを小さくできる。
- 技術的不確実性が高いテーマを試しやすい。
- Data / Assumption不足を早期に発見できる。

競合との違い：

- 大規模Transformationを得意とする会社とは異なる入口を作れる。

留保：

- 「小さい会社だから安い・速い」という訴求に落としてはいけない。
- 契約単位や案件設計として本当にSmall-Betが可能か確認が必要。

---

### 仮説I｜顧客の内製DSに対する「Specialist Second Opinion」

**主張案**

> **内製チームを代替せず、因果推論・検証設計等の難所だけに専門家として参加する。**

顧客価値：

- Internal Domain Knowledgeを失わない。
- 全分析を外注せずに済む。
- 高難度テーマのみ外部専門性を利用できる。
- Internal Teamの設計・結果へ独立したSecond Opinionを得られる。

これは特に、既にDS組織を持つ成熟企業に対する差別化候補となる。

---

### 仮説J｜PoC成果を「Model」ではなく「Evidence Package」として残す

**主張案**

> **何を試し、何が分かり、何が分からず、次に何をすべきかを再検証可能な形で残す。**

Evidence Package候補：

- Business / Analysis Question
- Data Definition
- Analysis Plan
- Assumptions
- Code / Configuration
- Metrics / Diagnostics
- Results
- Limitations
- Decision Rationale
- Next Action

Ariadneは、この主張を裏側で支える可能性がある。

ただし、Ariadne自体をWhy Usとして売る必要はない。

顧客価値：

- 数か月後に「なぜこの結論になったのか」が追える。
- 担当者交代後も検証条件が残る。
- 本番化時・再評価時のStarting Pointになる。

**単独差別化ではなく、仮説A/Cを証拠化するCapabilityとして有力。**

---

## 6. どの仮説が本当に「決め手」になり得るか

`wk02`のような点数評価よりも、今回は以下の3条件で絞る。

### 条件1｜競合の強みを否定せず成立するか

強い差別化は、

> 「競合はそれができない」

ではなく、

> 「競合は別の局面で非常に強い。当チームはその前段 / 狭い専門領域で異なる役割を持つ」

と説明できる方がよい。

### 条件2｜顧客が「別料金を払う理由」になるか

単なる品質原則ではなく、顧客が明確に以下を感じる必要がある。

- 大きな投資失敗を避けられる
- 難しいテーマを前へ進められる
- Vendor Lock-inを減らせる
- 社内にない専門性を一時利用できる

### 条件3｜当チームのOperating Modelそのものが根拠になるか

競合も営業資料に書ける言葉では弱い。

以下のような**実際のサービス構造**で裏付けられるものが強い。

- PoC単体で契約可能
- 本番製品の購入を前提にしない
- 特定Technology / Platformに固定しない
- DS本人が問い設計から実装まで担当
- Go / No-Go条件を開始時に定める
- 成果物がPortable
- Assumption / Validation / Limitationを成果として残す

## 7. 暫定Tier

### Tier S｜Why Usの核になり得る

#### S1. 本番投資前の「Analytical R&D / Evidence Gate」

> **この意思決定をデータで改善できるのか。本番投資の前に専門家が検証する。**

これが最も競争軸を変えられる。

#### S2. Implementation-neutral / Portable PoC

> **PoCで成立条件と分析仕様を確定し、その後の実装先を縛らない。**

S1と組み合わせることで、「なぜ独立したPoC専門チームを使うのか」に答えられる。

#### S3. Expert-direct Delivery

> **問いを設計した専門家自身が実装・検証・解釈まで担当する。**

事実として成立するなら非常に強い。ただし事実確認が必須。

### Tier A｜Sを支える差別化要素

- 非定型Analytical R&D
- Predictive / Causalの専門性
- Small-Bet型PoC
- Evidence Package
- Internal DSへのSpecialist Second Opinion
- No-Go / Redesignを正規Outcomeとして扱う

### Tier B｜必要だが単独では弱い

- Business-first
- Scientific rigor
- Flexible implementation
- 問いから手法を選ぶ
- 業務Decisionへ接続する

これらは捨てるのではなく、Tier Sを成立させるSupporting Capabilityとして使う。

## 8. Why Usのメッセージ候補

以下は最終案ではなく、方向性を確認するための叩き台である。

### 案1｜最もストレート

> **本番投資の前に、「その意思決定をデータで本当に改善できるか」を見極める。**

### 案2｜PoC専門性を強調

> **AIを作るためのPoCではなく、AI / 分析へ投資するかを判断するためのPoC。**

※ 「AI」に限定すると因果推論等を狭めるため、最終表現では調整が必要。

### 案3｜競合との役割分担が最も明確

> **本番構築の前に、何を作る価値があるかを分析で確かめる。**

### 案4｜専門チーム性

> **まだ解き方のない定量課題を、本番化できる分析仕様まで落とし込むAnalytical R&Dチーム。**

### 案5｜Investment Gate

> **予測・因果のPoCを、本番投資のEvidence Gateにする。**

専門用語色が強いため、Speaker Note / Supporting Logic向き。

## 9. 競合比較を1枚にする場合の構造案

Why Usの主図として競合比較を直接出すかは別途判断が必要だが、内部整理としては以下が最も分かりやすい。

```text
                       得意な局面

総合コンサル     ── Strategy / Transformation / Change
                         ▲
                         │
当チーム          ── Analytical R&D / Evidence Gate
                         │
                         ▼
SIer              ── Build / Integrate / Operate

AI Vendor         ── Productize / Deploy / Scale

内製              ── Domain Context / Continuous Operation
```

競合を劣位に置くのではなく、**専門領域をずらす**。

顧客に伝えたいことは、

> 「大手コンサルやSIerより全部できます」

ではない。

> **「本番導入を始める前の、分析上もっとも不確実な部分を専門的に引き受けます」**

である。

この方が現実的で、反論耐性も高い。

## 10. この仮説が成立するために確認すべき事実

Why Usへ採用する前に以下を確認する。

### 10.1. Service Model

- 当チームのサービスはPoC単体で完結して契約可能か。
- 本番開発や特定製品購入がPoCの前提になっていないか。
- No-Goになってもサービスとして正常終了できるか。

### 10.2. Delivery Model

- Business Question整理を行う人と実際にCoding / Analysisする人は同一または密な同一チームか。
- Senior DS / Scientistが顧客との議論に直接参加するか。
- 営業 / Consultant → Offshore / Junior Deliveryのような強いHandoffがないか。

### 10.3. Output Portability

- PoC成果を他のSIer / Vendor / 内製チームへ引き継げるか。
- Code / Data Definition / Assumption / Validation Requirement等をどこまで引き渡せるか。
- Ariadneなしでも成果を利用できるか。

### 10.4. Analytical Scope

- Predictive / Causal以外に、必要に応じたEDA、Experimental Design、Optimization等をどの程度扱えるか。
- 非定型問題をスクラッチで扱った実績があるか。

### 10.5. Evidence

- 「PoC結果としてNo-Go / 追加データ / Redesignを返した」実例があるか。
- PoC結果が後続の本番要件・RFP・投資判断へ利用された実例があるか。
- 顧客から「専門家が直接入ること」が評価された実例があるか。

## 11. 今回の暫定結論

競合差別化を考える際、これまでの議論は、

> 「当チームはBusinessもScienceもTechnologyもちゃんとやる」

という**能力品質の説明**に留まっていた。

しかし、競合各社を彼ら自身の立場から見ると、彼らも同じ能力を主張する合理性があり、実際にそのように市場へ訴求している。

したがって、Why Usでは能力比較ではなく、**「何のために存在するチームなのか」というRole / Categoryの差**を作るべきである。

現時点で最も有力なのは、

> **当チーム = 本番投資前のAnalytical R&D / Evidence Gate**

という位置づけである。

すなわち、

```text
大手コンサル：企業をどう変えるか
SIer：どう本番システムを作り運用するか
AI Vendor：どうAIを速く展開・Scaleするか

当チーム：
そもそも、その意思決定はデータで改善できるのか？
何を本番化する価値があるのか？
```

という役割分担である。

このPositioningなら、競合の強みを否定せず、むしろ競合が強力であるほど「大きな後続投資の前に専門的なPoCで確かめる」合理性を作れる。

さらに、以下が事実として成立するなら差別化は強くなる。

1. **本番実装・特定Productから独立したPoC**
2. **問いを設計した専門家がHands-onで分析まで担当**
3. **成果物を後続Vendor / 内製へPortableに引き渡せる**
4. **PredictionとCausal Inferenceを含む非定型のAnalytical R&Dに対応**
5. **GoだけでなくNo-Go / Redesignを正式な成果として扱う**

次の検討では、この5点について「実際の当チームはどこまで事実として言えるか」を確認し、その証拠があるものだけを用いてSlide 5のMessage / Chartへ落とすのがよい。
