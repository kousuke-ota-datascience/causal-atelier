# 19. Slide 19｜予測モデルの評価と解釈

## 19.1. Message

**予測モデルは、未知データ性能だけでなく、信頼性・失敗条件・Decision Utilityまで評価して利用可否を判断する。**

## 19.2. Chart

**チャートタイトル:** Prediction / Detection Performanceを、業務利用可否まで4層で評価する

### 19.2.1. Chart Structure

```text
① GENERALIZATION
Locked HoldoutでBaselineを超えるか
分類 / 回帰 / 時系列 / 異常検知をTaskに応じて評価
        ↓
② RELIABILITY
Score / Probabilityをどこまで信頼できるか
Calibration / Stability / Uncertainty
        ↓
③ FAILURE MODE
どこで・どのように外れるか
Segment / Period / Equipment / Error Type / Error Cost
        ↓
④ BUSINESS UTILITY
OutputをDecision Ruleへ変換して使えるか
Ranking / Threshold / Capacity / Action Cost
Baseline Decisionとの比較
        ↓
「性能が高いか」ではなく
「誤りを含めてもDecisionに使えるか」
```

### 19.2.2. Chart内の最小表示テキスト

- ① GENERALIZATION｜Locked HoldoutでBaselineを超えるか
- ② RELIABILITY｜Calibration / Stability / Uncertainty
- ③ FAILURE MODE｜Segment / Period / Equipment / Error Cost
- ④ BUSINESS UTILITY｜Ranking / Threshold / Capacity / Action Cost
- **誤りを含めてもDecisionに使えるか**

## 19.3. Supporting Logic

### 19.3.1. Slide 19の役割

- Slide 17ではPrediction QuestionとValidation Designを固定した。
- Slide 18では同じ条件のもとでFit-for-useなModelを選定した。
- **Slide 19では、選定済みModel / Detection Pipelineを業務Decisionへ使えるかという観点まで含めて評価する。**
- Generalization → Reliability → Failure Mode → Business Utilityの順にEvidenceを積み上げる。

### 19.3.2. Layer 1｜Generalization

| Task | 指標候補 | 主に確認すること |
|---|---|---|
| Binary Classification | AUROC、AUPRC、Precision、Recall等 | Ranking、Class imbalance、見逃し / 過剰対応 |
| Regression | MAE、RMSE、Quantile loss等 | 誤差の大きさ、Outlier |
| Forecast / RUL | Horizon別MAE等 | 予測先による劣化、Time Splitでの再現性 |
| Ranking / Risk | Precision@K、Recall@K、Lift等 | Capacity制約下の優先対象選定 |
| Anomaly Detection | Labelがある場合のPrecision / Recall、Event-level検知率、誤報率等 | 重大異常の捕捉とAlert負荷 |

- 異常検知では正解Labelが不完全なことも多く、MetricだけでなくKnown Event、専門家Review、Alert頻度等を組み合わせる場合がある。
- 設備案件では新期間だけでなく、必要に応じて未見設備・別拠点へのGeneralizationも確認する。

### 19.3.3. Layer 2｜Reliability

- Failure ProbabilityをThresholdやRisk Bandへ使う場合、Ranking性能だけでなくCalibrationを確認する。
- 期間、設備型式、拠点、運転条件等で性能が極端に変動しないかStabilityを見る。
- RUL等の不確実性を推定できる場合は、Uncertaintyが大きいCaseをHuman Reviewへ回す設計も検討する。
- Anomaly Scoreは確率とは限らないため、Scoreの意味をFailure Probabilityとして説明しない。

### 19.3.4. Layer 3｜Failure Mode

1. Segment / Equipment：設備種・拠点・運転条件で性能差がないか。
2. Period：季節、保全方針変更、設備更新等で劣化しないか。
3. Error Type：False Negative / False Positive、早すぎ / 遅すぎ検知のどれが多いか。
4. Error Cost：突発停止、不要点検、早期交換等へどう影響するか。
5. Failure Magnitude：重大設備で致命的な見逃しがないか。

- 重要条件で不足する場合、対象範囲限定、Human Review、Safety Rule、追加Data等を利用条件へ反映する。
- SHAP等はModel挙動理解に用いるが因果効果として解釈しない。

### 19.3.5. Layer 4｜Business Utility

| Decision Pattern | Offline評価例 | 確認したいこと |
|---|---|---|
| PRIORITIZE / REVIEW | Top-K Capture、Lift、Alert burden | 限られた点検件数で重要対象を拾えるか |
| THRESHOLD | Expected Error Cost、Threshold別Utility | 見逃しと不要対応のTrade-offを許容できるか |
| SCHEDULE | 早すぎ / 遅すぎCost、RUL error | 点検・交換時期をBaselineより改善できるか |
| ALLOCATE / PLAN | Scenario Simulation、Capacity mismatch | 人員・部品配分のMismatchを減らせるか |

- OfflineでDecision Utilityの仮説は評価できるが、実Business Outcome改善を直接証明するわけではない。
- 保全施策そのものの効果を確認する場合は、Production比較、実験、因果評価等を別途設計する。

### 19.3.6. Success Criteriaへ戻して利用可否を判断する

- Locked HoldoutでBaselineを超えるか。
- 重要設備・Segmentで許容できるか。
- Score / Probability / RULをDecision Ruleへ使えるか。
- 誤りのDownsideをHuman Review / Safety Rule等で制御できるか。
- 実運用時点で必要Dataを取得できるか。

これらを次SlideのEvidence Packageへ渡す。

## 19.4. Speaker Note

Modelの評価では、Accuracyだけでは足りません。まず未知データでBaselineを超えるか、次にScoreやProbabilityが安定して使えるかを確認します。そのうえで、どの設備・期間・条件で外れるかを見て、最後に実際の点検件数や誤判定Costを入れてDecisionとして有用かを判断します。

異常検知では正解Labelが十分でない場合もあるため、既知の異常Eventや専門家Review、Alert負荷を組み合わせて評価することがあります。また、Anomaly Scoreを故障確率として読み替えないことも重要です。
