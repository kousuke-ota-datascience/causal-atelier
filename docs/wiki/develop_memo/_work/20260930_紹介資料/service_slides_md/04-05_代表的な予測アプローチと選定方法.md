# 15. Slide 15｜代表的な予測アプローチと選定方法

## 15.1. Message

**予測モデルは、高度さではなく、必要性能・説明性・安定性・運用制約を満たすFit-for-useで選定する。**

## 15.3. Supporting Logic

### 15.3.1. Slide 15の役割

- Slide 14では、Prediction Question、Prediction Time、Target / Feature、Split、Holdout、BaselineをModel開発前に固定する必要性を示した。
- **Slide 15では、その固定条件の内側で、どのModel Familyを採用するかを決める。**
- 主題は「代表アルゴリズムの紹介」ではなく、**案件ごとに必要な性能と運用条件を満たすModelを、Baselineからの増分価値で選ぶ判断ロジック**である。

### 15.3.2. Model FamilyはDataとQuestionに合わせて候補化する

代表的な候補は以下だが、案件ごとに必要なFamilyだけを比較する。

| Model Family | 向きやすい状況 | 主な留意点 |
|---|---|---|
| Linear / Logistic | 比較的単純な関係、説明性重視、小〜中規模表形式 | 非線形・高次Interactionの表現力に限界 |
| Tree | 非線形・条件分岐を扱いたい | 単木はVarianceが大きくなりやすい |
| Random Forest | 非線形、頑健な表形式予測 | Model size、局所説明、Calibration等を確認 |
| Gradient Boosting | 表形式で高性能が必要、非線形・Interactionが重要 | Tuning、過学習、Calibration、推論Costを確認 |
| Time-series / Forecasting | 時間依存・季節性・Trendを明示的に扱う | Forecast HorizonとBacktest設計が重要 |
| Domain-specific / Other | Text、Image、Graph、Survival等 | Data量、運用基盤、専門的Validationが必要 |

- この表は候補の整理であり、「この条件なら必ずこのModel」という決定表ではない。
- 同じModel FamilyでもFeature設計、Regularization、Hyperparameter、Training schemeにより性能・安定性は変わる。

### 15.3.3. Baselineを起点にComplexityの増分価値を見る

- Baselineは、現行Rule、単純Score、Majority / Mean予測、Linear / Logistic等から案件に合うものを置く。
- Candidateは必ず**同じSplit / Validation / Metric定義**で比較する。
- 複雑なModelがわずかな性能改善しか生まない一方、Explainability、Latency、更新Cost、保守負荷が大きく増えるなら、単純Modelの方がFit-for-useな場合がある。
- 逆に、誤判定Costが高く、性能改善がDecision Utilityへ直結する場合は、複雑なModelの追加Costが正当化されることがある。

### 15.3.4. Fit-for-useは複数軸で判断する

Model Selectionでは少なくとも以下を確認する。

1. **Predictive Performance**：目的に必要なDiscrimination / Error水準を満たすか。
2. **Calibration / Reliability**：ProbabilityやScoreをDecision Ruleに使える程度に信頼できるか。
3. **Stability**：期間・Segment・再学習で性能が極端に不安定でないか。
4. **Explainability / Reviewability**：Human ReviewやStakeholder説明に必要な理解可能性があるか。
5. **Operational Fit**：Latency、Batch / Online、更新頻度、Model size、依存ライブラリ、Cost等が許容されるか。
6. **Data Fit**：Sample Size、欠損、Cardinality、Drift、Label availability等に対して現実的か。

- これらの優先順位は案件のDecision Criticalityと運用形態で変わる。
- たとえばHuman Review前提のRanking用途と、Low-latency自動判定用途では最適なModelは異なる。

### 15.3.5. Explainabilityは選定条件だが、因果説明ではない

- Feature Importance、Permutation Importance、SHAP等は、Modelがどの変数を使ってPredictionを変えているかを理解するために有用である。
- ただし、Predictive Explanationは「この変数を変更すればOutcomeが変わる」というCausal Effectを意味しない。
- したがってExplainabilityは、Model Review、Error Analysis、Stakeholder Communication、Governanceのために用い、介入判断の根拠へそのまま読み替えない。

### 15.3.6. Hyperparameter探索もValidation設計の内側で行う

- Hyperparameter Tuning、Feature Selection、Model Family比較はTrain / Validation内で行う。
- 同じValidation setを多数回見て選択を繰り返すと、そのValidationへの過適合が起こり得るため、Cross-validationやNested scheme等を必要に応じて使う。
- 最終HoldoutはSlide 14の原則どおりModel Selectionに使わない。

### 15.3.7. サービス紹介資料としての位置づけ

- 当チームの価値は特定アルゴリズムの販売ではなく、**Question / Data / Decision条件に応じて適切なModel FamilyとComplexityを選び、未知データでの再現性と業務利用性を検証すること**にある。
- 実装はデータサイエンティストによるスクラッチ開発を基本とし、成熟したOSS / Libraryを必要に応じて利用する。
- Ariadneの現時点の実装済みModel範囲と、分析サービスとして提供可能なModel範囲は同一ではないため、資料上で混同しない。

## 15.4. Speaker Note

ここではアルゴリズム一覧を覚えていただくことが目的ではありません。重要なのは、Slide 14で固定したValidation条件のもとで、現行Ruleや単純Baselineからどれだけ増分価値があるかを比較し、業務に必要な条件を満たすModelを選ぶことです。

たとえばGradient Boostingが最も高いAccuracyを出しても、改善幅が小さく、説明性や更新Costが大きく悪化するなら、より単純なModelを採用する方が合理的です。一方、誤判定Costが大きく、わずかな性能差がDecision Utilityへ大きく効く場合は、複雑なModelを選ぶ理由があります。

また、SHAP等でModel挙動を説明できても、それは原因説明ではありません。Predictive Modelが使う関連と、Treatmentを変えたときのCausal Effectは分けて扱います。

## 15.5. Slide 15からSlide 16への接続

> **Modelを選定した後は、単一のAccuracyではなく、未知データでの再現性・信頼性・失敗パターン・業務Utilityまで含めて利用可否を評価する。**
