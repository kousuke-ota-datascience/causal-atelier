# 12. Slide 12｜予測分析が適する業務課題

## 12.1. Message

**予測分析は、結果前の多数の判断に予測を組み込み、誤りを許容しつつKPIの期待値を改善する。**

## 12.2. Chart

**チャートタイトル:** 予測分析の適用候補を「先に動けるか」と「誤りを含む予測を累積価値へ変えられるか」で見極める

Slide 11で示した `Decision時点の観測情報 → Prediction → Decision / Action` を受け、予測分析を適用しやすい業務を、特定の業界や予測対象ではなく、**Outcomeが判明する前にPredictionを利用してActionを変えられ、個々の予測誤りを許容しながら多数のDecisionで期待値を積み上げられるか**という業務構造で整理する。

## 12.3. Supporting Logic

### 12.3.1. Slide 12の役割

- Slide 11では、Predictiveを `Decision時点で利用可能な観測情報 → Prediction → Decision / Action` として定義し、Predictionの価値はOutcomeが判明する前に判断を変えられることにあると示した。

- **Slide 12では、これらをPredictiveの適用判断へ具体化し、「どのような業務構造ならPredictionをActionへ接続し、予測誤差を含みながらもKPIの期待値を改善しやすいか」を示す。**
- Slide 13では、そのPredictionをActionへ利用した場合に、どのような期待効果へ接続し得るかをValue Chainとして示す。そのため本スライドではBusiness Outcomeの種類を主題にしない。

### 12.3.2. Predictive PoC候補となる6条件

Predictive Modelは、個々の事象を必ず正しく言い当てる仕組みではない。実務上の価値は、一定のPrediction Errorを前提に、**多数のDecisionへ予測情報を組み込み、Baselineより良い判断を繰り返すことでKPIの期待値を改善できるか**で考える方が適切である。

したがってPredictive PoC候補は、Actionへ接続できるかだけでなく、予測の不確実性を業務プロセスの中で扱えるかまで確認する。

#### 12.3.2.1. ① BEFORE｜Outcomeが判明する前にDecisionがある

- Predictiveの価値は、未知・将来のOutcomeに関する見通しを、Outcome確定前のDecisionへ利用することにある。
- Outcomeが判明した後にしかActionできない業務では、PredictionによってDecisionを先回りさせる価値は生じにくい。
- したがって、「何を予測するか」だけでなく、**いつDecisionし、Outcomeはいつ確定し、Actionにどの程度のLead Timeが必要か**を確認する必要がある。
- 例えば、解約対応は実際の解約前、配送対応は遅延確定前、設備保全は停止前にPredictionを利用できることが前提となる。

#### 12.3.2.2. ② CHANGE｜Predictionに応じて変更可能なActionがある

- Predictionは判断材料であり、それ自体が業務価値ではない。
- Predictionを見ても何も変更できない場合、分析結果を業務Actionへ接続する経路が弱い。
- Predictiveで変更対象になりやすいActionには、以下がある。
  - **Prioritize**：どの対象へ先に対応するか。
  - **Review / Escalate**：どの案件を重点確認・追加審査するか。
  - **Schedule**：いつ点検、交換、Follow-up等を実施するか。
  - **Allocate / Plan**：人員、時間、Capacity等をどこへ配分するか。
- Actionは案件ごとに異なり、Predictionが自動的にActionを決めるわけではない。実際の利用時にはDecision Ruleや業務制約を介して判断する。

#### 12.3.2.3. ③ DIFFERENTIATE｜Predictionによって判断を変える余地がある

- 予測分析が特に有効なのは、対象、案件、時点等によってRiskや将来状態が異なり、それに応じてActionを差別化できる業務である。
- すべての対象へ同じActionを実施でき、かつそれが合理的である場合、個別Predictionによる優先順位付けの追加価値は小さい場合がある。
- 一方、対応可能件数、検査能力、保全要員、処理Capacity等に制約があり、全件へ同じ強度で対応できない場合、Predictionは限られたResourceの配分判断に利用しやすい。
- ただし、Predictionによる差別化が業務上許容されるかは別途確認が必要である。公平性、規制、契約条件、安全上の要件等により、Predictionに応じたAction変更へ制約がある場合がある。

#### 12.3.2.4. ④ REPEAT / ACCUMULATE｜多数のDecisionで予測上の優位を累積できる

- Predictiveの典型的な価値は、1回のPredictionを100%当てることではなく、**同種のDecisionを多数回行う中で、Baselineより平均的に良い判断を積み上げること**にある。
- 例えば、毎月多数の顧客へFollow-up対象を選ぶ、毎日多数のShipmentを優先管理する、多数の製品から重点検査対象を選ぶ、といった業務では、個々の誤りが残っても全体KPIを改善できる可能性がある。
- この意味で、Predictionは大きな単発Decisionを完全自動化するより、日常業務の細かな判断へ埋め込む方が価値を作りやすい場合がある。
- ただし、**反復性は絶対条件ではない。** 単発または低頻度のDecisionでも、十分なPredictive Signalがあり、不確実性を評価でき、誤りのDownsideを管理できる場合には利用可能である。

#### 12.3.2.5. ⑤ TOLERATE｜個々の誤予測を一定範囲で許容・緩和できる

- Predictive ModelにはFalse Positive、False Negative、Forecast Error等が残るため、業務設計は「誤りゼロ」を暗黙前提にしない。
- 適用しやすいのは、個々の誤りによる損失が限定的、または以下の仕組みで影響を緩和できる業務である。
  - Human review / Second check
  - Prediction confidenceが低いCaseでは自動判断しないAbstention
  - Safety rule / Hard constraintによる上限制御
  - 高Risk Decisionだけ追加審査へ回すEscalation
  - Action強度を段階的に変えるSoft intervention
- 逆に、1回の誤判定が重大な安全事故、不可逆な権利侵害、極端な経済損失等へ直結し、代替確認やFail-safeも置けない場合、Prediction単独での自動Decisionには適しにくい。
- 重要なのはAccuracyの高さだけではなく、**誤りの種類・頻度・Costを業務側で扱えるか**である。

#### 12.3.2.6. ⑥ OBSERVE｜OutcomeとKPIを事後観測できる

- Predictionの有用性を継続的に確認するには、予測対象Outcomeが後から観測でき、Predictionと実績を照合できる必要がある。
- Outcomeを観測できれば、Accuracy / Calibration / Ranking等のModel Performanceだけでなく、False Positive / False Negativeの発生、Segment別性能、Decision Ruleの妥当性を継続評価できる。
- さらに、対象KPIやAction履歴を追跡できれば、Predictionを使った運用が現行Ruleと比べてどのようなOperational Utilityを持つかを検討しやすい。
- Outcomeが長期間観測できない、Labelが不安定、ActionによってOutcome定義自体が変わる等の場合は、Feedback Loop設計をPoC段階で検討する必要がある。

### 12.3.3. 適用候補とTechnical Feasibilityを分ける

- 上記6条件は、**業務課題としてPredictiveを検討する価値があるか**を見るための条件であり、十分な予測性能を事前に保証するものではない。
- 実際にPredictionを業務で利用できるかはPoCで検証する。案件に応じて、少なくとも以下を確認する。
  - Decision時点で利用可能なFeatureとTarget / Outcomeを構成できるか。
  - Target Leakage / Future Leakageを避けた検証ができるか。
  - 十分なSample / Event数があり、性能と不確実性を評価できるか。
  - 適切に分離した未知データで、Baselineに対して有用な予測性能が再現するか。
  - Probability等を判断材料に使う場合、Calibrationが利用目的に対して十分か。
  - False Positive / False Negativeや予測誤差が、業務コストやCapacity制約に対して許容可能か。
  - PredictionをDecisionに間に合うLatency / Frequencyで提供できるか。
  - 時間変化、対象母集団の変化、データ取得条件の変化によって性能が崩れないか。必要に応じてDrift監視・再学習が可能か。
- これらはSlide 14以降のPredictive固有workflow、Model Evaluation、Go / No-Goで具体化する。

### 12.3.4. 代表ユースケースは業界ではなくAction構造で見る

公開Competition、Open Data / Public Dataset、企業公開事例を再整理すると、Predictive Analyticsの適用対象はCustomer、Operations / Logistics、Business Process、Quality、Maintenance、Risk等へ広く存在する。

本スライドでは、サービスScopeを特定Domainへ限定して見せないため、以下のようにAction構造で代表例を整理する。

| Action構造 | Prediction Questionの例 | Prediction後のAction |
|---|---|---|
| Prioritize | 誰が解約しそうか / どの製品が不良になりそうか | Follow-up / 検査対象を優先 |
| Review / Escalate | どの配送が遅れそうか / どのCaseがDeviationしそうか | High-risk案件を重点管理 |
| Schedule | どの設備が停止しそうか / あとどの程度使えるか | 点検・交換時期を調整 |
| Allocate / Plan | Case完了までどの程度かかりそうか | 人員・Capacity配分を調整 |

- CustomerではChurn / Response、OperationsではDelivery Delay / Process Completion、QualityではDefect、MaintenanceではFailure / Remaining Useful Life等の公開Problemが存在する。
- これらはPrediction Target自体が異なっても、**Outcome判明前にPredictionを使ってActionを変える**という共通構造を持つ。
- 故障予測は有力なIndustrial Use Caseの一つだが、Predictive Service全体を代表する唯一の例ではない。

### 12.3.5. PredictiveとCausalの境界

- `高Riskな対象を見つけて対応優先順位を決める` ことはPredictiveの代表的な利用方法である。
- ただし、`高Riskな対象` と `特定施策によって最もOutcomeが改善する対象` は一致するとは限らない。
- 例えばChurn Riskが高い顧客を予測できても、Retention施策によるTreatment Effectが大きい顧客であるとは限らない。
- Predictionを原因分析や施策効果として解釈せず、施策によるOutcome変化を知りたい場合はCausal Questionとして別途扱う。

## 12.4. Speaker Note

前のスライドでは、予測分析を「結果がまだ分からない時点でPredictionを得て、事前のDecisionやActionへ使う分析」と整理しました。では、どのような業務で予測分析を使いやすいのでしょうか。

ここで重要なのは、予測モデルは個々の事象を必ず当てる仕組みではないということです。実務では、一定の誤りが残る前提で、多数のDecisionに予測を組み込み、現行Ruleより平均的に良い判断を積み上げることでKPIを改善する、という使い方が中心になります。

そのため、適用条件は2種類に分けて考えます。まず、PredictionをActionへ接続できることです。結果が分かる前にDecisionがあり、Predictionを見て対象、時期、量、優先順位等を変えられ、対象や時点ごとに判断を変える余地があることです。

もう一つは、予測の不確実性を業務で扱えることです。同種のDecisionが多数または反復して発生し、小さな予測上の優位を累積できること。個々の誤予測をHuman reviewや追加確認、Safety Rule等で許容・緩和できること。そしてPrediction後にOutcomeやKPIを観測し、誤り方と有用性を継続評価できることです。

例えば、解約Riskや不良Riskを使って毎月多数の対象から優先対応先を選ぶ、配送遅延Riskから重点管理対象を選ぶ、といった用途では、すべてを正しく予測できなくても、限られたResourceの配分を全体として改善できれば価値があります。

逆に、一回の誤判定が致命的で、Human reviewやFail-safeも置けない単発DecisionをPredictionだけで自動化する用途は慎重に扱うべきです。ただし、単発Predictionが常に不適切という意味ではありません。不確実性とDownsideを十分管理できる場合には利用できます。

また、この6条件を満たすからといって、実際に十分な予測精度が得られるとは限りません。Decision時点で使えるデータがあるか、未来情報の混入なく未知データで性能が再現するか、必要なLatencyを満たせるか、分布変化へ対応できるか等はPoCで検証します。

高Riskな対象が、特定施策で最も改善する対象とは限りません。施策効果を知りたい場合は、予測とは別に因果の問いを立てます。

## 12.5. Slide 12からSlide 13への接続

> **予測分析は、Outcome判明前のDecisionへPredictionを組み込み、誤りを許容しながら多数の判断で期待値を改善する。では、そのAction変更はどのような業務効果へ接続し得るのか。**
