# 24. Slide 24｜因果構造と前提条件の整理

## 24.1. Message

**因果効果を推定するには、変数の時間順序と因果上の役割を分け、Estimandに応じて「何を調整するか」を設計する必要がある。**

## 24.2. Chart

**チャートタイトル:** 同じ「関連変数」でも、因果上の役割でAdjustmentは変わる

### 24.2.1. Chart Structure

Confounder / Mediator / Colliderを一つのDAGへ混在させず、3つの独立した最小DAGを横並びで比較する。

```text
A｜Confounding                 B｜Mediation                  C｜Collider

    C                               T                          T      U
   ↙ ↘                              ↓ ↘                         ↘    ↙ ↓
  T → Y                             M → Y                         Z    Y

Pre-treatment C                 Post-treatment M              ZにConditioningすると
TとY双方に影響                 Treatment経路上                非因果Pathを開き得る
        ↓                              ↓                           ↓
Adjustment候補                 Total Effectでは               原則として安易に
                              安易に調整しない                 調整しない
```

最下部にTemporal Orderingの帯を置く。

```text
Pre-treatment ---------------- Treatment ---------------- Post-treatment
         変数の役割を時間順序とEstimandから判断する
```

**PowerPoint上の配置・強調**

- 3つのDAGカードを同じ大きさで横並びにする。
- 各カードは `構造 → 役割 → Adjustment上の含意` の順で読む。
- Confounderだけを「Adjustment候補」として強調し、Mediator / Colliderは「入れれば安全ではない」ことを対比する。
- 下段にTemporal Orderingを置き、Treatment後に決まる変数をPre-treatment Covariateと同様に扱わないことを示す。
- DAGはDomain Knowledge / Data Generating Processに関する仮定の可視化であり、自動的に真の因果構造を発見する図として描かない。

### 24.2.2. Chart内の最小表示テキスト

- **Confounder**｜TとYの双方に影響
- → Adjustment候補
- **Mediator**｜Treatmentの効果経路上
- → Total Effectでは安易に調整しない
- **Collider**｜複数の原因が合流
- → ConditioningでBiasを導入し得る
- Pre-treatment → Treatment → Post-treatment
- **変数を多く入れるほど安全、ではない**

## 24.3. Supporting Logic

### 24.3.1. Slide 24の役割

- Slide 23ではTreatment / Outcome / Population / Time / Contrastを固定し、Estimandを定義した。
- **Slide 24では、そのEstimandに対して、どの変数を調整すべきか・調整すべきでないかをCausal Structureから設計する。**
- 主題はDAGそのものではなく、変数の役割とTemporal Orderingを明示し、Adjustment SetとAssumptionの根拠を関係者で共有することである。
- 次のSlide 25では、こうして整理したAssumptionのもとでEstimandをObserved Dataから表現できるか、Identificationを検討する。

### 24.3.2. Confounder｜Backdoor Pathを閉じるためのAdjustment候補

- ConfounderはTreatmentとOutcomeの双方へ因果的に影響するPre-treatment Variableである。
- 未調整だと、Treatment群とControl群のOutcome差にConfounder由来の差が混在し、Causal EffectとAssociationを分離できない場合がある。
- ただし「Outcomeと相関がある」「Treatment予測に重要」というだけではConfounderとは限らない。因果上の位置づけが必要である。
- 調整対象は個々の変数ではなく、Estimandを識別するためにBackdoor Pathを閉じるAdjustment Setとして考える。
- 必要なConfounderが未観測の場合、単純なCovariate AdjustmentではIdentificationできない可能性を明示する。

### 24.3.3. Mediator｜調整するとEstimand自体が変わり得る

- MediatorはTreatmentからOutcomeへの因果経路上に位置するPost-treatment Variableである。
- Total Effectを知りたい場合、MediatorへConditioningするとTreatment Effectの一部を遮断し、別の対象量を推定することになる場合がある。
- Direct / Indirect Effectを知りたい場合はMediation Analysisとして別のEstimandを定義し、追加のAssumptionを検討する必要がある。
- したがって「Prediction性能が上がるから」「Outcomeと強く関連するから」という理由でTreatment後変数をAdjustmentへ追加しない。

### 24.3.4. Collider｜調整によって新たなBiasを作り得る

- Colliderは複数の原因から矢印が入る変数である。
- 本来閉じているPath上のColliderへConditioningすると、そのPathを開き、TreatmentとOutcomeの間に非因果的なAssociationを導入し得る。
- Selection Variable、Sample Inclusion、Post-treatment Behavior等がColliderとなるケースもある。
- 「利用可能な変数は全部入れる」という回帰式設計は、このCollider Biasを誘発する可能性があるため安全策ではない。

### 24.3.5. Temporal Orderingは最低限の整合性チェックになる

- 変数がTreatment前に決まるのか、Treatment後に決まるのかを確認することは、Causal Structure設計の基本である。
- Treatment後に観測された変数をPre-treatment Confounderとして扱わない。
- 同じ変数名でも、測定時点によって役割が変わる場合がある。例えば利用頻度が施策前の履歴ならConfounder候補になり得るが、施策後の利用頻度ならMediatorとなり得る。
- Dataset上の列名ではなく、業務Process上の生成時点を確認する必要がある。

### 24.3.6. DAGの役割と限界

- DAGは、Domain KnowledgeとData Generating Processに関する仮定を可視化する道具である。
- DAGを描いたこと自体でAssumptionが真になるわけではない。
- 観測データだけから真のCausal Graphを一意に自動発見できると前提にしない。
- 実務では、施策担当者・業務担当者・Data Scientistが、Treatment Assignment、Data取得時点、Policy Rule、Measurement Processを照合しながらGraphをレビューする。
- Graph上のArrowについて、Evidenceが強い部分と業務仮定に依存する部分を区別して記録することが望ましい。

### 24.3.7. Adjustment Set設計時の実務チェック

少なくとも以下を確認する。

1. Treatmentより前に測定されているか。
2. Treatment AssignmentとOutcomeの両方に関係する原因候補か。
3. MediatorやColliderを誤って含めていないか。
4. 重要なConfounderが未観測ではないか。
5. Adjustment後もTreatment / Controlの比較可能なSupportが残るか。
6. EstimandとAdjustment Setの組み合わせが一致しているか。

- この確認結果をSlide 25以降のIdentification AssumptionとDiagnosticsへ渡す。

## 24.4. Speaker Note

因果分析では、Outcomeと関連する変数をすべて回帰式へ入れれば安全、という考え方は取りません。重要なのは、その変数が因果構造のどこにいるかです。

左のConfounderはTreatmentとOutcomeの両方に影響するTreatment前の変数で、未調整だと施策効果と元々の顧客差が混ざるため、Adjustment候補になります。ただし相関が強いだけでConfounderと決めるのではなく、業務上の生成過程を確認します。

中央のMediatorはTreatmentの効果がOutcomeへ伝わる経路上にあります。Total Effectを知りたいのにMediatorを調整すると、知りたい効果の一部を消してしまう場合があります。右のColliderはさらに注意が必要で、条件付けることで本来なかったAssociationを作ることがあります。

そのため、変数選択はFeature Selectionとは考え方が異なります。いつ測定されたか、Treatmentの前か後か、業務Process上どのように決まるかをDomain Expertと一緒に整理します。

DAGは真実を自動的に発見する図ではありません。どの因果構造を仮定しているかを可視化し、「この変数をなぜ調整するのか」「この前提が崩れたら何が言えなくなるのか」を関係者で確認するために使います。
