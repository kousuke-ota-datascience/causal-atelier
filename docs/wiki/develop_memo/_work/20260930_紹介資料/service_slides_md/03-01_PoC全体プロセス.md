# 9. Slide 9｜PoC全体プロセス

## 9.1. Message

**PoCは「業務課題の定義」から「意思決定への接続」までを一連のプロセスとして進め、分析工程だけを切り離さない。**

## 9.2. Chart

**チャートタイトル:** 業務設計から意思決定までをつなぐPoC共通プロセス

Slide 7〜8で具体化したDecision / Analysis Question / 利用ルールをPoCの入口に置き、Data Assessmentから分析設計・実行・検証を経て、Decision / ActionとNext Phaseへ戻るまでを、**業務設計 → 分析検証 → 業務接続**の3フェーズとして示す。

## 9.3. Supporting Logic

### 9.3.1. Slide 9の役割

- Slide 6では、PoCで `分析成立性 / 業務利用性 / 次フェーズ判断` を検証するという目的を定義した。
- Slide 7では、Business Questionから `Decision → Required Evidence → Analysis Question` を逆算する考え方を示した。
- Slide 8では、分析結果を実際のDecision / Actionへ変換するために、`WHO / WHEN / Decision Rule / Action` という利用ルールを具体化した。
- **Slide 9では、これらの業務設計をPoCの入口に置き、分析検証を経て再び業務判断へ戻るまでの共通プロセスを俯瞰する。**
- Slide 10では、このプロセスを開始・終了する際に何を合意・確認するかをStart Gate / Exit Gateとして具体化する。

### 9.3.2. ① 業務設計｜何の判断のためのPoCかを固定する

- PoCは、手元のデータや利用したいAlgorithmから開始するのではなく、Business QuestionとDecisionを起点とする。
- Decisionに必要なEvidenceを定義し、それをPrediction QuestionまたはCausal Questionへ変換する。
- さらに、分析結果を誰がいつ利用し、どの基準で何のActionへつなげるかを利用ルールとして定義する。
- ここで定義したDecision / Analysis Question / 利用ルールが、後続のData Assessment、Analysis Design、Validationの判断基準になる。
- ただし、初期定義を無条件に固定するわけではない。データ不足や科学的成立条件、業務制約により検証不能と判明した場合は、Business Questionとの整合を保ちながらScopeを見直す。

### 9.3.3. ② 分析検証｜問いに対するEvidenceを作り、妥当性を確かめる

1. **Data Assessment**
   - 必要なPopulation、Outcome / Target、Treatment、特徴量、時点情報等が利用可能かを確認する。
   - 欠損、観測粒度、データ生成過程、Leakage、Selection等、分析成立性に影響する条件を把握する。
2. **Analysis Design**
   - Analysis Questionに対し、評価方法、比較条件、Baseline、データ分割、Assumption、Diagnostics等を設計する。
   - Predictive / Causalで必要な設計内容は異なるため、共通工程名だけで意味論を統一しない。
3. **Execution**
   - 合意した設計に基づき、データ処理、モデル学習、推定、評価用Artifact生成等を実行する。
4. **Validation / Interpretation**
   - Predictiveでは主に未知データでの性能、Calibration、Error Pattern等を、CausalではIdentification Assumption、推定不確実性、Diagnostics / Sensitivity等を案件に応じて確認する。
   - 数値結果だけでなく、成立条件・限界・どこまで主張できるかを整理し、業務判断に利用できるEvidenceへ変換する。

### 9.3.4. ③ 業務接続｜EvidenceをDecision / Actionと次フェーズ判断へ戻す

- Validation / Interpretationで得たEvidenceを、Slide 8で定義したDecision Ruleや業務制約と照合する。
- Predictiveでは、予測結果を対象選択、優先順位、計画、Resource配分等へ利用できるかを判断する。
- Causalでは、Effect Estimateと不確実性、Assumption等を、施策の実施・継続・変更等へ利用できるかを判断する。
- PoC終了時のActionは本番化だけではない。追加検証、追加データ取得、Scope変更、中止も合理的なNext Phaseとなり得る。
- このため、PoCの出口は「分析結果を納品すること」ではなく、**結果と限界を根拠に次の意思決定を行える状態**とする。

### 9.3.5. 入口と出口にDecisionが現れる理由

- 入口のDecisionは、**何の判断に必要なEvidenceを作るかを定義する設計アンカー**である。
- 出口のDecision / Actionは、**PoCで得たEvidenceを実際の判断へ適用する工程**である。
- 同じ語が入口と出口に現れるが役割は異なる。入口で利用先を定義し、出口で検証結果をその利用先へ戻すことで、分析工程だけが独立することを防ぐ。

### 9.3.6. PoCは必要に応じて反復する

- 図は主たる読み順を示すため左から右のプロセスとして表現するが、実際のPoCが常に一方向に一度だけ進むことを意味しない。
- Data Assessmentで必要データが不足していれば、Analysis QuestionやScopeを見直すことがある。
- Execution / Validationで性能不足、識別上の問題、Assumption違反等が判明した場合は、Data、Design、Questionへ戻って追加検証することがある。
- ただし、場当たり的に評価指標や問いを変更すると検証の解釈が曖昧になるため、変更理由・前提・判断を記録し、Success Criteriaとの整合を保つ必要がある。

### 9.3.7. Predictive / Causal固有workflowとの役割分担

- 本スライドは、Predictive / Causalに共通する**PoC運営上の骨格**を示す。
- Predictive固有のPrediction Question、Train / Validation / Test、Model Selection、Calibration、Error Analysis等はPredictive章で扱う。
- Causal固有のCausal Question / Estimand、Causal Structure、Identification、Estimation、Diagnostics / Sensitivity等はCausal章で扱う。
- 共通プロセスを示すことは、Predictive / Causalの成立条件や評価方法が同じであることを意味しない。

## 9.4. Speaker Note

前の2枚では、まず誰が何を決めるのかを起点にAnalysis Questionを定義し、さらに分析結果を誰がいつ使い、どの基準でActionへつなげるかを設計しました。このスライドでは、それらをPoC全体の工程の中に置きます。

PoCの入口は業務設計です。Business QuestionとDecisionを明確にし、必要なEvidenceをAnalysis Questionへ変換し、結果の利用ルールまで定義します。

そのうえで、必要なデータが使えるかを確認し、分析と検証の方法を設計して実行します。ここで重要なのは、PredictiveとCausalで中身は異なるという点です。Predictiveであれば未知データで性能が再現するか、Causalであれば必要な前提のもとでどこまで効果を主張できるか、といった観点で検証します。

最後に、得られた結果と限界を、最初に定義したDecision / Actionへ戻します。そのEvidenceをもとに、本番化するのか、追加検証や追加データが必要なのか、Scopeを変えるのか、あるいは中止するのかを判断します。

つまり、分析部分だけを切り出してPoCとするのではなく、業務上の問いから始まり、分析を経て、再び業務判断へ戻るところまでを一つのプロセスとして扱います。なお、実際にはデータや検証結果に応じて前工程へ戻ることもあります。

## 9.5. Slide 9からSlide 10への接続
