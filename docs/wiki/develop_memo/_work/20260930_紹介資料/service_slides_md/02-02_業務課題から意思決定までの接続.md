# 7. Slide 7｜業務課題から意思決定までの接続

## 7.1. Message

**分析設計は、「誰が何を決めるか」から必要な判断材料を逆算する。**

## 7.2. Chart

**チャートタイトル:** 業務課題をDecision起点でAnalysis Questionへ落とし込む

業務課題をそのまま分析仕様へ変換するのではなく、まず業務上のDecisionを明確にし、そのDecisionに必要なEvidenceを経由してAnalysis Questionへ落とし込む構造を示す。

### 7.2.1. Chart Structure

PowerPoint上では、左から右へ読む4段階の単一フローとする。

```text
┌──────────────────┐   ┌──────────────────┐   ┌────────────────────┐   ┌────────────────────┐
│ Business Question│ → │ Decision         │ → │ Required Evidence  │ → │ Analysis Question  │
│ 何を改善したいか │   │ 誰が何を決めるか │   │ 何が分かれば       │   │ 何を予測・推定     │
│                  │   │                  │   │ 決められるか       │   │ すればよいか       │
└──────────────────┘   └──────────────────┘   └────────────────────┘   └────────────────────┘
                              └────────────── Decisionから分析要件を逆算 ──────────────→

                    業務課題だけでは、分析仕様は決まらない
```

**PowerPoint上の配置・強調**

- `Business Question → Decision → Required Evidence → Analysis Question` を一つの横フローとして示す。
- `Decision` を視覚上のアンカーとして最も強く表示する。Business Questionは目的・背景、Decision以降は分析設計へ落とすための具体化として見せる。
- `Decision → Required Evidence → Analysis Question` の上または下に「Decisionから分析要件を逆算」と示し、分析手法・データから設計を始めないことを強調する。
- `Required Evidence` を置くことで、Business QuestionからAnalysis Questionへ直接ジャンプせず、「何が分かればそのDecisionを改善できるか」を明示する。
- Predictive / Causalの手法分岐、Data / Analysis / Validationの工程、利用タイミング・Action・Threshold等の詳細は主図に入れない。これらは前後・後続スライドの役割として分離する。
- 最下段に「業務課題だけでは、分析仕様は決まらない」を短い補助メッセージとして置く。

## 7.3. Supporting Logic

### 7.3.1. Slide 7の役割

- Slide 6では、PoCで分析成立性だけでなく、分析結果をDecision / Actionの判断材料として利用できるかまで検証することを示した。
- Slide 7では、その業務利用性を検証可能にするための前提として、**業務課題を具体的なDecisionとAnalysis Questionへ接続する考え方**を示す。
- Slide 2の「業務課題と何を知りたいかからPredictive / Causalを選ぶ」というサービス選択より一段具体化し、PoC設計では「誰が何を決めるために、何を知る必要があるか」まで定義する。
- 利用者・利用タイミング・Action・判断基準の詳細はSlide 8、PoC工程全体はSlide 9で扱うため、本スライドでは分析工程や運用設計まで広げない。

### 7.3.2. なぜDecisionを設計アンカーにするのか

- 「解約率を下げたい」「不良を減らしたい」「配送遅延を減らしたい」といった業務課題は、目的を示すが、そのままでは分析Targetや評価対象を一意に定めない。
- 同じ業務課題でも、優先対応対象を選ぶDecisionにはPredictionが、施策を実施・継続するDecisionにはCausal Effectが必要になる場合がある。
- したがって、分析設計では「使いたいAlgorithm」や「手元にあるData」から始めるのではなく、まず誰が何を判断するのかを具体化し、その判断に不足しているEvidenceを定義する。
- Decisionが明確になることで、Analysis Question、Outcome、Prediction Horizon、Treatment / Comparison、評価指標等の候補を具体化しやすくなる。ただし、Decisionだけでこれらが自動的に一意に決まるわけではなく、データ生成過程・利用可能データ・科学的妥当性・業務制約との整合が必要である。

### 7.3.3. 4段階の接続

1. **Business Question｜何を改善したいか**
   - 売上、解約、品質、Lead Time、Cost等、改善したいBusiness Outcomeや業務課題を定義する。
2. **Decision｜誰が何を決めるか**
   - その課題に対して、実際に変更可能な意思決定を特定する。
   - 例：対応対象を選ぶ、施策を継続する、工程条件を変更する、Resource配分を変える。
3. **Required Evidence｜何が分かれば決められるか**
   - Decisionを改善するために不足している判断材料を定義する。
   - 将来Risk、需要量、介入効果、効果の不確実性等が候補となる。
4. **Analysis Question｜何を予測・推定すればよいか**
   - Required Evidenceを、データから評価可能なPrediction QuestionまたはCausal Questionへ変換する。
   - ここで初めて、Target / Outcome、Prediction Horizon、Treatment、Comparison、Population等の分析要件を具体化する。

### 7.3.4. Predictive / Causalでの具体例

**Predictiveの例｜解約対応**

```text
Business Question
解約を減らしたい
        ↓
Decision
対応Resourceを、どの顧客へ優先配分するか
        ↓
Required Evidence
Decision時点での顧客別・近未来の解約Risk
        ↓
Analysis Question
利用可能な情報から、所定期間内の解約をどの程度予測できるか
```

- Prediction Horizonや利用可能特徴量は、実際にDecisionを行う時点と整合させる必要がある。
- 解約Riskが高いことは、特定Retention施策の効果が大きいことを意味しない。

**Causalの例｜施策継続判断**

```text
Business Question
施策投資の効率を改善したい
        ↓
Decision
対象施策を継続・変更するか
        ↓
Required Evidence
施策によるOutcomeの増分変化と不確実性
        ↓
Analysis Question
対象Populationで、施策実施は非実施と比べOutcomeをどの程度変えるか
```

- 群間差や予測上の関連だけでは介入効果を表さないため、Causal Question / EstimandとIdentification Assumptionを別途検討する必要がある。

### 7.3.5. 「Decisionから逆算する」の意味と留保

- Decisionを先に考える目的は、分析結果の利用先を固定し、不要な分析や評価指標の最適化を避けることである。
- 一方で、最初に置いたDecisionを無条件に固定するという意味ではない。データ不足、識別不能、予測可能性不足、運用制約等が判明した場合は、Business Questionとの整合を保ちながらDecisionやScopeを再定義することがある。
- Predictiveでは、Decision時点で利用できない情報を特徴量に含めると実運用不能またはLeakageにつながる。
- Causalでは、Decisionに必要な効果が定義できても、その効果が利用可能データからIdentification可能とは限らない。
- したがって、Decisionは分析設計のアンカーだが、最終的なPoC設計はDecision・Data・Assumptions・Evaluationの整合で決まる。

## 7.4. Speaker Note

業務課題だけでは、分析仕様は決まりません。例えば「解約を減らしたい」という課題があっても、誰に優先対応するかを決めたいのか、Retention施策を継続するかを決めたいのかで、必要な分析は変わります。

そこでPoC設計では、まず「誰が何を決めるのか」を具体化します。次に、そのDecisionを改善するために何が分かればよいかを判断材料として定義し、最後にデータから答えられるAnalysis Questionへ落とします。

例えば、限られた対応Resourceをどの顧客へ配分するかを決めたいなら、Decision時点で利用できる情報から近未来の解約Riskを予測する問いが候補になります。一方、Retention施策を継続するかを決めたいなら、施策による解約率の増分変化を推定する因果の問いになります。

重要なのは、分析手法や手元のデータを先に置くのではなく、分析結果が使われるDecisionから必要なEvidenceを逆算することです。ただし、Decisionを決めれば分析仕様が自動的に決まるわけではありません。利用可能データや科学的な成立条件と照合し、必要に応じてScope自体を調整します。

## 7.5. Slide 7からSlide 8への接続

> **Decisionと必要なEvidenceを定義したら、次はその結果を「誰が・いつ使い・何を判断し・どのActionへつなげるか」を具体化する。**
