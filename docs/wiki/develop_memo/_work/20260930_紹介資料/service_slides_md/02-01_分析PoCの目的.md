# 5. Slide 5｜分析PoCの目的

## 5.1. Message

**PoCの目的はモデルや推定値を作ることではなく、業務上の意思決定に使える情報を再現可能な形で得られるかを検証することである。**

## 5.2. Chart

**チャートタイトル:** PoCの評価対象を「分析」から「意思決定」へ広げる

Messageを説明・論証するための主たる視覚表現として、以下の構造を採用する。

### 5.2.1. Chart Structure

- 既存の論理フロー／概念図を主チャートとして用い、要素間の関係・順序が一目で追える構造にする。

```text
従来の狭いPoC
データ → モデル / 推定 → 指標

本サービスのPoC
業務課題 → 意思決定 → 分析上の問い → データ → 分析
      → 妥当性確認 → 解釈 → Decision / Action
```

**PowerPoint上の配置・強調**

- 上段に狭いPoC、下段に本サービスのPoCを対比する。
- 下段を主役として、Business QuestionとDecisionを両端に配置する。
- 分析工程は中間手段として表現する。

### 5.2.2. Chart内の最小表示テキスト

実際のPowerPoint上では、以下のラベル・短文を中心に表示する。Supporting Logicの全文をスライド上へ掲載しない。

- 従来の狭いPoC
- データ → モデル / 推定 → 指標
- 本サービスのPoC
- 業務課題 → 意思決定 → 分析上の問い → データ → 分析
- 妥当性確認 → 解釈 → Decision / Action

## 5.3. Supporting Logic

- 分析精度が高くても、利用タイミング・責任者・Actionが定義されていなければ業務利用にはつながらない。
- 逆に、完全な自動化を目指さなくても、意思決定の質を高める判断材料として価値が成立する場合がある。
- PoCでは技術成立性と業務利用性を同時に確認し、本番化・追加検証・中止の判断材料を作る。
- 分析結果の再現性、前提、適用範囲、限界も成果物に含める。

- 補足論点：**PoC成功とは「良いモデルができた」ではなく、「次の業務判断を根拠を持って行える状態になった」ことである。**

## 5.4. Speaker Note

技術PoC化を防ぐための原則を説明する。PoC終了時のGo/No-Goが何に対する判断かを先に定義する。
