Document title: PoC開始条件と成功基準

# 10. Slide 10｜PoC開始条件と成功基準

## 10.1. Message

**PoCは成功基準を合意し、変更時は根拠を示して再合意する。**

## 10.2. Chart

**チャートタイトル:** 成功基準は合意して始め、変更時は理由と新基準を再合意する

Slide 9で示したPoC共通プロセスを、開始前の `Start Gate` と終了時の `Exit Gate` で挟む。Start Gateでは「何を検証し、結果をどう判断するか」を合意する。ただしPoCでは、Data Assessmentや業務検討を通じて契約前には分からなかった制約が判明し得るため、Success CriteriaやScopeを不変とは扱わない。変更が必要な場合は、変更理由・変更後のゴール / 基準・その妥当性をステークホルダーへ説明し、再合意したうえでPoCを継続する。Exit Gateでは、最終的に合意されている基準へEvidenceを照合してNext Phaseを判断する。

### 10.2.1. Chart Structure

PowerPoint上では、左に `START GATE`、中央にSlide 9で示したPoCの分析検証工程、右に `EXIT GATE` を置く横長の単一チャートとする。中央のPoC内に `CHANGE / RE-AGREEMENT` を配置し、成功基準が合理的な理由により更新され得ることを明示する。

**PowerPoint上の配置・強調**

- `START GATE → PoC → EXIT GATE` を主たる読み順とする。
- Start Gateは、Slide 7〜8で設計した `Question / Decision / 利用ルール` と、Slide 9の入口に置いた `Data` を、PoC開始前の合意事項として4つに束ねる。
- `Success Criteria` は契約前 / PoC開始前に合意するが、**PoC中に不変であることを前提としない**。
- 中央のPoCは、Slide 9の9工程を再掲せず、`Data Assessment → Analysis Design → Execution → Validation / Interpretation` の分析検証部分だけを圧縮表示する。
- PoC工程の下または中央下段に `CHANGE / RE-AGREEMENT` を置き、Data Assessmentや業務検討によって新しい事実・制約が判明した場合の変更管理を示す。
- `CHANGE / RE-AGREEMENT` では、最低限 `変更理由 → 変更後のゴール / Success Criteria → 妥当性 → Stakeholder再合意` の順を見せる。
- 変更理由の代表例として、想定以上の欠損・品質問題・観測粒度不足等のData制約、必要な業務知識・レビュー・現場協力を確保できない等のDelivery制約を示してよい。
- **結果が期待値に届かなかったこと自体を理由として、事後的に基準を緩める構造にはしない。** 新しい事実・制約が判明し、それにより当初ゴールの妥当性・実行可能性が変化したことを説明できる場合に変更候補とする。
- Exit Gateは、Slide 6で定義した `分析成立性 / 業務利用性 / 次フェーズ判断` の3観点へ揃え、**当初基準ではなく、変更履歴を含む最終合意済みSuccess Criteria**へEvidenceを照合する。
- `分析精度`、`統計的有意差`、`Effect Estimate` 等の単一指標をExit Gateの代表項目にしない。Predictive / Causalで評価内容が異なるため、主図では共通の判定観点に留める。
- `Next Phase` は二値のGo / No-Goだけにせず、`本番化 / 追加検証 / Data Acquisition / Scope変更 / 中止` を候補として示す。
- 数値Thresholdは案件固有であり、根拠なく固定値を置かない。業務要件、Baseline、科学的妥当性等から根拠を置ける場合に案件単位で設定し、変更する場合も同様に根拠を説明する。
- Start Gateの `Data` は「全てのデータ品質がPoC前に確認済み」という意味ではない。必要データの所在・利用可否・対象期間・主要な不足を初期確認し、詳細なData AssessmentはPoC工程内で行う。このため、PoC中に当初想定を覆すData品質上の問題が判明することは正常な検証結果として扱う。

## 10.3. Supporting Logic

### 10.3.1. Slide 10の役割

- Slide 6では、PoCで検証する対象を `分析成立性 / 業務利用性 / 次フェーズ判断` の3観点として定義した。
- Slide 7では、Business Questionから `Decision → Required Evidence → Analysis Question` を逆算する考え方を示した。
- Slide 8では、分析結果をDecision / Actionへ利用するために、`WHO / WHEN / Decision Rule / Action` という利用ルールを設計した。
- Slide 9では、これらを入口に置き、`業務設計 → 分析検証 → 業務接続` を一つのPoCとして進める共通プロセスを示した。
- **Slide 10では、ここまでの設計内容をPoC開始時の合意事項へ束ねるとともに、PoC中に新しい事実・制約が判明した場合のSuccess Criteria変更と再合意の原則を定義する。**
- したがって本スライドは、個別のPredictive / Causal評価指標を説明するスライドではなく、**開始前に判断軸を揃えつつ、検証で得られた新事実に応じて透明性を保って基準を更新するための共通ガバナンス**を示す役割を持つ。

### 10.3.2. Start Gate｜PoC開始前に合意する4項目

#### 10.3.2.1. ① Question / Scope

- Business Questionと、PoCでEvidenceを作るAnalysis Questionを明確にする。
- Slide 7で定義したDecision / Required Evidenceとの接続を確認し、「この分析結果が何の判断に必要なのか」を説明できる状態にする。
- 案件に応じてPopulation、Target / Outcome、Prediction Horizon、Treatment / Comparison、対象期間等を具体化する。
- ただし、PoC開始前に科学的成立条件がすべて証明済みである必要はない。PoCで検証すべき不確実性と、既に判明している制約を区別する。

#### 10.3.2.2. ② Decision / Action

- 分析結果を誰が、いつ、どのDecisionに利用し、どのActionを変える想定かを確認する。
- `WHO / WHEN / Decision Rule / Action` は本番運用仕様を先に固定するためではなく、**業務利用性をPoCで検証可能にする仮説**として置く。
- Decision / Actionが特定できない場合、分析結果が業務上どの価値へ接続するかを評価できないため、PoC Scopeを再検討する必要がある。

#### 10.3.2.3. ③ Data

- 必要なデータソースの所在、アクセス可能性、対象期間、観測粒度、主要変数等を初期確認する。
- Predictiveでは、Decision時点で利用できる情報とTargetを構成できる見込みがあるかを確認する。
- Causalでは、Treatment / Outcome / Populationに関するデータと、候補となる比較設計を検討できる情報が存在するかを確認する。
- Start Gateで行うのは**初期的なData Feasibility確認**であり、欠損、Leakage、Selection、データ生成過程、Overlap等を含む詳細評価はPoC内のData Assessment / Analysis Designで扱う。
- したがって、PoC開始後に「想定より欠損が多い」「必要な時点情報がない」「ラベル定義が業務上の意味と一致しない」等が判明し、当初ScopeやSuccess Criteriaの見直しが必要になることはあり得る。
- データ利用可否自体が不明、または重大な不足が既知である場合は、PoCをそのまま開始するのではなく、Data Acquisition、事前調査、Scope変更等を先行させることがある。

#### 10.3.2.4. ④ Success Criteria

- Success Criteriaは「高い精度が出る」「有意な効果が出る」ことを約束する目標値ではない。
- **PoCで得たEvidenceを見たときに、分析が成立したか、業務判断へ使えるか、次に何をすべきかを判断するための基準**として定義する。
- 少なくとも以下の3観点を案件に応じて具体化する。
  1. **分析成立性**：対象Questionへ妥当に答えられるか。評価方法、Baseline、前提、再現性、不確実性、限界等をどのように確認するか。
  2. **業務利用性**：結果を想定Decision / Actionの判断材料として利用できるか。利用時点、解釈可能性、業務制約、誤判定Cost、対応可能件数等と整合するか。
  3. **次フェーズ判断**：どのEvidenceなら本番化、追加検証、追加データ取得、Scope変更、中止等を選ぶか。
- 数値Thresholdを置く場合は、既存業務のBaseline、最低限必要な業務水準、統計・科学上の根拠等から設定する。根拠のないAccuracy、改善率、ROI等を資料側で補完しない。
- すべての基準を完全な数値へ落とせるとは限らない。定性的条件や未確定事項が残る場合は、その項目とExit時の判断方法を明示しておく。
- **ここでの「合意」は固定を意味しない。PoCは未知事項を明らかにする活動であるため、契約前 / 開始前には把握できなかった事実により、Success Criteria自体を変更する必要が生じ得る。**

### 10.3.3. Success Criteria変更の原則｜変更可能だが、黙って書き換えない

- PoCでは、実データを詳細に確認した結果、想定以上にデータが汚い、必要な変数・期間・粒度が不足している、データ生成過程が当初理解と異なる等が判明することがある。
- また、分析成立性とは別に、必要な業務知識を持つ担当者のレビュー時間を確保できない、現場部門から必要な協力を得られない、対象業務や施策の運用条件が変更される等、Delivery / Business側の制約がPoC中に判明・変化することもある。
- こうした新事実により、契約前 / PoC開始前に合意したゴール・Scope・Success Criteriaが非現実的、評価不能、またはBusiness Questionとの整合を失う場合は、変更を許容する。
- ただし変更は分析チームの裁量だけで完結させない。少なくとも以下を明示する。
  1. **変更理由**：何が新たに判明・変化し、なぜ当初基準を維持できない / 維持すべきでないのか。
  2. **変更後のゴール / Success Criteria**：何を新たな検証対象・判断基準とするのか。
  3. **妥当性**：変更後の基準がBusiness Question、Decision / Action、利用可能Data、残り期間・体制等に照らしてなぜ合理的なのか。
  4. **Stakeholder再合意**：顧客側・実施側の関係者へ説明し、変更後のゴールと判断基準について再度合意する。
- 変更前のゴール / Success Criteria、変更理由、変更後の内容、合意時点を追跡可能な形で保持し、Exit Gateでは**最新の合意だけでなく、そこへ至った変更履歴も含めて結果を解釈できる状態**にする。
- この変更管理は、PoCを硬直化させるためではなく、未知事項への適応と評価の公正性を両立するために行う。

### 10.3.4. 合理的な変更と「ゴールポストを動かすこと」を区別する

- Success Criteriaが変更可能であることは、期待した結果が出なかった後に「成功」に見えるよう基準を緩めてよいという意味ではない。
- 例えば、当初合意した評価方法で性能が不足したという結果だけを理由に、より良く見える別MetricやSegmentへ無説明で切り替えることは避ける。
- 一方、Data AssessmentによりTarget定義自体が成立しない、業務制約により想定Actionが実行不能になった、必要なStakeholder協力を得られず当初の検証方法が実施不能になった等、**当初基準の前提条件が変化・否定された場合**は見直す合理性がある。
- 判断のポイントは、「結果が悪かったから変える」のか、「当初基準を成立させていた前提が新しいEvidenceによって変わったから変える」のかを区別できることである。
- 変更後は、変更前の基準で何が分かったかも可能な範囲で残し、新基準だけを遡及的に当初基準であったかのように扱わない。

### 10.3.5. 「PoC成功」と「期待した分析結果」を分ける

- PoCは不確実性を減らし、次の意思決定に必要なEvidenceを得るための検証である。
- したがって、期待した高性能モデルや正のTreatment Effectが得られなかったことだけで、PoCそのものを失敗とは定義しない。
- 例えばPredictiveで十分なOut-of-sample性能が得られず、その原因と追加データの必要性が明確になれば、`Data Acquisition` や `No-Go` を合理的に判断するEvidenceになる。
- CausalでEffectが小さい、推定不確実性が大きい、Identification上の懸念が残る等の場合も、その結果から施策を見送る、追加実験を行う、別Designへ変更するという判断が可能になる。
- 逆に、見かけ上高い精度や統計的有意差が得られても、Leakage、再現性不足、Identification Assumptionへの重大な懸念、業務利用条件との不整合等があれば、Goの根拠にはならない。
- **PoCの成功は「望ましい数字が出たこと」ではなく、合意された問いに対して、次の判断に使えるEvidenceと限界が得られたかで評価する。**
- Success Criteriaが途中変更された場合は、変更理由と再合意内容を含めて評価し、「最終基準だけを見れば成功」という説明にはしない。

### 10.3.6. Exit Gate｜3観点でEvidenceを判定する

#### 10.3.6.1. ① 分析成立性

- 最終的に合意されたAnalysis Questionに対して、妥当な方法でEvidenceを得られたかを確認する。
- Predictiveでは、適切に分離された未知データでの性能、Calibration、Error Pattern等を案件に応じて確認する。
- Causalでは、対象Estimandに対するIdentification Assumption、推定不確実性、Diagnostics / Sensitivity等を案件に応じて確認する。
- 結果そのものだけでなく、成立した条件、成立しなかった条件、適用範囲、残る不確実性を明示する。
- Scope / Success Criteriaを途中変更した場合は、その変更によって何が評価対象外になったかも明示する。

#### 10.3.6.2. ② 業務利用性

- 得られたEvidenceが、最終合意したDecision / Actionの判断材料として使えるかを確認する。
- `WHO / WHEN / Decision Rule / Action` と照合し、結果提供時点、業務上必要な粒度、誤判定・不確実性、対応Capacity等との整合を評価する。
- Offline分析で確認できたことと、実際に業務Actionを変更して初めて確認できることを区別する。
- 分析結果が業務利用可能であることと、売上向上・Cost削減等のBusiness Outcomeが実現済みであることを同一視しない。
- 業務側の協力・体制不足が原因で利用性検証を十分に実施できなかった場合は、それ自体を制約・残存リスクとしてExit時に明示する。

#### 10.3.6.3. ③ Next Phase

- 分析成立性と業務利用性のEvidenceをもとに、次に取るActionを判断する。
- 代表的な選択肢は以下とする。
  - **本番化 / Go**：対象条件で業務利用を進める根拠が十分に得られた。
  - **Additional Validation**：追加期間、別Segment、実運用Pilot、追加Diagnostics等による検証が必要である。
  - **Data Acquisition**：判断に必要なデータ不足が主要なボトルネックである。
  - **Scope Change**：Question、Population、Outcome、Treatment、Decision等の再定義が合理的である。
  - **No-Go / Stop**：現条件では期待するDecisionへ接続する根拠が不足し、追加投資の合理性も低い。
- Go / No-Goは二値の最終評価ラベルではなく、**PoC Evidenceから次の投資・検証Actionを選ぶための意思決定**として扱う。

### 10.3.7. Success Criteriaを開始前に合意する理由

- Success Criteriaが変更され得るとしても、開始前に基準を持たないこととは異なる。
- 初期基準がなければ、何を検証しているのか、どの新事実が当初前提を覆したのか、なぜ変更が必要なのかを説明できない。
- 主要なQuestion、評価方法、Baseline、判断条件を開始前に合意することで、PoC中に起きた学習と、単なる事後的な基準変更を区別できる。
- Data Assessmentや業務制約の把握により当初想定が成立しないと分かった場合は、Question、Scope、評価方法、Success Criteria等を見直す。
- その際は、**何を、なぜ、どのEvidenceを根拠に変更するのか、変更後のゴールがなぜ妥当なのか**を説明し、Stakeholderと再合意する。
- したがって原則は「Success Criteriaを固定する」ではなく、**「初期基準を明示し、変更を透明かつ合意可能な形で管理する」**ことである。

### 10.3.8. Predictive / CausalでSuccess Criteriaの中身は異なる

- Start Gate / Exit Gate / Re-agreementという管理構造はPredictive / Causalに共通するが、分析成立性を評価する意味論は同一ではない。
- Predictiveでは、未知データでの汎化性能を中心に、案件に応じてBaseline、Calibration、Precision / Recall、Error Pattern、業務Cost等を組み合わせる。
- Causalでは、Causal Question / Estimand、Identification Strategy、Assumptions、Estimation、Uncertainty、Diagnostics / Sensitivity等の整合を確認する。
- Feature importanceやSHAP等のPredictive ExplanationをCausal EffectのSuccess Criteriaとして扱わない。
- Causalでは統計的有意差の有無だけを施策判断基準にせず、Effect Size、不確実性、Identification上の妥当性、業務上意味のある差、施策Cost等をDecisionと整合させる。
- これらの具体的な分析プロセス・評価方法は後続のPredictive / Causal各章で説明する。

### 10.3.9. 後段Slide 31との役割分担

- 本スライドは、**PoCの論理上のStart Gate / Exit Gate、Success Criteriaの考え方、およびPoC中の変更・再合意原則**を定義する。
- 後段の「PoC開始までの進め方」では、顧客ヒアリング、データ初期確認、分析可能性確認、Scope / Success Criteria合意等、実際にPoC開始へ至る対外的な進め方を示す。
- したがって本スライドでは、商談・契約・体制・日程等の開始手続きを主題にせず、「何が揃えば検証を開始でき、途中で前提が変わった場合にどう合意を更新し、何をもって次の判断を行うか」に集中する。

## 10.4. Speaker Note

前のスライドでは、業務上の問いから分析を実行し、結果をDecision / Actionへ戻すまでを一つのPoCとして示しました。このプロセスをぶれずに進めるために、開始前にゴールとSuccess Criteriaを合意します。

ただし、ここで重要なのは、このSuccess Criteriaを固定されたゴールとして扱わないことです。PoCはそもそも、契約前には分からない不確実性を明らかにするための活動です。実際にデータを見ると想定以上に欠損が多い、必要な粒度や期間がない、業務上の定義とデータのラベルが合わない、といったことが分かる場合があります。また、必要な業務知識を持つ方のレビュー時間が取れない、現場部門の協力が得られない、といった業務側・体制側の制約が途中で判明することもあります。

そうした新しい事実によって、契約前に合意したゴールやSuccess Criteriaを維持することが合理的でなくなった場合は、変更します。ただし、分析チームだけで黙って変更するわけではありません。なぜ変更が必要なのか、変更後は何をゴール・Success Criteriaとするのか、それがBusiness Questionや利用可能なデータ、残り期間や体制に照らしてなぜ妥当なのかをステークホルダーへ説明し、再度合意したうえで進めます。

これは、結果が悪かったから後から基準を下げるという意味ではありません。重要なのは、当初の基準を成立させていた前提が、PoCで得た新しいEvidenceによって変化したかどうかです。変更前の基準、変更理由、変更後の基準、再合意した時点は記録として残します。

Start Gateでは、大きく4点を確認します。何のBusiness Questionに対して何を分析するのか、その結果を誰がいつどの判断やActionに使うのか、必要なデータを利用できる見込みがあるか、そして得られた結果を何によって評価し次に何を判断するのか、というSuccess Criteriaです。

Exit Gateでは、契約時の基準を機械的に使うのではなく、変更があった場合は最終的に再合意された基準へEvidenceを照合します。同時に、なぜ基準が変わったのか、何が検証できずに残ったのかも含めて、本番化、追加検証、追加データ取得、Scope変更、中止等を判断します。

PredictiveとCausalでは、この分析成立性の見方が異なります。ここまでは両者に共通するPoC設計を整理したので、ここからはまずPredictiveについて、何を予測し、その結果をどのような判断に使うのかを具体化します。
