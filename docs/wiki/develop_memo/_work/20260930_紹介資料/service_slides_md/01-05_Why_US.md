## 5.3. Supporting Logic

### 5.3.1. Business-first

- 分析手法やアルゴリズムを起点にせず、まずBusiness QuestionとDecision / Actionを明確にし、その判断に必要なAnalysis Questionへ落とし込む。
- Predictive / Causalの選択も、利用したい技術ではなく「何を知り、何を決めたいか」という問いから決める。
- この設計により、分析結果は得られたが利用先がない、というPoCを避ける。

### 5.3.2. Scientific rigor

- Predictiveでは、未知データに対する予測性能を中心に、必要に応じてCalibration、Error Pattern、業務コスト等まで確認する。
- Causalでは、Effect Estimateだけでなく、Causal Question / Estimand、Assumptions、Identification、Estimation、Diagnostics / Sensitivityを必要に応じて区別して検討する。
- 予測上のExplainabilityを因果効果として解釈しない等、問いに対して主張可能な範囲を明示する。
- PoC成功を「モデルが作れた」「有意差が出た」とは定義せず、業務上の判断可能性と科学的妥当性を合わせて評価する。

### 5.3.3. Flexible implementation

- 分析実装はデータサイエンティストによるスクラッチ開発を基本とし、成熟したOSSや既存ライブラリを必要に応じて組み合わせる。
- 特定製品や単一アルゴリズムへ案件を合わせるのではなく、問い、データ特性、必要性能、説明性、運用制約等に応じて手法を選択する。
- Ariadneはサービス提供の必須前提ではなく、Research Context、分析条件、実行、結果、判断理由、Lineage等の構造化・追跡を補助する選択肢として利用する。

### 5.3.4. 顧客にとっての価値

- 当チームの差別化は、独自アルゴリズムの数そのものではなく、Business Questionから分析設計、妥当性確認、実装、結果解釈までを一貫して接続することにある。
- その結果として目指すのは、「分析を実施した」という状態ではなく、PoC結果を用いて次のDecision / Actionを判断できる状態である。
- 本スライドでは、他社比較、精度優位、価格優位、短納期、導入実績等、現時点で根拠資料がない競争優位は主張しない。

## 5.4. Speaker Note

このスライドでは、なぜ当チームにPoCを依頼するのかを説明する。

第一に、分析手法から入らず、顧客が最終的に何を判断する必要があるのかから逆算する。例えば「機械学習を使いたい」ではなく、「誰に対応するかを決めたい」「施策を継続するかを決めたい」といったDecision / Actionを起点として、必要な分析上の問いを設計する。

第二に、その問いに対して主張するために必要な科学的妥当性を確認する。予測分析と因果推論では必要な評価や前提が異なるため、同じ評価軸で扱わない。特に因果推論では、推定器を選ぶ前にIdentificationに必要な前提を整理し、どこまで主張できるかを明示する。

第三に、実装を特定ツールへ固定しない。案件に応じてスクラッチ開発と成熟OSSを組み合わせ、必要な場合にはAriadneを用いて分析条件や判断理由の追跡可能性を補助する。

この3点はそれぞれ独立した売り文句ではなく、「判断に使えるPoC結果」を得るための一連の設計力として捉える。
