# 5. Slide 5｜Why US

## 5.1. Message

**問い・妥当性・実装を一貫設計し、意思決定に耐えるPoCをつくる。**

## 5.3. Supporting Logic

### 5.3.1. Slide 5の役割

- Slide 1〜4では、当チームがPredictive / CausalのPoCを提供し、問いに応じて分析を使い分け、その結果をBusiness OutcomeにつながるActionへ利用することを示した。
- Slide 5では、その価値を実現するために「なぜ当チームへ依頼するのか」を示す。
- 後続のSlide 6〜10ではPoCの目的、業務課題からDecision / Actionへの接続、全体プロセス、開始条件・成功基準を詳述するため、本スライドではプロセス自体を先取りしすぎない。
- 差別化の中心は、個別アルゴリズムやツールの保有数ではなく、**問い・科学的妥当性・実装を一つのPoCとして整合させる設計力**に置く。

### 5.3.2. ① 問いの設計｜分析結果ではなくDecision / Actionから逆算する

- 分析手法やアルゴリズムを起点にせず、まずBusiness QuestionとDecision / Actionを明確にし、その判断に必要なAnalysis Questionへ落とし込む。
- Predictive / Causalの選択も、利用したい技術ではなく「何を知り、何を決めたいか」から決める。
- これにより、モデルや推定値は得られたが「誰が、いつ、何の判断に使うのか」が決まっていないPoCを避ける。
- 顧客にとっての価値は、PoC終了時に単なる分析結果ではなく、**その結果を使って何を判断できるか**が明確になることである。

### 5.3.3. ② 妥当性の設計｜問いに対して主張できる範囲を明確にする

- PredictiveとCausalでは、推論対象、必要な前提、評価基準が異なるため、それぞれに適した検証設計を行う。
- Predictiveでは、未知データに対する予測性能を中心に、必要に応じてCalibration、Error Pattern、segment別性能、業務上の誤判定コスト等を確認する。
- Causalでは、Effect Estimateだけでなく、Causal Question / Estimand、Assumptions、Identification、Estimation、Diagnostics / Sensitivityを必要に応じて区別して検討する。
- Feature ImportanceやSHAP等のPredictive Explainabilityを因果効果として解釈しないなど、分析結果から主張可能な範囲を明示する。
- PoC成功を「モデルが作れた」「精度が高かった」「有意差が出た」だけでは定義せず、**その問いへの答えとして妥当か**を評価する。

### 5.3.4. ③ 実装の設計｜案件を特定ツールへ合わせない

- 分析実装はデータサイエンティストによるスクラッチ開発を基本とし、成熟したOSSや既存ライブラリを必要に応じて組み合わせる。
- 特定製品や単一アルゴリズムへ案件を合わせるのではなく、問い、データ特性、必要性能、説明性、検証条件、運用制約等に応じて手法と実装方式を選択する。
- この方針により、既製ツールの対応範囲だけで問いを狭めるのではなく、PoCで確認すべき仮説・前提・評価に合わせて必要な分析を構成できる。
- Ariadneはサービス提供の必須前提ではない。必要に応じてResearch Context、分析条件、実行、結果、判断理由、Lineage等を構造化し、追跡可能性・再現性を補助する選択肢として利用する。

### 5.3.5. 3つを一貫して設計する意味

- Business Questionだけを明確にしても、分析の前提や評価が不適切であれば判断材料として信頼できない。
- Scientific Validityだけを追求しても、結果の利用先となるDecision / Actionが定義されていなければ業務価値へ接続しない。
- 高度な実装能力があっても、問いや妥当性と整合しなければ、複雑なモデルを作ること自体が目的化する。
- したがって当チームの価値は3要素の個別保有ではなく、**Business Question → Analysis Question → Validation → Implementation → Interpretationを分断せず整合させること**にある。
- その結果として目指すのは、「分析を実施した」という状態ではなく、PoC結果とその前提を踏まえて次のDecision / Actionを判断できる状態である。

### 5.3.6. 主張範囲

- 本スライドでは、他社比較による優位性、特定の精度優位、価格優位、短納期、導入実績等、現時点で根拠資料がない競争優位は主張しない。
- 「意思決定に耐えるPoC」は、業務上の判断に利用するための問い・前提・評価・結果解釈が整理されている状態を意味し、将来のBusiness Outcomeや意思決定の成功を保証する表現ではない。

## 5.4. Speaker Note

Slide 4では、予測や因果の分析結果を実際のActionへつなげることで、収益向上、コスト削減、ROI改善等のBusiness Outcomeにつながり得ることを示しました。

ただし、その価値は分析手法を適用するだけで自動的に生まれるものではありません。当チームが重視しているのは、PoCを「分析できた」で終わらせず、実際の判断に使える状態まで設計することです。

そのために、3つを一貫して設計します。

一つ目は問いです。最初にモデルやアルゴリズムを選ぶのではなく、顧客が最終的に何を判断する必要があるのかから逆算して、必要なAnalysis Questionを定義します。これにより、分析結果は出たものの使い道が決まっていない、という状態を避けます。

二つ目は妥当性です。PredictiveとCausalでは、必要な前提も評価方法も異なります。予測であれば未知データでどこまで再現するか、因果であればどの前提のもとで介入効果として解釈できるかを整理し、結果からどこまで主張できるかを明確にします。

三つ目は実装です。特定の製品やアルゴリズムに課題を合わせるのではなく、案件の問い、データ、検証条件に応じて、スクラッチ開発と成熟したOSS等を組み合わせます。必要な場合にはAriadneを用いて、分析条件や結果、判断理由の追跡可能性を補助します。

重要なのは、この3つを別々の強みとして持つことではありません。問い、妥当性、実装を一つのPoCとして整合させることで、PoC終了時に「何が分かったか」だけでなく、「その結果を前提込みで何の判断に使えるか」を明確にすることが、当チームの提供価値です。
