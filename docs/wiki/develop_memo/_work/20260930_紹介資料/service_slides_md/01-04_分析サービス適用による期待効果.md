## 4.3. Supporting Logic

### 4.3.1. Slide 4の役割

- Slide 1ではPredictive / Causalがそれぞれ「将来の見通し」「施策の効果」という判断材料を提供することを示した。
- Slide 2では、業務課題を「何を知りたいか」へ落とし込み、その問いによってPredictive / Causalを選ぶことを示した。
- Slide 3では、両者は推論対象・成立条件・評価基準まで異なることを示した。
- Slide 4では、その違いを再説明するのではなく、**分析結果を業務Actionへ利用することで、どのような具体的Business Outcomeにつながり得るか**を示す。
- Open Data / Competition / Enterprise Caseを再調査した結果、適用対象はCustomer、Industrial、Operations等に広く存在するため、本スライドでは特定Domainを単一主例としない。

### 4.3.2. PredictiveからBusiness Outcomeへの接続

Predictiveの価値は、予測精度そのものではなく、予測を利用して結果発生前にActionを変えることにある。

**Customer**

```text
解約Risk予測
→ 高Risk顧客を把握
→ 対応対象を優先
→ 限られた対応Resourceを重点配分
→ 対応効率 / 継続機会の改善
```

- completejourney、Bank Marketing、各種Churn Competition等からCustomer Behavior Predictionの適用範囲を確認できる。
- ただし解約Riskが高いことはRetention施策のTreatment Effectが大きいことを意味しない。

**Industrial / Quality**

```text
不良Risk予測
→ High-risk製品 / Lotを把握
→ 重点検査
→ 検査Resourceを重点配分
→ 不良流出 / 検査Costの削減、品質改善
```

- SECOM、Steel Plates Faults等のOpen Dataが存在する。
- 設備停止 / RULも同じPredictive Value Chainの一例であり、AI4I、NASA C-MAPSS、IMS Bearings等で検証可能なProblemである。

**Operations / Logistics**

```text
配送遅延Risk予測
→ High-risk shipmentを把握
→ 優先Follow-up / Escalation
→ 遅延対応を前倒し
→ 遅延損失 / 対応工数の削減
```

- Olist、DataCo、E-Commerce Shipping等から配送遅延Prediction Problemを構成できる。
- BPI Challenge 2019ではLead Time、Completion Time、Next Activity、Process Deviation等、企業内部Process自体もPrediction Targetとなる。

したがってPredictiveの適用例は、設備保全に限定せず、**Customer / Quality / Operationsで「将来を見通して先にActionを変える」**という共通構造で整理できる。

### 4.3.3. CausalからBusiness Outcomeへの接続

Causalの価値は、Effect Estimateそのものではなく、施策・介入によるOutcome変化を判断材料としてActionを変えることにある。

**Customer / Marketing**

```text
Retention施策の効果推定
→ 施策実施 / 継続を判断
→ 有効施策へResourceを配分
→ 施策費 / 継続率 / Incremental Revenueの改善
```

- Criteo Uplift Datasetのように、Randomized incrementality test由来のTreatment / Conversion Dataを用いたUplift / HTE Benchmarkが存在する。
- 対象別Targetingを行う場合は、平均効果だけでなくCATE / HTE等の対象別効果を妥当に推定・検証する必要がある。

**Industrial / Quality**

```text
工程条件変更の効果推定
→ Process変更を判断
→ 有効な工程条件へ変更
→ 不良率 / Quality Costの改善
```

- Predictiveで「どの製品が不良になりそうか」を当てることとは別に、「工程条件を変更した場合に不良率がどう変わるか」というCausal Questionを定義できる。
- Open Dataに工程条件やExposureが存在しても、それだけで効果がIdentification可能とは限らない。

**Operations / Process**

```text
業務Process変更の効果推定
→ Rule / Process変更を判断
→ 有効な変更を実施
→ Lead Time / Cost / Service Qualityの改善
```

- UberはProduct Feature、Marketing Campaign、Promotion等の実験に加え、Delivery Delayが将来Engagementへ与える影響のようなObservational Causal Inferenceの利用例を公開している。
- Difference-in-Differences、Synthetic Control等は、RandomizationできないPolicy / Process Changeで候補となり得るが、適用可能性はDesignとAssumptionに依存する。

### 4.3.4. Predictive / Causalの適用対象を対称に見る

Open Data / Competition / Enterprise Caseを横断すると、次のような対称例が成立する。

|業務課題|Predictive Question|Causal Question|
|---|---|---|
|解約を減らしたい|誰が解約しそうか？|Retention施策で解約はどれだけ減るか？|
|配送品質を改善したい|どの配送が遅れそうか？|Process変更で遅延はどれだけ減るか？|
|不良を減らしたい|どの製品が不良になりそうか？|工程条件を変えると不良率はどう変わるか？|
|設備停止を減らしたい|どの設備が停止しそうか？|保守施策で停止率はどれだけ下がるか？|

- この整理により、故障予測はIndustrial Domainの有力例の一つであるが、Predictive Service全体の唯一の代表例ではないことが明確になる。
- また、CausalもMarketing施策だけではなく、Product、Quality、Operations等のInterventionへ広がる。

### 4.3.5. 期待効果は分析結果から直接発生しない

- 予測精度が高いだけではBusiness Outcomeは改善しない。Predictionを誰がどのDecision Ruleで利用するかを設計する必要がある。
- 因果効果を推定しただけでもROIや品質は改善しない。Estimateを施策選択、Process変更、Resource配分等へ反映する必要がある。
- Actionを変更した場合でも、市場環境、業務制約、運用定着、実装品質等によってOutcomeは変わる。
- したがって本資料ではBusiness Outcomeを**期待効果の種類**として示し、案件固有の検証なしに効果量を保証しない。

### 4.3.6. Why Usへの接続

- このようなBusiness Outcomeへつなげるには、単にModelやEffect Estimateを作るだけでは不十分である。
- まず業務課題をPredictive / Causalの適切なQuestionへ落とし込み、利用可能Data、Prediction Horizon、Treatment、Outcome、Decision / Actionを定義する必要がある。
- Predictiveでは、実運用時点で利用できる情報からどのOutcomeを予測し、その結果を誰がどのActionへ使うかまで設計する。
- Causalでは、Causal Question / Estimand、Identification Assumption、推定、Diagnostics / Sensitivityを整合させ、そのEffect Estimateをどの施策判断へ利用するかを設計する。
- 次の01-05では、この「業務課題から分析設計・Action接続まで」を当チームがどのように支援するかを説明する。

## 4.4. Speaker Note

PredictiveとCausalは、分析結果そのものではなく、その結果を使って業務Actionを変えることで価値につながります。

Predictiveの場合、設備停止だけが代表例ではありません。例えば解約Riskを予測できれば、限られた対応Resourceをどの顧客へ優先配分するかを変えられます。不良Riskを予測できれば重点検査へつなげられます。配送遅延Riskを予測できれば、遅れそうなShipmentを先にFollow-upできます。

共通しているのは、将来起こりそうなことを先に見通して、対象・時期・対応を変えるという点です。その結果として、対応効率、品質、Cost、Lead Time等の改善につながる可能性があります。

Causalでは、施策やProcess変更の効果を推定し、その情報を施策実施や継続、Process変更、投資配分の判断へ利用します。例えばRetention施策の効果、工程条件変更の不良率への効果、業務Process変更のLead Timeへの効果などが対象になります。

ただし、分析結果が出たこと自体をBusiness Outcomeとは呼びません。予測結果やEffect Estimateを実際の業務判断へ組み込み、Actionが変わって初めて価値につながります。また、対象別施策効果を使ったTargetingを行う場合は、平均効果だけではなく対象別の効果差を妥当に評価する必要があります。

このように、Customer、Industrial、OperationsのいずれでもPredictive / Causalの適用先はあります。重要なのは、手法を先に選ぶのではなく、業務課題から何を知り、どのActionを変えたいかを定義することです。
