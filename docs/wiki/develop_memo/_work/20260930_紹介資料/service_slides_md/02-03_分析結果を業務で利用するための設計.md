# 8. Slide 8｜分析結果を業務で利用するための設計

## 8.1. Message

**分析結果を業務で使うには、利用ルールをPoC段階で設計する。**

## 8.2. Chart

**チャートタイトル:** 分析結果をDecision / Actionへ変換する利用ルール

Slide 7で定義したDecisionを実際の業務で実行可能にするために、**誰が・いつ分析結果を利用し、どの判断基準でActionへつなげるか**を一つの利用ルールとして示す。

### 8.2.1. Chart Structure

PowerPoint上では、上段に利用コンテキストとして `WHO / WHEN`、下段に `Analysis Result → Decision Rule → Action` の横フローを置く、上下2段の単一チャートとする。

```text
│ Prediction / Effect│   │ 基準・不確実性・制約   │   │ 対象 / 施策 / 配分 │

```

**PowerPoint上の配置・強調**

- 主たる読み順は `WHO / WHEN → Analysis Result → Decision Rule → Action` とする。
- `Decision Rule` を視覚上のアンカーとして最も強く表示し、分析結果が自動的にActionを決めるのではなく、明示した判断基準を介して業務判断へ変換されることを示す。
- `WHO / WHEN` は、結果を利用する担当・意思決定者と、結果が利用可能でなければならない時点を定義する利用コンテキストとして上段に置く。
- `Analysis Result` は、PredictiveではPrediction / Risk / Forecast等、CausalではEffect Estimateとその不確実性等を想定する。ただし分析固有の詳細は主図へ載せない。
- `Decision Rule` の「基準・不確実性・制約」は、案件に応じてThreshold、比較基準、業務コスト、対応可能件数、Effectの不確実性等を考慮することを示す。単一の固定ルールを一般化しない。
- `Action` は、結果を受けて実際に変更可能な対象・施策・Resource配分等とする。
- Slide 7で定義済みのDecisionは、新しい独立ボックスとして再定義せず、Decision RuleがどのDecisionのためのルールかを示す注記として置く。
- Dashboard、API、Batch、画面UI等のIT実装方式は本スライドの主題ではないため、主図へ入れない。
- 最下段に「分析結果を『見る』だけでなく、判断とActionのルールまでPoCで設計」を補助メッセージとして配置する。

## 8.3. Supporting Logic

### 8.3.1. Slide 8の役割

- Slide 6では、PoCで分析成立性だけでなく、分析結果をDecision / Actionの判断材料として利用できるかまで検証することを示した。
- Slide 7では、業務課題から `Decision → Required Evidence → Analysis Question` を逆算し、何の判断に必要な分析かを定義した。
- Slide 8では、そのDecisionを実際の業務で運用可能にするために、**分析結果を誰が・いつ利用し、どのルールでActionへ変換するか**を設計する。
- Slide 9では、ここまで定義した業務課題・Decision・利用ルールを含め、PoC全体をどの工程で進めるかを示す。
- したがって本スライドは、分析手法やPoC工程を説明するのではなく、**分析結果の利用仕様を定義すること**に集中する。

### 8.3.2. 利用ルールを構成する要素

1. **WHO｜誰が使うか**
   - 分析結果を確認し、判断またはActionを実行する主体を特定する。
   - 意思決定者、分析利用者、運用担当者が同一とは限らないため、必要に応じて役割を分ける。
2. **WHEN｜いつ使うか**
   - 日次・週次・案件発生時・施策実施前等、Decisionに間に合う利用時点を定義する。
   - PredictiveではPrediction Horizonと結果提供時点が、Actionを実行できるLead Timeと整合する必要がある。
   - Causalでは、施策開始・継続・変更等のDecision時点までに、対象期間のデータと妥当な分析結果が得られる必要がある。
3. **Analysis Result｜何を判断材料にするか**
   - Predictiveでは予測値、Risk、Forecast、Calibration等が判断材料になり得る。
   - Causalでは、対象Estimandに対応したEffect Estimate、不確実性、Diagnostics / Sensitivity等を判断材料として扱う。
   - 何を表示するかではなく、対象Decisionに必要なEvidenceとして何を利用するかを定義する。
4. **Decision Rule｜どう判断するか**
   - 分析結果を、実際のDecisionへ変換する基準を定義する。
   - Threshold、順位、比較基準、業務コスト、対応可能件数、Minimum Practically Relevant Effect、不確実性等は案件に応じた候補であり、一律のルールではない。
   - 判断基準は、分析指標だけでなく実際の業務制約と整合させる。
5. **Action｜何を変えるか**
   - 判断結果を受け、対象選択、優先順位、施策実施・継続・変更、Resource配分、追加Review等、実際に変更可能な行動へ接続する。
   - Actionが定義できない場合、分析結果が業務上の価値へ接続する経路も定義できない。

### 8.3.3. Predictiveでの利用設計例

```text
Decision
限られた対応Resourceを、どの顧客へ優先配分するか
        ↓
WHO / WHEN
担当者が、対応計画を確定する前に利用
        ↓
Analysis Result
所定期間内の顧客別Churn Risk
        ↓
Decision Rule
Riskだけでなく対応可能件数・誤判定コスト等を踏まえて対象を選ぶ
        ↓
Action
優先対象へFollow-up Resourceを配分
```

- Classificationであっても、予測確率0.5を機械的に業務Thresholdとする根拠はない。
- 実際のDecision Ruleは、Calibration、False Positive / False Negativeのコスト、対応可能件数、対象ごとの価値等によって変わり得る。
- 高Riskであることは、特定施策による改善効果が大きいことを意味しない。施策効果によるTargetingが必要な場合はCausal Questionとして別途扱う。

### 8.3.4. Causalでの利用設計例

```text
Decision
対象施策を継続・変更するか
        ↓
WHO / WHEN
施策責任者が、次期施策の確定前に利用
        ↓
Analysis Result
対象Estimandに対応したEffect Estimateと不確実性
        ↓
Decision Rule
効果量・不確実性・施策Cost・業務上意味のある差を踏まえて判断
        ↓
Action
継続 / 変更 / 追加検証 / 中止
```

- `p < 0.05` や統計的有意差の有無だけで、施策のBusiness Valueや実施可否が自動的に決まるわけではない。
- 効果量の大きさ、推定不確実性、Identification Assumption、施策Cost、実装制約等をDecisionと整合させる必要がある。
- IdentificationやDiagnostics / Sensitivityに重大な懸念が残る場合は、「効果がない」と断定するのではなく、追加データ・追加検証・別Design等をAction候補とすることがある。

### 8.3.5. PoCで何を検証するか

- 利用ルールをPoC段階で定義する目的は、本番運用仕様を先に固定することではなく、**分析結果が業務判断に使える条件を検証可能にすること**である。
- PoCでは、少なくとも以下を案件に応じて確認する。
  - Decision時点までに必要なデータ・分析結果を用意できるか。
  - 分析結果を業務上解釈可能な形式で提示できるか。
  - 想定したDecision Ruleが、予測性能・Effectの不確実性・業務制約と矛盾しないか。
  - Actionを実行するための対象・権限・運用責任が存在するか。
- 過去データによるSimulationやOffline Evaluationで確認できる範囲と、実際の業務Actionを変更して初めて確認できる範囲は区別する。
- 分析結果を利用する仕組みを設計しただけで、売上向上・コスト削減等のBusiness Outcomeが実現したとはみなさない。実際のOutcome改善を主張するには、必要に応じて本番運用・実験・追加評価等のEvidenceが必要である。

### 8.3.6. 「業務接続」とIT実装を分ける

- Dashboard、API、Batch、Notification等は、分析結果を届ける実装方式の候補であり、それ自体が業務接続ではない。
- 先に定義すべきなのは、`WHO / WHEN / Decision Rule / Action` という利用仕様である。
- IT実装方式は、利用仕様、Latency、更新頻度、Security、System Integration、Operation等の制約を踏まえて後段で具体化する。
- この分離により、「Dashboardを作ったが誰も判断を変えない」「Model APIはあるがActionが定義されていない」といった状態を避けやすくなる。

## 8.4. Speaker Note

前のスライドでは、業務課題から「誰が何を決めるのか」を明確にし、そのDecisionに必要なEvidenceからAnalysis Questionを逆算しました。

ここでは、その分析結果を実際の業務でどう使うかを具体化します。重要なのは、分析結果をDashboard等で見せること自体ではありません。誰が、いつ結果を利用し、どの基準で判断し、その結果として何を変えるのかまで定義することです。

例えば予測分析でChurn Riskを出す場合、Riskが高い顧客を表示するだけでは業務利用の設計として不十分です。対応計画を決める前に担当者が結果を確認し、対応可能件数や誤判定コスト等も踏まえて対象を選び、実際にFollow-up Resourceの配分を変える、という利用ルールまで具体化します。予測確率が0.5を超えたら自動的に対応する、と一般化できるわけではありません。

因果推論でも同様です。Effect Estimateを算出しただけでは施策判断にはなりません。施策責任者が次期施策を決める前に、効果量と不確実性、施策Cost、業務上意味のある差を確認し、継続・変更・追加検証・中止等のActionへつなげる必要があります。統計的有意差だけで施策価値が決まるわけでもありません。

PoC段階でこの利用ルールを設計しておくことで、モデルや推定値が得られた後に初めて使い道を考えるのではなく、「この結果は実際のDecisionに使えるか」という業務利用性まで検証できます。ただし、利用ルールを設計できたことと、Business Outcomeが改善したことは別です。実際の効果確認には、必要に応じて運用後の追加評価が必要です。
