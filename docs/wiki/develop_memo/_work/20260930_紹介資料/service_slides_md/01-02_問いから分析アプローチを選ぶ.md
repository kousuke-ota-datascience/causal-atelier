# 2. Slide 2｜問いから分析アプローチを選ぶ

## 2.1. Message

**サービス選択は、業務課題と「何を知りたいか」から決める。**

## 2.2. Chart

**チャートタイトル:** 業務課題と知りたいことから、予測分析・因果推論を選ぶ

Slide 1で示した2つのPoCサービスについて、「どちらを選ぶべきか」という読者の問いに答える。業務課題を起点に、「何を知りたいか」を明確にし、その問いに応じてPredictive / Causalを選ぶ構造とする。

### 2.2.1. Chart Structure

PowerPoint上では、上段に「業務課題」、中央に「何を知りたいか？」、下段にPredictive / Causalを左右対称に配置するシンプルな分岐チャートとする。

読み順は以下の通りとする。

1. 顧客が解決したい業務課題を起点にする
2. その課題について「何を知りたいか」を具体化する
3. 将来・未知のOutcomeを知りたい場合はPredictiveを選ぶ
4. 施策・介入によるOutcomeの変化を知りたい場合はCausalを選ぶ

```text
                         業務課題
                            │
                            ▼
                    何を知りたいか？
                            │
             ┌──────────────┴──────────────┐
             ▼                             ▼
      何が起こりそうか？            何をするとどう変わるか？
         Predictive                       Causal
             │                             │
             ▼                             ▼
      将来の見通しを得る            施策の効果を捉える

            知りたいことが、選ぶ分析を決める
```

**PowerPoint上の配置・強調**

- 最上段の「業務課題」を起点として明示し、分析手法やアルゴリズムから始めない。
- 中央の「何を知りたいか？」を最も大きく見せ、サービス選択の基準であることを示す。
- 下段ではPredictive / Causalを左右対称に配置し、Slide 1で提示した2つのPoCサービスとの連続性を保つ。
- Predictive側は「何が起こりそうか？」、Causal側は「何をするとどう変わるか？」を主要ラベルとする。
- Exploratory / Data UnderstandingはPredictive / Causalの実施上重要だが、「どのサービスを選ぶか」という本スライドの読者の問いに直接答える要素ではないため、主図には置かない。
- 最下部に「知りたいことが、選ぶ分析を決める」と置き、Messageを視覚的に回収する。

## 2.3. Supporting Logic

### 2.3.1. Slide 2の役割

- Slide 1では、当チームがPredictive / Causalという2つのPoCサービスを提供し、それぞれが業務判断に異なる価値を提供することを示した。
- その直後に読み手が持つ自然な問いは、「では、自社の課題ではどちらを選べばよいのか」である。
- Slide 2は、このサービス選択の基準を示すことに集中する。
- データ分析一般の分類体系を説明することや、Exploratory / Predictive / Causalの3分類を網羅的に教えることは本スライドの目的ではない。

### 2.3.2. 業務課題だけでは分析アプローチは決まらない

- 「売上を伸ばしたい」「解約を減らしたい」「設備停止を減らしたい」といった業務課題だけでは、必要な分析アプローチは一意に決まらない。
- 例えば「解約を減らしたい」という同じ業務課題でも、「誰が解約しそうか」を知りたい場合と、「どの施策が解約を減らすか」を知りたい場合では必要な分析が異なる。
- そのため、業務課題を「何を知りたいか」という具体的な問いへ落とし込む必要がある。

### 2.3.3. Predictiveを選ぶ問い

- Predictiveは、現在までに観測できる情報を用いて、未知・将来のOutcomeを見通したい場合に選ぶ。
- 例えば「どの機材で停止リスクが高まりそうか」「どの顧客が解約しそうか」といった問いに対応する。
- 得られた見通しは、計画、配分、優先順位等の業務判断に利用する。
- 予測できる特徴が見つかっても、その特徴へ介入すればOutcomeが変化するとは限らない。

### 2.3.4. Causalを選ぶ問い

- Causalは、施策や介入を変えたときにOutcomeがどう変化するかを知りたい場合に選ぶ。
- 例えば「割引施策を実施すると購買額はどう変わるか」「施策Aと施策BではどちらがOutcomeを改善するか」といった問いに対応する。
- 得られた効果の情報は、施策の実施、継続、変更等の業務判断に利用する。
- 観測された相関や高い予測性能だけでは介入効果を主張できない。

### 2.3.5. Exploratory / Data Understandingの扱い

- Exploratory / Data Understandingは、Predictive / Causalのいずれを実施する場合でも、データ品質、分布、傾向、変数間関係、データ生成過程等を把握するために重要である。
- また、現状理解自体が独立したBusiness Questionとなる場合もある。
- ただし本スライドでは、「Slide 1で示したPredictive / Causalのどちらを選ぶか」というサービス選択の問いに答えることを優先し、Exploratoryを第3の選択肢として主図には置かない。
- Exploratoryの位置づけは、実際のPoCプロセスや分析設計を説明する後続スライドで必要に応じて扱う。

## 2.4. Speaker Note

Slide 1では、当チームが予測分析と因果推論という2種類のPoCを提供することを示しました。次に生まれるのは、「自社の課題では、どちらを使えばよいのか」という疑問です。

その答えは、アルゴリズムやデータの種類から決めるのではなく、まず業務課題を確認し、その課題について何を知りたいかを明確にすることです。

例えば「解約を減らしたい」という業務課題があるとします。「誰が解約しそうか」を知り、対応対象の優先順位を決めたいのであればPredictiveです。一方、「どの施策を実施すれば解約を減らせるか」を知り、施策の実施や選択を判断したいのであればCausalです。

つまり、同じ業務課題でも、知りたいことが違えば選ぶ分析も変わります。

Exploratoryなデータ理解は、Predictive / Causalのどちらでも実務上必要です。ただし、このスライドではサービス選択の基準を明確にすることを優先し、第3のサービスとして並べてはいません。

次のスライドでは、「何が起こりそうか」と「何をするとどう変わるか」が、なぜ同じ分析では答えられないのかを、Predictive / Causalの目的・前提・評価軸の違いから整理します。
