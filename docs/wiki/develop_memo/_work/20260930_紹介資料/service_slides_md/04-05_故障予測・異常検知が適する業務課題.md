## 15.3. Supporting Logic

### 15.3.1. Slide 15の役割

- Slide 14で異常検知と故障予測の分析上の違いを整理した。
- 本スライドでは、どの設備・保全業務がPoC候補になりやすいかを、業界名ではなく**DataとDecisionの成立条件**で示す。
- 「工場だから適する」「センサーデータがあるから適する」といった過度な一般化を避ける。

### 15.3.2. 適用条件

1. **OBSERVE**：設備状態や運転条件を、必要な時間粒度・品質で継続観測できる。
2. **BEFORE**：故障・停止・品質異常が確定する前に兆候を捉える実務上の価値がある。
3. **CHANGE**：兆候やRiskに応じて、点検、交換、保全時期、監視強度等のActionを変えられる。
4. **REPEAT**：設備、部品、ロット、期間等で類似Decisionが繰り返され、学習・評価に必要な事例が蓄積する。
5. **COST ASYMMETRY**：False Negative、False Positive、突発停止、過剰保全等のCost差があり、Decision Ruleを設計する意味がある。

### 15.3.3. Data availabilityによって問いを変える

| Data状況 | 検討しやすい分析課題 |
|---|---|
| 故障Labelと故障前履歴が十分 | Failure Probability、Time-to-Failure、RUL等 |
| 故障Labelが少ないが正常稼働Dataが豊富 | 異常検知、状態監視、変化点検知 |
| 点検結果・劣化状態が継続取得 | 劣化予測、RUL、状態遷移の把握 |
| 設備ごとの差が大きい | Group-aware Validation、設備別Model / 階層化等を検討 |

- 手法を先に決めず、利用可能Dataから成立するQuestionを定義する。
- 故障Eventが極端に少ない場合、教師ありFailure Predictionが不安定または成立しないことがある。

### 15.3.4. 代表的な業務課題

- **突発故障の事前把握**：一定Horizon内のFailure Riskを使い、重点監視・点検候補を選ぶ。
- **劣化設備の優先点検**：Anomaly / Risk上位をHuman Reviewへ回す。
- **点検対象の絞り込み**：全数点検が困難な場合に、優先対象をRankingする。
- **部品交換時期の判断**：RULや劣化推定を参考に、早すぎる交換と遅すぎる交換を減らす。
- **保全計画の見直し**：設備RiskやRemaining Lifeを踏まえて、点検・交換Scheduleを調整する。
- **工程 / 品質異常の早期検知**：設備状態の変化を検知し、追加確認や工程Reviewへつなげる。

### 15.3.5. 適用しにくい条件

- 状態Dataが事後にしか取得できず、Action前に利用できない。
- Failure Labelの定義が不安定、設備ごとに記録基準が異なる。
- 兆候を把握しても保全Actionを変更できない。
- 一件の誤判定が重大で、Human ReviewやSafety Rule等の緩和策を置けない。
- 設備構成や運転条件が頻繁に変わり、Data Generating Processが安定しない。

## 15.4. Speaker Note

故障予測・異常検知は、設備データがあれば自動的に適用できるわけではありません。重要なのは、状態を継続的に観測できること、故障や異常が確定する前に兆候を捉える意味があること、そしてその結果を使って点検や交換、保全計画を実際に変えられることです。

また、Dataの持ち方によって適切な問いは変わります。故障履歴が十分なら故障確率やRULを検討できますが、故障Labelが少ない場合は、まず異常検知や状態監視が現実的なこともあります。

したがってPoCでは「どのアルゴリズムを使うか」ではなく、どの設備状態を観測でき、どのDecisionを変えたいかから分析課題を設計します。
