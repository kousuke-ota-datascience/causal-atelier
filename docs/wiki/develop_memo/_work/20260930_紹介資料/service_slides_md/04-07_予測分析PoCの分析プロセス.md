# 17. Slide 17｜予測分析PoCの分析プロセス

## 17.1. Message

**予測PoCでは、モデルより先にPrediction Questionと検証設計を固定し、実利用時の未知データを模した条件で性能を確かめる。**

## 17.2. Chart

**チャートタイトル:** Model開発より先に、Prediction QuestionとValidationを設計する

Slide 11〜16で示した一般的なPredictiveの価値構造と重点テーマを、再現可能なPoCへ落とすため、何を予測するか・いつ利用可能な情報を使うか・未知データをどう模擬するかを先に固定する。

## 17.3. Supporting Logic

### 17.3.1. Slide 17の役割

- Slide 11〜13ではPredictiveの定義・適用条件・価値を示した。
- Slide 14〜16では故障予測・異常検知を重点テーマとして、分析対象・適用条件・保全Decisionへの期待効果を具体化した。
- **Slide 17では、一般Use Caseでも設備Use Caseでも共通するPredictive PoCの検証Workflowへ戻る。**
- 主題はModel構築手順ではなく、実利用を模した条件でPrediction / Detectionが再現するかを検証できる設計を先に固定することである。

### 17.3.2. Prediction Questionを先に固定する

| 要素 | 確認する問い | 設計上の意味 |
|---|---|---|
| Who / Unit | 誰・何を予測するか | 顧客、案件、設備、製品、時点等の予測単位を固定する |
| Prediction Time | いつ予測を出すか | Featureとして利用可能な情報のCutoffを決める |
| Target | 何を予測するか | Event、Probability、Value、Time-to-event等を定義する |
| Horizon | どこまで先を予測するか | 次30日、次工程、次回点検まで等を固定する |
| Decision / Action | 何に使うか | Ranking、Threshold、Schedule、Allocation等へ接続する |

- 設備例なら「点検日の時点で利用可能なSensor / 運転履歴から、次30日以内のFailure Riskを予測し、点検優先順位へ使う」等まで具体化する。
- 異常検知ではFuture Targetを置かない設計もあるため、正常状態の定義、Reference Window、評価方法、利用Actionを明示する。

### 17.3.3. Leakageを防ぎ、実運用を模擬する

- Featureは実運用のPrediction / Detection時点までに観測可能な情報に限定する。
- Outcome確定後の情報、将来集計、Targetを直接反映する情報を含めない。
- Random Splitだけを機械的に使わず、時系列ならTime Split、同一顧客・設備・拠点の跨りが問題ならGroup Splitを検討する。
- 設備データでは同一設備の近接時点がTrain / Testへ混在すると性能を過大評価し得るため、Time × Groupの設計も検討する。

### 17.3.4. HoldoutとBaselineを明確にする

- Train / ValidationはModel Family、Feature、Hyperparameter等の比較に使う。
- 最終HoldoutはModel Selectionから分離し、選定済みPipelineの未知データ性能を確認する。
- 現行Rule、単純Score、Majority / Mean予測、Linear / Logistic等をBaseline候補とし、複雑化の増分価値を同一条件で確認する。

### 17.3.5. このWorkflowで確認する中心命題

1. Prediction / Detection Feasibility：利用時点のDataから必要Evidenceを作れるか。
2. Generalization：実利用を模した未知データで性能が再現するか。
3. Incremental Value：現行Rule / 単純Baselineに対する増分があるか。
4. Failure Visibility：どの条件で誤るかを把握できるか。
5. Decision Usability：そのOutputをDecision Ruleへ接続できるか。

- この段階でBusiness Outcome改善そのものを証明するわけではない。

## 17.4. Speaker Note

予測PoCで最初に決めるべきなのはアルゴリズムではありません。誰について、いつの時点で、何を、どこまで先まで予測し、その結果を何の判断に使うのかを先に固定します。

設備データでも同様です。同じ設備の近接期間をTrainとTestに混ぜたり、故障後の情報をFeatureに含めたりすると、見かけ上は高性能でも本番では再現しません。そこで、実運用を模したTime / Group Splitを設計し、最終HoldoutをModel Selectionから分けます。

確認したいのは高度なModelを作れたかではなく、未知データでもBaselineより有用なEvidenceを再現できるかです。
