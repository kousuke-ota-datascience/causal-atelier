# 22. Slide 22｜因果推論PoCの分析プロセス

## 22.1. Message

**因果PoCでは、Estimatorより先に「何の効果を、どの前提で識別するか」を設計し、その後に推定と妥当性確認を行う。**

## 22.2. Chart

**チャートタイトル:** Causal PoCは「設計 → 推定 → Evidence化」の順に進める

**PowerPoint上の配置・強調**

- 4つのPhaseを左から右へ配置し、② Causal Designを最も大きくする。

- `Propensity Score` や特定アルゴリズム名は主Chartに置かない。

## 22.3. Supporting Logic

### 22.3.1. Slide 22の役割

- Slide 18〜21では、CausalがCounterfactual Effectを扱うこと、Prediction RiskとTreatment Effectが異なること、Causal PoCの適用条件、EffectをDecisionへ使うValue Chainを示した。
- **Slide 22では、そのEffectを妥当なEvidenceとして得るための因果PoC固有Workflowを定義する。**
- PredictiveでPrediction QuestionとValidation DesignをModelより先に固定したのと同様、CausalではCausal Question / Estimand / IdentificationをEstimatorより先に固定する。
- このSlideは後続Slide 23〜27の索引でもあり、各工程を「何を決める工程か」として分離する。

### 22.3.2. Phase 1｜Question / Estimand：何の効果を知るかを固定する

- Business QuestionをTreatment、Outcome、Population、Time、Contrastまで具体化する。
- そのDecisionに必要な対象量をEstimandとして定義する。
- 「Retention施策は有効か」ではなく、「対象顧客群について、施策あり vs なしで30日以内の解約確率が平均何ポイント変わるか」のように効果対象を固定する。
- Estimandが曖昧なままでは、必要Data、Identification Assumption、Estimator、Interpretationを一貫して設計できない。
- ATE / ATT / CATE等は手法名ではなく、何を推定対象とするかの定義である。

### 22.3.3. Phase 2｜Causal Design：なぜその比較を因果効果と解釈できるかを設計する

- Treatment Assignment Mechanism、Temporal Ordering、Confounder / Mediator / Collider、Comparison Group、制度・Threshold等を整理する。
- DAG等を用いてData Generating Processに関する仮定を可視化し、必要なAdjustmentや比較構造を検討する。
- Randomization、Backdoor Adjustment、DiD、RD、IV等、どのIdentification StrategyでEstimandをObserved Dataから表現するかを決める。
- ここで重要なのは「データにどのMethodを当てるか」ではなく、**どのAssumptionのもとでCounterfactual Comparisonを成立させるか**である。

### 22.3.4. Identification Gate｜推定へ進める条件を判定する

- Identification Gateでは、少なくとも以下を確認する。
  - Treatment / Outcome / Timingが明確か。
  - 必要なComparison Structureが存在するか。
  - 主要Assumptionを業務Process・Data生成過程から合理的に支持できるか。
  - 必要なCovariate、Pre-period、Threshold、Instrument等が観測されているか。
  - Positivity / Overlap等、実データ上の支持が極端に不足していないか。
- GateでNoの場合は、Estimatorを高度化せず、Question変更、Data追加、Experiment、別Designへ戻る。
- Identification Failureを早期に発見すること自体がPoC上の重要な成果である。

### 22.3.5. Phase 3｜Estimation：Identified Estimandを有限標本から推定する

- Identificationされた対象量に対して、Regression / G-formula、Weighting、Matching、Doubly Robust、DiD Estimator等をDesignに応じて選ぶ。
- Estimator選択ではBias / Variance、Model Misspecification、Sample Size、Overlap、Extreme Weight、Computational Stability等を考慮する。
- 複数Estimatorを用いる場合も、それぞれが同じEstimand / Identification Strategyを推定しているか確認する。
- Point Estimateだけでなく、Standard Error、Confidence Interval、Bootstrap等、適切なUncertaintyを付与する。

### 22.3.6. Phase 4｜Validation / Decision：Effectの主張可能範囲をEvidence化する

- Designに応じたDiagnosticsで、観測可能な問題やDesignの適合性を確認する。
- Refutation / Placeboで、明らかにEffectが出るべきでない条件でも同じ結論が出ていないかを確認する。
- Sensitivityで、Adjustment Set、Window、Bandwidth、Trimming、Estimator、未観測交絡等への結論依存性を評価する。
- これらを統合し、「どの前提のもとで、誰について、どのTreatment ContrastのEffectをどこまで主張できるか」をClaim Scopeとして明示する。
- 最終出力はEffect Estimate単体ではなく、Slide 27のEvidence Stackへ統合し、GO / ADDITIONAL VALIDATION / NO-GOを判断する。

### 22.3.7. Predictive Workflowとの対応関係

| Predictive | Causal |
|---|---|
| Prediction Question | Causal Question / Estimand |
| Split / Validation Design | Identification Design |
| Model Selection | Estimator Selection |
| Holdout / Error / Utility | Diagnostics / Sensitivity / Claim Scope |
| Evidence Package | Evidence Stack |

- 両者とも「Algorithmを適用すること」がPoCの中心ではない。
- Predictiveは未知データへのGeneralization、CausalはCounterfactual EffectのIdentificationという異なるValidity問題を扱う。
- この違いを保持したまま、どちらも最後はBusiness Decision / Next PhaseへEvidenceを返す。

## 22.4. Speaker Note

因果PoCでは、最初に「どの手法を使うか」を決めません。最初に決めるのは、何の効果を知りたいのかです。誰に対する、どのTreatmentの、どのOutcomeへの、どの期間の効果かをEstimandまで固定します。

次に、その効果を手元のデータから因果効果として読み取るためのDesignを作ります。Treatmentがどう割り付けられたか、どの変数が交絡しているか、比較群や時間構造がどうなっているかを整理し、どのAssumptionのもとでCounterfactualを構成するかを決めます。

ここでIdentificationできる見込みが立たなければ、RegressionやCausal MLを試しても問題は解決しません。その場合は、追加Dataを取る、Experimentを行う、別の比較構造を使う、あるいは問い自体を見直します。このGateをEstimatorの前に置くことが重要です。

Identificationが成立して初めて、有限標本からEffectをどう推定するかを選びます。その後も、推定値だけを見るのではなく、Designに応じたDiagnostics、Placebo、Sensitivityを行い、結論がどの程度前提や仕様へ依存しているかを確認します。

最終的には「効果が何ポイントだった」だけではなく、「どの前提なら、誰について、どこまでこの効果を主張できるか」と、次に実装へ進むのか追加検証するのかまでを返します。これが因果PoC全体の流れです。

## 22.5. Slide 22からSlide 23への接続
