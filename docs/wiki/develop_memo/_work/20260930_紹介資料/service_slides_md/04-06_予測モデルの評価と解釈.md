# 16. Slide 16｜予測モデルの評価と解釈

## 16.1. Message

**予測モデルは、未知データ性能だけでなく、信頼性・失敗条件・Decision Utilityまで評価して利用可否を判断する。**

## 16.3. Supporting Logic

### 16.3.1. Slide 16の役割

- Slide 14では、Prediction QuestionとValidation Designを先に固定し、Locked HoldoutをModel Selectionから分離した。
- Slide 15では、その条件の内側でBaselineとCandidate Modelを比較し、Fit-for-useなModelを選定した。
- **Slide 16では、選定済みModelを「業務Decisionへ使えるか」という観点まで含めて評価する。**
- 主題はMetricの一覧ではなく、**Generalization → Reliability → Failure Mode → Business Utilityの順に、利用可否のEvidenceを積み上げること**である。

### 16.3.2. Layer 1｜Generalization：未知データで再現するか

- 最初に確認するのは、Train / Validationで選んだPipelineがLocked Holdoutでも性能を再現するかである。
- 指標はPrediction Taskと業務上の誤り方に応じて選ぶ。

| Task | 指標候補 | 主に確認すること |
|---|---|---|
| Binary Classification | AUROC、AUPRC、Precision、Recall、F1等 | Ranking、Class imbalance、見逃し / 過剰対応 |
| Multiclass Classification | Macro / Weighted F1、Class別Recall等 | 特定Classだけ性能が低くないか |
| Regression | MAE、RMSE、Quantile loss等 | 誤差の大きさ、Outlierへの感度 |
| Forecasting | MAE / RMSE / MASE等、Horizon別Backtest | 予測先が長くなるとどう劣化するか |
| Ranking / Risk | Precision@K、Recall@K、Lift等 | Capacity制約下で上位対象を選べるか |

- 指標名は代表例であり、案件ごとのPrediction QuestionとDecision Ruleに合わせて選定する。
- Holdout性能がValidationより大きく低下する場合、Overfit、Temporal Drift、Group leakage、Distribution shift等を疑う。
- 絶対性能だけでなく、現行Rule / 単純Baselineからの増分を見る。

### 16.3.3. Layer 2｜Reliability：ScoreやProbabilityをどこまで信頼できるか

- ClassificationでProbabilityをThreshold、Risk Band、Expected Cost等へ使う場合、Ranking性能が高いだけでは不十分でありCalibrationが重要になる。
- たとえば予測確率0.8の対象群が、実際にも概ね80%発生するかという整合を確認する。
- Calibration curve、Brier score等は候補だが、資料上では指標名より「Probabilityに意思決定上の意味があるか」を重視する。
- 期間別、拠点別、主要Segment別に性能が極端に変動しないかを確認し、Stabilityを把握する。
- Prediction IntervalやUncertainty Estimateを利用できるTaskでは、不確実性の大きいケースをAbstain / Human Reviewへ回す設計も検討する。

### 16.3.4. Layer 3｜Failure Mode：どこで、どのように外れるか

全体平均のMetricだけでは、業務上重要な失敗を見落とすことがある。少なくとも以下を確認する。

1. **Segment**：顧客属性、製品群、設備種、拠点等で性能差がないか。
2. **Period**：季節、制度変更前後、環境変化等で劣化しないか。
3. **Error Type**：False Positive / False Negative、過大 / 過小予測のどちらが多いか。
4. **Error Magnitude**：一部のCaseで致命的に大きな誤差が出ないか。
5. **Error Cost**：誤りがどのAction Cost / Opportunity Costへつながるか。

- 重要Segmentで性能が不足する場合、対象範囲を限定する、Human Reviewを必須にする、追加Dataを取得する等の利用条件へ反映する。
- ExplainabilityはFeature依存やModel挙動、異常なFailure Modeを理解する補助手段として利用する。
- **SHAP、Feature Importance等はPredictive Explanationであり、Featureを変えればOutcomeが変わるという因果効果を意味しない。**

### 16.3.5. Layer 4｜Business Utility：PredictionをDecision Ruleへ変換して有用か

Slide 13で示したとおり、PredictionはそのままBusiness Outcomeではない。PredictionをRanking、Threshold、Capacity等のRuleへ変換したとき、現行Decisionより良い選択ができるかを確認する。

| Decision Pattern | Offline評価例 | 確認したいこと |
|---|---|---|
| PRIORITIZE / REVIEW | Top-K Precision / Recall、Lift、Capacity別Capture Rate | 限られた対応件数で重要対象を多く拾えるか |
| THRESHOLD | Confusion Matrix、Expected Error Cost、Threshold別Utility | 見逃しと不要対応のTrade-offが許容できるか |
| SCHEDULE | Error distribution、早すぎ / 遅すぎCost | Action時期をBaselineより適切に選べるか |
| ALLOCATE / PLAN | Forecast Error、Scenario Simulation、Capacity Mismatch | Resource配分のMismatchを減らせる見込みがあるか |

- ThresholdやTop-Kは、Model Metricだけでなく実際のCapacity、Action Cost、Review工数等を含めて選ぶ。
- Offline SimulationでDecision Utilityの仮説は評価できるが、**Predictionに基づくActionが実際にBusiness Outcomeを改善したことを、Offline予測評価だけで証明することはできない。**
- 実Business Outcomeを確認する必要がある場合は、Production比較、段階導入、A/B Test、因果評価等を別途設計する。

### 16.3.6. Success CriteriaはPoC開始時の合意へ戻して判定する

- Slide 10で合意したPoC成功基準に対し、Slide 16の各Evidenceを対応付ける。
- 「最高Accuracyが得られたからGo」ではなく、少なくとも以下の問いで判定する。
  - Locked HoldoutでBaselineを超えるか。
  - 重要Segmentで許容できるか。
  - Prediction Score / ProbabilityをDecision Ruleへ使えるか。
  - 誤りのDownsideをHuman Review / Safety Rule等で制御できるか。
  - Prediction Timeで必要Dataを取得できるか。
- 成功基準に届かない場合も、追加Dataや対象限定で解決可能か、構造的にPredictionが難しいかを分けて判断する。

### 16.3.7. Evaluationの出力はSlide 17のEvidence Packageへ渡す

Slide 16で得た以下のEvidenceを、次スライドで利用条件・制約と統合する。

- Holdout PerformanceとBaseline比較
- Calibration / Stability
- Segment別・期間別・Error Type別のFailure Mode
- ExplainabilityによるModel挙動の確認
- Threshold / Ranking / Capacity等のDecision Utility
- 未検証事項と追加検証候補

これにより、Modelそのものではなく、**「どの条件なら使えるか」「どの条件では使わないか」まで含めて次フェーズを判断できる**状態にする。

## 16.4. Speaker Note

Modelの評価というとAccuracyやAUROCの話になりがちですが、顧客が知りたいのは最終的に「このPredictionを業務判断に使えるか」です。そのため、評価を4段階に分けます。

まず未知データでBaselineを超えるかを確認します。次にProbabilityやScoreが安定して使えるか、Calibrationや期間別性能を見ます。そのうえで、どのSegmentで、どのように失敗するかを調べ、必要ならHuman Reviewや対象限定といった利用条件へ反映します。

最後に、実際の対応可能件数や誤判定Costを入れて、RankingやThresholdを使ったDecisionが現行Ruleより有利かを見ます。ここまで評価して初めて、Predictionを業務へ接続できるかを判断できます。

ただし、OfflineでPredictionとDecision Ruleの有用性を示せても、実際のBusiness KPI改善を直接証明したことにはなりません。そこは必要に応じて本番環境で追加検証します。
