# 14. Slide 14｜予測分析PoCの分析プロセス

## 14.1. Message

**予測PoCでは、モデルより先にPrediction Questionと検証設計を固定し、実利用時の未知データを模した条件で性能を確かめる。**

## 14.3. Supporting Logic

### 14.3.1. Slide 14の役割

- Slide 11では、Predictiveを `Decision時点の観測情報 → Prediction → Decision / Action` と定義した。
- Slide 12では、Outcome確定前にPredictionをActionへ変換でき、誤予測を業務で扱える課題がPredictive PoC候補になることを示した。
- Slide 13では、PredictionをDecision Ruleへ組み込み、多数のDecisionをBaselineより平均的に改善することがBusiness Valueの源泉であると整理した。
- **Slide 14では、そのValue Chainの起点となるPredictionが、実利用時の未知データでも再現するかを検証するためのWorkflowを示す。**
- 主題は「モデルをどう作るか」ではなく、**何を未知データとみなし、何をもって再現性を評価するかをModel開発前に設計すること**である。

### 14.3.2. Prediction Questionを先に固定する

Prediction Questionは少なくとも以下を明示する。

| 要素 | 確認する問い | 設計上の意味 |
|---|---|---|
| Who / Unit | 誰・何を予測するか | 顧客、案件、設備、製品、時点等の予測単位を固定する |
| Prediction Time | いつ予測を出すか | Featureとして利用可能な情報のCutoffを決める |
| Target | 何を予測するか | Event、Probability、Value、Time-to-event等のOutcomeを定義する |
| Horizon | どこまで先を予測するか | 30日以内、次工程、次回点検まで等の予測期間を固定する |
| Decision / Action | 予測を何に使うか | Ranking、Threshold、Schedule、Allocation等の利用方法へ接続する |

- たとえば「解約を予測する」だけでは不十分であり、「月末時点の既存顧客について、次30日以内の解約Riskを予測し、Retention担当者のReview優先順位に使う」のようにPrediction TimeとActionまで固定する。
- 同様に、Qualityでは「出荷前時点で不良Riskを予測し重点検査へ回す」、Operationsでは「発送時点で遅延Riskを予測しHigh-risk shipmentを優先管理する」といった形で定義できる。
- これにより、Customer / Quality / Operations / Maintenance等の異なるUse Caseでも、共通の設計原則でPredictive PoCを扱える。

### 14.3.3. Target / FeatureはPrediction Timeを基準に定義する

- Featureは、**実運用でPredictionを出す時点までに観測可能な情報**に限定する。
- Outcome確定後にしか得られない情報、将来の集計値、Targetを直接反映する情報を含めると、Future Leakage / Target Leakageにより見かけの性能が過大評価される。
- Target Labelの生成ロジックもPrediction TimeとHorizonに整合させる。ラベル期間とFeature期間が重複する場合は特に注意する。
- 欠損値やカテゴリ定義等のPreprocessingも、将来情報を利用しない形でTrain / Validation単位に適用する必要がある。

### 14.3.4. Split DesignはData Generating Processと実運用を模擬する

- Splitは単に一定割合でRandomに分ければよいわけではない。
- **Random Split**：観測が概ね交換可能で、同一Entityや時系列依存によるLeakageが小さい場合。
- **Time Split**：過去から将来を予測する運用で、環境変化やTrendを含めてGeneralizationを見たい場合。
- **Group Split**：同一顧客・設備・拠点等の情報がTrainとValidationへ跨ると過大評価になる場合。
- 実案件ではTimeとGroupを組み合わせる等、Data Generating Processに合わせた設計が必要になる。
- Splitの単位・Cutoff・除外条件は、結果を見て都合よく変えるのではなく、Prediction Questionと実運用条件から先に決める。

### 14.3.5. HoldoutはModel Selectionから分離する

- Train / ValidationはModel Family、Feature、Hyperparameter等を比較・選定するために使用する。
- Holdoutは、**選定済みPipelineを最後に未知データへ適用したときの再現性能を確認するために保持する**。
- Holdoutを繰り返し参照し、その結果に合わせてModelやFeatureを変更すると、実質的にHoldoutへ過適合し、未知データ性能の推定が楽観的になる。
- 必要な反復回数が多い場合はNested Validation、Cross-validation、時系列Backtest等を案件特性に応じて利用し、最終評価用データとの役割を分ける。

### 14.3.6. Baselineを置き、増分価値を検証する

- 比較対象は「Modelなし」だけではない。現行Rule、単純なScore、Majority / Mean予測、単純なLinear / Logistic Model等をBaseline候補とする。
- 高度なModelが高い絶対性能を示しても、現行判断や単純Baselineからの増分が小さければ、複雑化・運用Costに見合わない場合がある。
- したがってPoCでは、**同じValidation条件のもとでBaselineとCandidateを比較する**ことが重要である。

### 14.3.7. このWorkflowで確認できること

このWorkflowが直接検証する中心命題は、以下である。

1. **Prediction Feasibility**：Prediction Timeで利用可能なDataからTargetを予測できるか。
2. **Generalization**：実利用を模した未知データで性能が再現するか。
3. **Incremental Value**：現行Rule / 単純Baselineに対する増分があるか。
4. **Failure Visibility**：どの条件で誤るかを把握できるか。
5. **Decision Usability**：そのPredictionをDecision Ruleへ接続する余地があるか。

- ただし、この段階でBusiness Outcome改善そのものを証明するわけではない。
- Predictionを使ったActionが実KPIを改善するかは、Slide 16のBusiness Utility評価と、必要に応じたProduction比較・実験・因果評価等へ分けて考える。

## 14.4. Speaker Note

予測PoCで最初に決めるべきなのはアルゴリズムではありません。誰について、いつの時点で、何を、どこまで先まで予測し、その結果を何の判断に使うのかを先に固定します。

そのうえで、実運用時に利用できる情報だけでFeatureを作り、将来の未知データをできるだけ模擬するSplitを設計します。時系列データなのにRandom Splitを使う、同じ顧客や設備がTrainとTestへ跨る、Outcome確定後の情報がFeatureへ入る、といった設計では、見かけ上は高精度でも本番では再現しません。

Model開発はTrain / Validationの内側で反復し、最終HoldoutはModel Selectionから分離します。ここで確認したいのは「高度なModelを作れたか」ではなく、「実利用時の未知データでも、現行Ruleや単純Baselineより有用なPredictionを再現できるか」です。
