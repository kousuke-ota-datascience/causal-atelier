# 13. Slide 13｜予測分析適用による期待効果

## 13.1. Message

**予測分析は、誤りを含む予測でも、多数のDecisionで対象・時期・量をより良く選ぶことで、KPIの期待値を改善し得る。**

## 13.2. Chart

**チャートタイトル:** 予測上の優位を、反復するDecisionを通じてKPI価値へ変換する

## 13.3. Supporting Logic

### 13.3.1. Slide 13の役割

- Slide 11では、Predictiveを `Decision時点の観測情報 → Prediction → Decision / Action` と定義した。
- Slide 12では、そのPredictionを業務へ適用しやすい条件を、`BEFORE / CHANGE / DIFFERENTIATE` と `REPEAT / ACCUMULATE / TOLERATE / OBSERVE` で整理した。
- **Slide 13では、これらの条件を満たす業務にPredictionを組み込んだとき、なぜBusiness KPIの改善が期待できるのか、そのValue Chainを示す。**
- したがって、本スライドの主題は「どの業務が適するか」ではなく、**予測上の優位をDecision Ruleと反復Actionによって業務価値へ変換するメカニズム**である。

### 13.3.2. Predictiveの価値は「一件を必ず当てること」ではなくDecisionの期待値改善にある

- Predictive ModelにはFalse Positive、False Negative、Forecast Error等が残るため、個々の事象を必ず正しく言い当てることを前提にしない。
- 実務上は、Predictionを使ったDecisionがBaselineより平均的に良ければ、同種のDecisionを多数回行う中で差分を累積できる。
- したがって、評価すべき対象は単純なAccuracyだけではない。案件に応じてRanking、Calibration、Error Cost、Capacity制約等を踏まえ、**Predictionを使ったDecision Ruleが現行RuleよりKPI上有利か**を確認する必要がある。
- これは「AIは一発勝負の予測ができない」という意味ではない。単発・低頻度のDecisionでも、Predictionの不確実性を評価でき、誤りのDownsideを許容・緩和できるなら利用可能である。
- 一方、1回の誤判定が不可逆・致命的で、Human ReviewやSafety Rule等のFail-safeも置けない場合、Prediction単独による自動Decisionは適用しにくい。

### 13.3.3. Decision RuleがPredictionを業務価値へ変換する

PredictionそのものはBusiness Outcomeではない。PredictionをどのようなRuleでActionへ変換するかによって、得られるOperational Effectは変わる。

| Action Pattern | Decision Ruleの例 | Operational Effectの例 | 接続し得るKPI / Business Outcome |
|---|---|---|---|
| PRIORITIZE / REVIEW | Risk上位から対応、一定Score以上を追加確認 | 見逃し・不要対応を減らす | 損失抑制、対応効率、品質 |
| SCHEDULE | Risk / RULに応じて点検・交換時期を調整 | 早すぎる・遅すぎる対応を減らす | Down Time、保全Cost、稼働率 |
| ALLOCATE / PLAN | 予測量・完了見込みに応じてCapacity配分 | 不足・遊休・偏りを減らす | Resource効率、Lead Time、計画KPI |

- 同じPrediction性能でも、Thresholdや対象件数、Capacity、Human Reviewの有無により業務価値は変わる。
- そのためPoCでは、Model単体の性能だけでなく、**実際の業務制約を含むDecision Ruleまで含めてValue Chainを評価する**必要がある。

### 13.3.4. TOLERATE / OBSERVEは価値の維持にも効く

- `TOLERATE` はPrediction ErrorのBusiness Costを制御するための条件であり、Human Review、追加確認、Abstention、Safety Rule、段階的Action等によってDownsideを限定する。
- `OBSERVE` はOutcome / KPIを事後観測し、Prediction性能だけでなく、Error Pattern、Decision Rule、Operational Utilityの変化を継続評価するための条件である。
- Productionでは対象Population、業務Rule、データ生成過程が変化し得るため、継続観測によってDriftやRule劣化を検知できる設計が望ましい。

### 13.3.5. PoCで確認できることと、追加検証が必要なことを分ける

PoCでは少なくとも以下を段階的に確認する。

1. **Prediction Performance**：未知データでBaselineより十分な予測性能があるか。
2. **Decision Utility**：Threshold、Ranking、Capacity等を含むDecision Ruleで、現行Ruleより良い判断が期待できるか。
3. **Actionability / Operating Fit**：実業務でそのAction変更を実行でき、Prediction Errorを許容・緩和できるか。
4. **Business Outcome Hypothesis**：Operational Effectが対象KPIへ接続する合理的な経路があるか。

- Offline検証やSimulationで `Prediction Performance` と一定の `Decision Utility` は評価できる。
- ただし、Predictionに基づくActionが実際にBusiness Outcomeを改善したかは、Offlineの予測精度だけでは一般に証明できない。
- 実Business Outcomeを検証する場合は、案件に応じてProduction比較、A/B Test、段階導入、または因果的な評価設計等を検討する。

### 13.3.6. Slide 4との重複を避ける

- Slide 4は、Predictive / Causalの両サービスについて `Analysis Result → Action → Business Outcome` という全体価値を説明する。
- Slide 13ではPredictiveに限定し、**Prediction Errorを前提に、Decision Ruleを介して多数のActionの期待値を改善し、その差分をKPIへ累積する**というPredictive固有の価値発現メカニズムを深掘りする。
- したがって、単に `Prediction → Action → 収益向上 / Cost削減` を繰り返すだけのスライドにはしない。

## 13.4. Speaker Note

ここで伝えたいのは、「予測を当てれば価値が出る」ではない。Predictive Modelには誤りが残るが、そのPredictionをRankingやThreshold等のDecision Ruleへ組み込み、多数のDecisionで現行Ruleより平均的に良いActionを選べれば、KPIの期待値を改善できる。

そのため、1件ごとの正誤よりも、False Positive / False NegativeのCost、対応可能件数、Human Review、Safety Rule等を含めて、Decision全体で価値が出るかを見る。逆に、一度の誤判定が致命的でErrorを吸収する仕組みがない用途は、Prediction単独の自動化には適しにくい。

また、Model AccuracyとBusiness Outcomeは同義ではない。PoCではPrediction性能とDecision Utilityを評価し、実際のBusiness Outcome改善は必要に応じてProductionで追加検証する。
