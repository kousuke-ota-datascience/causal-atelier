## 1. 文書の目的

本書は、Ariadneが解決する問題、提供する価値、初期実装の対象範囲および設計原則を定義する。

初期版の目的は、分析管理機能を網羅的に実装することではない。次の価値仮説を、利用者が検証可能な最小構成で確かめることである。

> 複数の因果探索・因果推論結果を比較し、採用した結果について、使用データ、Graph、アルゴリズム、パラメータおよび判断理由まで遡れることは、分析者の判断品質と再現性を改善するか。

## 2. プロダクトの一文定義

> **Ariadneは、前処理済みデータに対する因果探索と因果効果推定を反復し、比較した条件・結果・判断理由を一つの分析来歴として確認できるワークスペースである。**

短く表現すると、次のとおりである。

> **何を変えて試し、何が変わり、なぜその結果を採用したかを残す。**

## 3. 初期版が解決する問題

Notebook、CLI、ファイル名および個別の実験追跡だけでは、次の情報が分散しやすい。

1. どの前処理済みデータを使ったか
2. どの因果探索アルゴリズムとパラメータを使ったか
3. 複数のGraph結果にどのような差があったか
4. どのGraphを推論入力として採用したか
5. なぜそのGraphを採用・修正したか
6. treatment、outcome、estimandおよび調整集合は何か
7. どの推定器を使用し、推定結果とdiagnosticsがどう異なったか
8. 数値結果を採用できない理由は何か
9. 結果からデータ、Graph、設定、コードおよびArtifactへ遡れるか

初期版では、これらを少数の正本Entityと4つの作業Workspaceで管理する。

## 4. 対象利用者

### 4.1 主利用者: Analyst

基本的な統計・因果推論の知識を持ち、Python、NotebookまたはCLIで分析している利用者。

初期版では、非専門家へ因果推論を自動化することを目的としない。

### 4.2 参照利用者: Viewer / Reviewer

Analystが残したResultと来歴を読み、結果の採用可能性を確認する利用者。

初期版では独立した承認ワークフローやレビューEntityを設けず、Results / Lineage Workspaceのread-only利用で検証する。

## 5. 対象利用場面

### 5.1 Golden Path: 売上改善

例:

- クーポン配布と売上の因果構造候補を探索する
- PC、GES等の結果を比較する
- PCのalphaを変更し、Graph構造の感度を確認する
- 採用Graphを用いて、クーポン配布のATEまたはATTを推定する
- 複数推定器の推定値、信頼区間、overlapおよびbalanceを比較する

### 5.2 Transfer Case: 退職者抑制

初期版の構造を人事データへ適用し、次を確認する。

- 予測因子と因果因子を混同しないか
- 介入可能変数と不変属性を区別できるか
- 機微属性を分析条件として明示できるか

生存時間分析、time-varying confoundingおよび自動的な対象者選定は初期対象外とする。

### 5.3 Transfer Case: 従業員エンゲージメント向上

初期版の構造を用いて、変数をOutcome、Mediator、Confounder等として扱う際の実務上の理解可能性を確認する。

階層モデル、反復測定および尺度モデルは初期対象外とする。

## 6. 初期版の分析サイクル

```text
Projectの目的・分析メモ
  ↓
前処理済みDataset Versionを登録
  ↓
複数条件で因果探索を実行
  ↓
Graph結果を比較
  ↓
採用Graph Versionを選択・必要に応じて修正
  ↓
Causal Designを指定
  ↓
複数推定器でATE/ATTを推定
  ↓
Resultとdiagnosticsを比較
  ↓
採用結果、判断理由、仮定および限界を記録
  ↓
Resultから使用条件とArtifactへ遡る
```

## 7. 設計原則

### 7.1 比較を中心に設計する

Ariadneの中心操作は単一Executionの閲覧ではなく、複数Execution / Resultの比較である。

比較では、少なくとも次を分けて表示する。

```text
同一条件
変更条件
結果差分
```

### 7.2 分析来歴を不変snapshotで保持する

初期版では、Research Context、Experiment、Analysis DefinitionおよびExecution Planを独立Resourceにしない。

Executionが次の不変snapshotを保持する。

- objective / question memo
- 分析方針の選定理由
- 使用Dataset Version
- operation
- algorithm / estimator
- parameter
- Causal Design
- 使用Graph Version
- code / runtime version

これにより、問いに相当する文脈から成果物までの主要な来歴を保持する。

### 7.3 概念、Entity、テーブルおよび画面を分離する

```text
意味論上区別する概念
≠ 独立Entity
≠ 独立テーブル
≠ 独立画面
```

初期版では、利用者の作業単位に合わせて画面を統合する。

### 7.4 因果探索結果のGraph semanticsを保持する

PCやGES等の出力を一律にDAGとして扱わず、Graph種別およびendpoint semanticsを保持して表示する。

次を区別する。

- Algorithm Output Graph
- Selected / Edited Graph Version
- Estimation Input Graph Version

### 7.5 数値を返せない状態を分析結果として扱う

次は技術障害と区別する。

- `NOT_IDENTIFIED`
- `INSUFFICIENT_OVERLAP`
- `INSUFFICIENT_SAMPLE`
- `ESTIMATION_UNRELIABLE`

初期版は、無理にATE/ATTを返さず、理由をResultとして保存する。

### 7.6 ResultとArtifactを分離する

- Result: Graph構造、効果推定値、diagnostics等の論理結果
- Artifact: JSON、CSV、画像、report、manifest等の物理生成物

### 7.7 計算条件の変更は別Executionとする

Algorithm、parameter、Dataset Version、Graph VersionまたはEstimatorを変更した利用者再実行は別Executionである。

技術的retryは同じExecutionとして扱う。ただし、初期版ではStage / Attemptを独立Entityにせず、Executionのretry情報として保持する。

### 7.8 Research Contextは段階的かつフラットに整理する

分析開始時に、完成したResearch Questionや階層構造を必須としない。初期版では、Research Contextに相当する目的、問題意識および問いを、ProjectメモまたはExecution snapshotとしてフラットに保持する。

将来、Research Contextを独立管理する場合も、正本はフラットなContextと任意のrelationを基本とする。relationの例は次のとおりである。

- `REFINES`
- `DERIVED_FROM`
- `SUPERSEDES`
- `RELATED_TO`

ツリー表示が必要な場合は、これらのrelationから生成するProjectionとして扱う。

## 8. 初期スコープ

### 8.1 MUST

- Project作成と目的メモ
- 前処理済みDataset Versionの登録
- Dataset previewと基本schema確認
- 複数因果探索Execution
- Algorithm / parameter差分とGraph差分の比較
- Graph Versionの選択・簡易修正・固定
- 二値TreatmentのATE / ATT
- 複数Estimatorの実行・比較
- diagnostics表示
- 科学的に採用できないResultの表示
- ResultからDataset、Graph、algorithm、parameter、codeおよびArtifactへの遡及
- 採用理由、仮定および限界のメモ

### 8.2 SHOULD

- Dataset Versionを変更した再評価
- read-only共有
- portable manifest / result export
- Graphの禁止edge、必須edge、時間順序制約

### 8.3 初期対象外

- Research Contextの独立Resource / Version
- Experimentの独立Workspace
- Analysis Definitionの独立Resource
- Interpretation / Claimの正式なVersion管理
- Comparisonの保存Resource
- 汎用Lineage Relation Entity
- Research Contextの階層編集UI
- 独立したレビュー・承認ワークフロー
- Stage Execution / Stage Attemptの詳細管理
- 詳細なRBAC
- 連続Treatment
- CATE / HTE
- 時系列・生存時間・反復介入
- IV、DiD、RDD、Synthetic Control
- policy optimization

## 9. 初期版の成功条件

初期版は、Analystが次を一連の操作で完了できた場合に価値仮説を支持する。

1. 前処理済みデータを登録する
2. 複数の探索条件を実行する
3. Graph差分を確認して採用Graphを決める
4. 採用Graphを用いて複数推定器を実行する
5. diagnosticsを含めてResultを比較する
6. 採用または不採用の理由を記録する
7. 後から、使用データと実行条件を復元する

## 10. 将来構想との関係

Ariadneでは、初期版の範囲を超える概念データモデルや機能も将来構想として検討する。

利用実績により、独立したライフサイクル、検索、共有、承認、再利用またはVersion差分の必要性が確認された概念だけを、独立Resourceへ昇格させる。

候補は次のとおりである。

- Research Context
- Experiment
- Analysis Definition Version
- Interpretation / Claim
- Comparison
- Lineage Relation
- Stage Execution / Stage Attempt
