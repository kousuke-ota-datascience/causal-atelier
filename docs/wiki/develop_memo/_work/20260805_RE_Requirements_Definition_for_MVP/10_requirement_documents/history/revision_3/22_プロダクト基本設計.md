## 1. 文書の設計粒度

本書は、利用者・画面・システムコンポーネント間の責務と、相互に受け渡す**論理情報**を定義する。

本書では次を確定しない。

- DTOクラス名と全フィールド
- JSON Schema、serialization形式
- Web APIのEndpoint一覧
- validation ruleとerror code
- package、class、repositoryの物理構成
- transaction境界と例外処理の実装方法

これらは、それぞれ`23_API・インターフェース設計.md`および`30_詳細設計.md`で定義する。

## 2. 設計対象と責務

### 2.1 対象コンポーネント

| コンポーネント | 存在目的 | 主な責務 | 主な対象外 |
|---|---|---|---|
| Web App | Analyst / Viewerが分析作業と結果確認を行うUIを提供する | 入力支援、Workspace遷移、Graph可視化、Comparison表示、Lineage表示、Annotation編集 | 数値計算、正本データの直接更新、長時間処理 |
| Web API | Web系機能の正本Control Planeを提供する | validation、認可、Entity操作、Execution受付、status取得、Comparison / Lineage照会、Artifact参照 | Scientific Coreの数値実装、長時間計算の同期実行 |
| 非同期Execution Worker | Web requestから長時間計算を分離し、受付済みExecutionを処理する | Executionの取得、入力解決、Scientific Core呼出し、Result / Artifact保存、status更新、技術エラー記録 | UI、分析条件の決定、科学的結論の作成 |
| Metadata DB | 分析来歴と実行状態の正本を保持する | 7つの正本Entityの永続化、参照整合性、状態管理 | 大容量ファイル本体の保存、数値計算 |
| Artifact Store | Datasetおよび生成物の物理ファイルを保存する | Dataset file、Graph、table、manifest、logの保存、hash検証、取得 | Entity関係やstatusの正本管理 |
| Scientific Core | 因果探索・因果推論の再利用可能な科学計算能力を提供する | Discovery、Graph utilities、Identification / preflight、Treatment Effect Estimation、Diagnostics、構造化Result生成 | Web/API/DBへの依存、Execution status管理、Artifact所在の決定 |
| Local CLI | Scientific Coreをローカルで直接利用する | 設定検証、Discovery / Estimation実行、local Result / Artifact / manifest生成 | Web Project管理、Web Execution Identity、Comparison UI、Queue管理 |

### 2.2 Workerを設ける理由

因果探索・因果推論は、Web requestの許容時間を超える可能性がある。複数条件の一括実行では処理時間がさらに増える。Workerは次を実現するために設ける。

- Web Appを計算完了までblockしない
- Executionごとにstatusを追跡する
- 技術例外を他のExecutionから隔離する
- ResultおよびArtifact保存を一貫した処理として行う
- cancelおよび技術的retryの制御点を設ける

### 2.3 初期対象外

- Research Context / Experiment / Analysis Definition専用モジュール
- 汎用Workflow / Pipeline Designer
- Stage / Attemptの詳細管理
- 独立Comparison Resource
- 独立Lineage Relation Store
- 承認Workflow
- 詳細監査UI
- 複数Artifact Storeの同時サポート
- 高可用性・マルチテナント構成

## 3. システム構成

### 3.1 Web構成

初期版はモジュラーモノリスを基本とする。

```text
Analyst / Viewer
      |
      v
   Web App
      |
      v
   Web API
   |      |       \
   |      |        \--> Artifact Store
   |      +-----------> Metadata DB
   |
   +--> Execution Worker
              |
              v
       Scientific Core
       ├── Discovery
       ├── Graph utilities
       ├── Identification / preflight
       ├── Treatment Effect Estimation
       └── Diagnostics
```

Web APIとWorkerは同一アプリケーションコードを共有してよいが、実行プロセスと責務を分離する。

### 3.2 Local CLI構成

```text
Local CLI
  ├── Scientific Core
  ├── local manifest
  ├── local Artifact
  └── experiment tracking adapter [optional]
```

CLIとWeb/APIは科学計算能力を共有するが、実行IdentityとControl Planeを共有しない。

## 4. アーキテクチャ原則

### 4.1 Product層とScientific Coreを分離する

- 数値実装をinterfaceごとに複製しない
- Metadata DBやWeb frameworkへの依存をScientific Coreへ持ち込まない
- optional external adapterをcore import時に必須としない
- Scientific Coreは構造化された入力を受け、構造化された科学結果を返す

### 4.2 単純なExecutionモデルを使う

- 1 algorithm / parameter / estimator条件 = 1 Execution
- 複数条件は`batch_key`で束ねる
- WorkerはExecution単位で処理する
- 初期版ではStage / Attempt Entityを作らない
- 技術的retry情報はExecutionに保持する

### 4.3 Execution Snapshotを正本とする

Execution受付時に次の論理情報を固定し、実行後に上書きしない。

- objective / rationale
- Dataset Version
- Graph Version
- analysis specification
- algorithm / estimator
- parameters
- random seed
- code / runtime version

### 4.4 ComparisonとLineageはQuery Modelとする

- Comparisonは選択されたExecution / Resultから都度導出する
- Lineageは論理データ設計上の明示参照を辿って導出する
- 初期版ではComparisonやLineageを独立CRUD対象にしない

### 4.5 Web/APIとCLIの実行Identityを分離する

Web/API経路は、Ariadne管理下の非同期処理要求として`execution_id`を持つ。CLI経路は独立した実行粒度を持ち、Web/APIの識別子を共有しない。

## 5. プロダクトモジュール

### 5.1 利用者向けWorkspace

| Workspace | 主な責務 |
|---|---|
| Project / Data Workspace | Project目的、Dataset Version登録・確認、最近の分析 |
| Discovery Workspace | 条件設定、一括実行、Graph比較、Graph選定・簡易修正 |
| Inference Workspace | Causal Design、preflight、複数Estimator実行、diagnostics比較 |
| Results / Lineage Workspace | Result比較、判断メモ、来歴、Artifact、read-only共有 |

### 5.2 論理Application Service

| Service | 主な責務 |
|---|---|
| Project Data Service | ProjectとDataset Versionの登録・照会 |
| Execution Service | 複数Executionの受付、状態照会、cancel、retry |
| Graph Version Service | Discovery ResultからGraph Versionを作成・固定する |
| Comparison Query Service | Execution SnapshotとResultから比較表示を生成する |
| Lineage Query Service | 明示参照からLineage表示を生成する |
| Annotation Service | Result / Graph Versionへの判断メモを管理する |
| Artifact Service | Artifact metadata、保存、取得、hash検証を仲介する |
| Scientific Core Adapter | Product層とScientific Core間の論理変換を行う |

Serviceのclass、method、repository依存は`30_詳細設計.md`で定義する。

### 6.2 Project / Data Workspace

#### 6.2.1 目的

### 6.3 Discovery Workspace

#### 6.3.1 目的

同一Datasetに対する複数探索条件を実行・比較し、推論に使用するGraph Versionを決める。

#### 6.3.2 画面構成

```text
左ペイン: 入力・実行条件
中央: Graph表示・重ね合わせ・差分
右ペイン: 条件差分、warning、採用・修正操作

```

#### 6.3.3 入力する論理情報

- Dataset Version
- objective

- algorithm selection
- parameter grid
- random seed

- 複数条件の実行受付

- Result選択
- Graph比較

- Graph Version固定

#### 6.3.5 比較表示

| 区分 | 表示例 |
|---|---|
| 同一条件 | Dataset Version、feature set、seed |

## 7. 画面遷移と論理引渡し情報

### 7.1 設計方針

画面間ではEntity全体を保持せず、識別子と遷移に必要な最小contextを引き渡す。遷移先は識別子を用いてWeb APIから正本情報を再取得する。

型、必須性、JSON表現およびDTO名は`23_API・インターフェース設計.md`で定義する。

### 7.2 遷移一覧

| 遷移元 | 遷移先 | 契機 | 引き渡す論理情報 | 遷移先の責務 |
|---|---|---|---|---|
| Project / Data | Discovery | Dataset Versionを選択して探索開始 | Project、Dataset Version、任意の元Execution | Dataset metadataを取得し、探索条件を初期化する |
| Discovery | Inference | Graph Versionを固定して推論開始 | Project、Dataset Version、Graph Version、source Discovery Result | Dataset、Graph、source Resultを取得し、Causal Designを初期化する |
| Discovery | Results / Lineage | Discovery Resultを比較する | Project、Result集合、比較種別 | ResultとExecution Snapshotを取得し、比較表示を生成する |
| Inference | Results / Lineage | Estimation Resultを比較する | Project、Result集合、比較種別 | Result、diagnostics、Lineageを取得する |
| Results / Lineage | Discovery | 探索条件を変更して再実行 | Project、元Execution、遷移先種別 | 元Executionから初期値を取得し、新規実行フォームとして表示する |
| Results / Lineage | Inference | 推定条件を変更して再実行 | Project、元Execution、遷移先種別 | 元Executionから初期値を取得し、新規実行フォームとして表示する |

## 8. Worker基本設計

### 8.1 論理処理

```text
QUEUED
→ Execution取得
→ 入力Dataset / Graph / Artifact解決
→ Snapshot整合性確認
→ RUNNING
→ Scientific Core実行
→ Artifact保存
→ Result保存
→ SUCCEEDED
```

### 8.2 技術失敗と科学的負結果

技術例外はExecutionを`FAILED`にする。一方、Scientific Coreが`NOT_IDENTIFIED`等を返した場合は、Resultを保存してExecutionを`SUCCEEDED`とする。

### 8.3 Queueの初期方針

- DB-backed queueを基本とする
- WorkerはExecution単位で排他的に取得する
- Transactional Outbox、lease、heartbeatの完全モデルは初期必須にしない
- stale `RUNNING`の回復は単純なtimeout判定またはOperator手順から開始する

排他取得方法、transaction境界、retry制御は`30_詳細設計.md`で定義する。

## 9. Scientific Core基本設計

### 9.1 Discovery能力

Scientific Coreは、Dataset参照、Algorithm、parameter、constraint、seedを受け取り、次を返す。

- graph type
- node / edge / endpoint representation
- scientific warnings
- diagnostics
- Artifact候補

### 9.2 Estimation能力

Scientific Coreは、Dataset参照、Graph参照、Causal Design、Estimator、parameter、seedを受け取り、次を返す。

- scientific status
- estimate
- uncertainty
- diagnostics
- warnings
- Artifact候補

具体的なinterface schemaは`23_API・インターフェース設計.md`で定義する。

## 11. 初期E2E処理フロー

### 11.1 Discovery

```text
Dataset Version選択
→ algorithm / parameter grid入力
→ 複数Execution受付
→ Worker実行
→ Result / Artifact保存
→ Comparison生成
→ Graph選定・修正
→ Graph Version固定
```

### 11.2 Inference

```text
Dataset Version + Graph Version選択
→ Causal Design入力
→ estimator群選択
→ 複数Execution受付
→ Worker実行
→ Result / Artifact保存
→ Comparison生成
→ Annotation記録
→ Lineage確認
```

## 12. 基本設計上の受入れ条件

- 4 WorkspaceでGolden Pathを完了できる
- Workspace間で必要な論理情報が定義されている
- Scientific CoreとProduct層の責務が分離されている
- ComparisonとLineageを正本Entityとして追加せずに生成できる
- Web/APIとCLIの実行Identityが混同されていない
- 技術失敗と科学的負結果が分離されている
