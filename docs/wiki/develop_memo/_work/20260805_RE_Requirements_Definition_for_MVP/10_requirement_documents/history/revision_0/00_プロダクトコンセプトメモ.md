# 00 プロダクトコンセプトメモ

- 文書状態: 討議用ドラフト
- 作成日: 2026-08-05
- 対象: Ariadne 初期プロダクト
- 主対象用途: 表形式の事業データを用いた因果探索・因果効果推定
- Golden Path: 売上改善
- Transfer Case: 退職者抑制、従業員エンゲージメント向上

## 1. 文書の目的

本書は、Ariadneが何を解決するプロダクトであり、どの設計思想を維持し、何を初期対象外とするかを定義する。

本書は物理ERやAPI仕様を直接決定するものではない。要件・論理データ設計・基本設計を判断する際の上位原則として使用する。

## 2. プロダクトの一文定義

> **Ariadneは、分析上の問題意識・問いから、使用データ、分析方針、実行条件、結果、限定付き解釈までを、再現・比較・レビュー可能な来歴として結び付ける分析ワークスペースである。**

より短く表現すると、次のとおりである。

> **問いから結果までの「なぜ・何を・どう試し・何が得られ・何を言えるか」を管理する。**

Ariadneは、因果探索アルゴリズムのランナー、Pipeline Runner、MLflow UIの代替、またはArtifact保管庫だけを目的としない。これらの機能を利用しながら、分析者の思考と科学計算の来歴を接続することを目的とする。

## 3. 解決する問題

既存のNotebook、CLI、ファイル管理および実験追跡ツールでは、以下が分断されやすい。

1. 何を明らかにしたかったのか
2. なぜその分析方針を選択したのか
3. どのデータを使用したのか
4. どのアルゴリズムとパラメータを使用したのか
5. 何を変更して再実行したのか
6. どの結果を比較したのか
7. どの結果を根拠として何を解釈したのか
8. 結論の適用範囲、仮定および限界は何か

Ariadneは、これらを単一の巨大な文書へ集約するのではなく、相互参照可能なVersion、Execution、Result、ArtifactおよびInterpretationとして管理する。

## 4. 対象利用者

### 4.1 主利用者: 分析者

基本的な統計・因果推論の知識を持ち、Python、NotebookまたはCLIで分析を行う利用者。

主な作業:

- 前処理済みデータの登録
- 因果探索
- 複数アルゴリズム・パラメータの比較
- Graph候補の選定・修正
- Causal Designの定義
- ATE/ATT推定
- 推定器・Dataset Version間の比較
- Interpretationの記録

### 4.2 副利用者: レビュー担当者

分析を直接実施していないが、結果の採用可否、再現性または説明可能性を確認する利用者。

主な作業:

- 問いと分析目的の確認
- ResultからDataset、Graph、Algorithm、Parameter、Diagnosticsへの遡及
- Interpretationの根拠、仮定、限界の確認
- 条件付き採用または差戻し判断

### 4.3 運用者

システム運用、権限、Execution障害およびArtifact保全を管理する利用者。初期価値検証の中心利用者ではない。

## 5. 初期対象の利用場面

### 5.1 Golden Path: 売上改善

例:

- クーポン施策は売上を増加させるか
- 店頭施策、価格、来店客数および売上の因果構造候補は何か
- 推定結果はアルゴリズム、パラメータまたはDataset Versionに対して安定しているか

売上改善をGolden Pathとする理由:

- TreatmentとOutcomeを比較的明確に定義できる
- 数値Outcomeを扱いやすい
- 複数探索結果比較からATE/ATT推定までを一貫して検証できる
- 人事・健康領域よりも初期の倫理・法務論点が少ない

### 5.2 Transfer Case: 退職者抑制

追加で検証する論点:

- 予測因子と因果因子の区別
- 介入可能変数と不変属性の区別
- 機微属性の取扱い
- subgroupごとの適用範囲
- 将来のtime-to-event対応の必要性

### 5.3 Transfer Case: 従業員エンゲージメント向上

追加で検証する論点:

- Outcome、Mediator、Confounderの役割区別
- アンケート尺度の解釈
- 上司・部署などの階層性
- 介入可能性と公平性

## 6. 中核となる分析サイクル

```text
Research Context
  ↓
Experimentの目的・分析方針・選定理由
  ↓
Analysis Definition
  ↓
Execution
  ↓
Result / Artifact
  ↓
Comparison / Diagnostics
  ↓
Interpretation / Claim
  ↓
次のResearch ContextまたはExperiment
```

このサイクルは反復される。Research Contextは開始時に完成している必要はない。

## 7. 設計思想

### 7.1 Start loose. Formalize progressively. Conclude strictly.

- 分析者は曖昧なProblem StatementまたはObjectiveから開始してよい。
- Research Question、Hypothesis、Significanceを開始時の一律必須入力にしない。
- 分析の進行に伴ってResearch Contextを精緻化する。
- Interpretationを正式に確定する段階では、問い、根拠、適用範囲、仮定および限界を明示する。

### 7.2 計算来歴ではなく分析来歴を管理する

以下だけでは不十分である。

```text
Dataset → Program → Parameter → Artifact
```

Ariadneが管理すべき来歴は次である。

```text
Research Context
→ Experiment / Analysis Definition
→ Execution
→ Result
→ Interpretation
```

### 7.3 比較を第一級の利用行為として扱う

分析者は単一結果だけで判断しない。Ariadneは次を明示できなければならない。

- 何が同一条件か
- 何を変更したか
- 結果がどう変化したか
- 変更と結果差の対応関係
- 比較対象に共通する上流来歴

### 7.4 因果探索結果を真のDAGと断定しない

- PCおよびGESの出力は、一般に因果DAGそのものではなく同値類を表すGraphとなり得る。
- Algorithm Output Graph、Selected Graph、Edited GraphおよびEstimation Input Graphを区別する。
- Graph選定・方向付け・編集には、人間の判断またはドメイン制約が含まれる。

### 7.5 数値を返せないことを正式な結果として扱う

以下はシステム障害と限らない。

- NOT_IDENTIFIED
- INSUFFICIENT_OVERLAP
- INSUFFICIENT_SAMPLE
- ESTIMATION_UNRELIABLE
- GRAPH_UNCERTAINTY_HIGH

Ariadneは無理にATE/ATTを返さず、推定不能・信頼不能の理由と追加で必要な情報を保存する。

### 7.6 ResultとInterpretationを分離する

- ResultはExecutionによって生成された分析上の結果である。
- ArtifactはResultを構成または裏付ける物理生成物である。
- Interpretation / ClaimはResultを根拠として人間が構成する限定付き回答である。
- Algorithm出力または点推定値を、そのまま業務上の結論として扱わない。

### 7.7 概念と物理エンティティを分離する

```text
概念として必要
≠ 独立Resourceとして必要
≠ 独立テーブルとして必要
≠ 利用者への必須入力として必要
```

豊かな意味論を維持しつつ、初期段階ではVersioned Document、snapshotまたは再生成可能なProjectionを使用する。

### 7.8 Question Treeを初期要件にしない

Project配下のResearch Contextは原則としてフラットに保持する。

理由:

- 分析中に厳密な階層を維持する利用者は限定的と想定される
- 問いの関係は必ずしもTreeではない
- 分解、精緻化、置換、派生、再検証など複数の関係が存在する
- 後から任意Relationを追加し、必要時にTreeまたはGraphとして表示できる

ただし、Research Context間の`DERIVED_FROM`、`REFINES`、`SUPERSEDES`等を任意で記録する余地は残す。

### 7.9 WebとCLIの実行Identityを混同しない

- Web/API実行はAriadne Executionとして管理し、`execution_id`を持つ。
- Local CLIはAriadne Executionを作成せず、Manifest、Artifact、設定hash、code versionおよび必要に応じてMLflow Runで再現性を保持する。
- 同じ科学計算Application Serviceを利用しても、Control Plane上のIdentityは同一ではない。

## 8. 初期プロダクト境界

### 8.1 初期対象

- 前処理済み表形式データ
- Project内の複数Dataset
- Dataset Version固定
- Research ContextとExperimentの関連
- 複数因果探索アルゴリズム
- 同一アルゴリズムのパラメータ感度比較
- Graph候補比較・選定・修正・Version固定
- 二値Treatment
- 連続または二値Outcome
- ATE / ATT
- 複数推定器比較
- Diagnostics
- Dataset Versionを変えた再評価
- 問いからResult・Artifact・Interpretationまでの来歴
- 第三者レビュー

### 8.2 初期対象外

- 連続Treatment
- CATE / HTEの自動探索
- 時系列因果推論
- time-varying treatment / confounding
- 生存時間分析
- IV、DiD、RDD、Synthetic Control
- 自動施策最適化
- 複数施策のpolicy optimization
- Graph不確実性の完全な確率伝播
- Question Treeの常時維持
- AIによる自動的な因果結論確定

## 9. Ariadneが提供すべき価値

### 9.1 分析者への価値

- 複数の探索・推定結果を同一条件／変更条件／結果差分で比較できる
- 上流Resultを下流分析の入力として明示的に再利用できる
- 過去の分析方針と選定理由を確認できる
- 同じ問いを別手法・別パラメータ・別Dataset Versionで再評価できる
- Notebookやファイル名に依存せず、結果の由来を追跡できる

### 9.2 レビュー担当者への価値

- Interpretationから根拠Resultへ遡れる
- Resultから使用Dataset、Graph、Algorithm、ParameterおよびDiagnosticsを確認できる
- 強い因果主張の前提と限界を確認できる
- 分析実施者へ口頭確認しなくても、判断材料を再構成できる

### 9.3 組織への価値

- 分析の再利用
- 再現性と監査可能性
- 結果の比較可能性
- 分析知識の属人化抑制
- 科学的に不適切な結論の抑制

## 10. プロダクト価値の検証仮説

| ID | 仮説 |
|---|---|
| PV-01 | 分析者は曖昧なResearch Contextから分析を開始できる |
| PV-02 | 複数Graphの比較は候補Graph選定に役立つ |
| PV-03 | パラメータ・推定器・Dataset Version差分の同定は分析判断に役立つ |
| PV-04 | 探索Resultから推論へ来歴を保ったまま接続することに価値がある |
| PV-05 | Resultから来歴へ遡ることはNotebook/CLIのみよりレビュー効率を改善する |
| PV-06 | 推定不能・信頼不能を正式な結果として扱うことは過剰な因果主張を抑制する |
| PV-07 | Research Context―Experiment―Result―Interpretationの接続は分析知識の再利用に役立つ |

## 11. 成功の定義

初期検証では、機能数やテーブル数ではなく、次を観察する。

- 利用者がE2Eシナリオを完了できる
- Graph比較・Result比較が実際の選定判断に使用される
- Resultから必要な来歴を第三者が再構成できる
- Interpretationが問いに回答し、根拠、仮定および限界を含む
- 使用されない入力項目・Resource・Projectionを特定できる
- Ariadne利用時にNotebook/CLIのみより比較・再現・レビューが改善する
