## 1. 設計原則

### 1.1 概念と物理実装を分離する

```text
論理Entity
≠ 独立Resource
≠ 独立Table
```

初期物理実装では、Versioned JSON、immutable snapshot、明示FKおよび再生成可能Projectionを組み合わせる。

### 1.2 正本とProjectionを区別する

- 正本: Resource、Version、Execution、Result、Artifact、明示的な関係
- Projection: 比較表、一覧、サマリー、Graph差分、Lineage表示
- Projectionは必要に応じて再生成できることを原則とする

### 1.3 VersionとExecutionを区別する

- Versionは「何を使うか」を固定する
- Executionは「固定した条件で一回処理した事実」を表す
- 技術的retryはExecutionを増やさずAttemptを増やす
- 条件変更再実行は新しいExecutionとする

## 2. 最小論理Entity

### 2.1 Project

**定義**

1つのResearch Topicを扱う分析、権限および来歴の境界。

**主要属性**

- project_id
- name
- topic_summary
- status
- owner / members
- created_at / updated_at

**関係**

- Project 1:N Research Context
- Project 1:N Dataset
- Project 1:N Experiment
- Project 1:N Execution
- Project 1:N Causal Graph
- Project 1:N Interpretation

### 2.2 Research Context

**定義**

分析を行う理由と問いの文脈を表すVersioned Document。

**主要内容**

- problem_statement
- objective
- research_question nullable
- significance nullable
- hypothesis nullable
- status: DRAFT / ACTIVE / SUPERSEDED / CLOSED
- created_by
- created_at
- optional relation:
  - DERIVED_FROM
  - REFINES
  - SUPERSEDES
  - RELATED_TO

**設計判断**

- Question Treeを必須構造としない
- Research ContextはProject配下でフラットに保持する
- relationは任意
- 初期物理実装ではProject内のVersioned JSONでもよい
- Interpretation確定時には、回答対象のResearch Contextを同定する

### 2.3 Dataset

**定義**

業務上同一とみなすデータの論理単位。

**主要属性**

- dataset_id
- project_id
- name
- description
- sensitivity classification
- lifecycle status

### 2.4 Dataset Version

**定義**

Executionで使用するデータ内容を固定した不変Version。

**主要属性**

- dataset_version_id
- dataset_id
- content hash
- schema
- column metadata
- row/column counts
- object references
- created_at
- created_by
- source / preparation notes

**不変条件**

- publishまたは使用開始後に内容を上書きしない
- 同一Executionは特定Dataset Versionを参照する

### 2.5 Experiment

**定義**

1つのResearch Contextに対して、何を比較・検証するかを表す利用者の分析作業単位。

**目的**

- Research Contextと複数Executionを接続する
- 「なぜこの実験方針を選んだか」を保存する
- 複数Algorithm、Parameter、EstimatorまたはDataset Version比較を束ねる

**主要属性**

- experiment_id
- project_id
- primary_research_context_id nullable at draft
- title
- objective
- rationale
- hypothesis nullable
- status
- derived_from_result_ids optional
- created_at / updated_at

**不変条件**

- DRAFT段階ではResearch Context参照を省略可能
- Interpretationを正式化する段階では対象Research Contextへ関連付ける
- ExperimentはExecutionそのものではない

### 2.6 Analysis Definition Version

**定義**

探索または推論で何をどの方法で分析するかを表す不変な分析仕様Version。

**主要内容**

- analysis_definition_version_id
- project_id
- domain: CAUSAL
- operation:
  - DISCOVERY
  - ESTIMATION
  - EDGE_WEIGHT
  - VALIDATION
- input contract
- feature semantics
- method / algorithm candidates
- domain-specific specification
- Causal Design nullable
- canonical JSON
- hash
- status: DRAFT / PUBLISHED / SUPERSEDED

**設計判断**

- Parameter gridを含められる
- 個々のExecutionの正確なParameterはExecution Plan snapshotで固定する
- 同じAnalysis Definition Versionから複数Executionを生成できる

### 2.7 Execution

**定義**

Web/API経路で、固定されたExecution Planに基づいてAriadneが受け付ける一回の処理要求とそのライフサイクル。

**主要属性**

- execution_id
- project_id
- experiment_id
- analysis_definition_version_id
- execution plan snapshot
- dataset_version input
- graph_version input nullable
- algorithm / estimator
- exact parameters
- random seed
- runtime / code version
- status
- requested_by
- timestamps
- mlflow_run_id nullable

**関係**

- Experiment 1:N Execution
- Analysis Definition Version 1:N Execution
- Execution 1:N Result
- Execution 1:N Artifact
- Execution N:M input Result/Artifact through explicit input binding
- Execution 1:N Stage Execution
- Stage Execution 1:N Stage Attempt

**不変条件**

- Algorithm、Parameter、Dataset Version等を変更した利用者再実行は別Execution
- 技術的retryは同じExecution内の新Attempt
- Execution Plan snapshotは変更しない

### 2.8 Result

**定義**

Executionによって得られ、利用者が比較・判断する分析上の論理結果。

**Result Type例**

- DISCOVERY_RESULT
- TREATMENT_EFFECT_RESULT
- EDGE_WEIGHT_RESULT
- IDENTIFICATION_RESULT
- VALIDATION_RESULT
- NOT_IDENTIFIED
- ESTIMATION_UNRELIABLE

**主要属性**

- result_id
- execution_id
- result_type
- status / scientific outcome
- summary
- structured payload
- interpretation level
- diagnostics references
- created_at

**設計判断**

- Execution失敗と科学的な負のResultを区別する
- 複数Algorithmを一括で実行した場合も、比較可能なResult単位を明確にする

### 2.9 Artifact

**定義**

Resultを構成、裏付けまたは再現する物理生成物。

**例**

- edge CSV
- Graph JSON
- Graph画像
- effect table
- diagnostics table
- report Markdown
- manifest
- config snapshot
- log

**主要属性**

- artifact_id
- execution_id
- optional result_id
- artifact type
- location
- checksum
- media type
- size
- lineage metadata

**不変条件**

- APIへlocal absolute pathを正本として露出しない
- ArtifactはResultそのものではない

### 2.10 Causal Graph

**定義**

Project内で継続的に管理される因果Graphの論理Resource。

**主要属性**

- causal_graph_id
- project_id
- name
- purpose
- lifecycle status

### 2.11 Causal Graph Version

**定義**

選定、編集、再利用または推論入力に使用するGraphの不変Version。

**主要属性**

- causal_graph_version_id
- causal_graph_id
- source_result_id nullable
- graph type: DAG / CPDAG / PAG / DIRECTED_WEIGHTED_GRAPH / UNKNOWN
- nodes
- edges
- endpoint semantics
- constraints
- edit rationale
- created_by
- status: DRAFT / PUBLISHED / SUPERSEDED
- hash

**関係**

- Discovery Result 0:N Causal Graph Version
- Causal Graph 1:N Causal Graph Version
- Causal Graph Version 1:N downstream Execution input

**不変条件**

- Algorithm Output Graphと人間が編集したGraphを区別する
- 使用済みVersionを上書きしない

### 2.12 Interpretation / Claim

**定義**

Resultを根拠として人間が構成するResearch Contextへの限定付き回答。

初期UIでは`Interpretation`を推奨名称とし、review・accept等の正式ライフサイクルが必要になった場合に`Claim`へ昇格してもよい。

**主要属性**

- interpretation_id
- project_id
- research_context_id
- statement
- claim type:
  - PREDICTIVE
  - ASSOCIATIONAL
  - MODEL_BEHAVIOR
  - CAUSAL
- scope / population
- assumptions
- uncertainty
- limitations
- status: DRAFT / REVIEWED / SUPERSEDED
- author / reviewer
- timestamps

**Evidence relation**

- Interpretation N:M Result
- 各Evidenceにはsupport / challenge / qualify等のrelation typeを持たせられる

**不変条件**

- InterpretationはResultと同一ではない
- 正式化時には1つ以上のResultを根拠とする
- 正式化時には回答対象Research Contextを持つ

### 2.13 Lineage Relation

**定義**

上流Resource/Version/Result/Artifactが下流Execution、Graph、ResultまたはInterpretationへどのように利用されたかを表す有向関係。

**初期Relation Type**

- USED_DATASET_VERSION
- USED_GRAPH_VERSION
- USED_ANALYSIS_DEFINITION_VERSION
- DERIVED_FROM_RESULT
- DERIVED_FROM_ARTIFACT
- GENERATED_RESULT
- GENERATED_ARTIFACT
- SUPPORTS_INTERPRETATION
- CHALLENGES_INTERPRETATION
- REPRODUCES_EXECUTION

**設計上の制約**

万能な任意型EAVにしない。必要なrelation typeと接続可能なentity typeを限定する。

## 3. Comparisonの扱い

### 3.1 初期判断

Comparisonは初期の正本Entityとしない。

理由:

- 比較は複数Result/Executionを入力とするqueryまたはProjectionとして生成できる
- 独立ライフサイクルがまだ確認されていない
- 保存、共有、承認、コメント等の要件が未検証

### 3.2 初期表現

```text
Comparison Request
  - target IDs
  - comparison type
  - selected dimensions
  - optional baseline ID
  ↓
Comparison Projection
  - common conditions
  - changed conditions
  - result differences
```

### 3.3 Entityへ昇格する条件

以下が実利用で必要になった場合、Comparison Resourceを導入する。

- 比較条件の保存
- 共有URL
- reviewer comment
- approval
- report versioning
- 比較の再現監査

## 4. 論理関係

```text
Project
├── Research Context [0..N]
├── Dataset [0..N]
│   └── Dataset Version [1..N]
├── Experiment [0..N]
│   ├── primary Research Context [0..1 while DRAFT, 1 when formalized]
│   └── Execution [0..N]
│       ├── Analysis Definition Version [1]
│       ├── Dataset Version [1..N; initial analysis stage is normally 1]
│       ├── Graph Version [0..1 for estimation]
│       ├── upstream Result / Artifact [0..N]
│       ├── Result [0..N]
│       └── Artifact [0..N]
├── Causal Graph [0..N]
│   └── Causal Graph Version [1..N]
└── Interpretation [0..N]
    ├── Research Context [1 when formalized]
    └── Evidence Result [1..N when formalized]
```

## 8. Identifier原則

- `project_id`: Project識別子
- `research_context_id`: Research Contextの論理識別子
- `experiment_id`: Experiment識別子
- `analysis_definition_version_id`: 不変分析仕様Version
- `execution_id`: Web/API上のAriadne Execution識別子
- `result_id`: 論理Result識別子
- `artifact_id`: Artifact識別子
- `causal_graph_version_id`: 推論入力に固定するGraph Version
- `interpretation_id`: 人間の解釈識別子
- `mlflow_run_id`: 外部MLflow Run識別子。`execution_id`と同一視しない

CLIはAriadne `execution_id`を生成しない。

## 9. 物理設計へのガイド

### 9.1 独立テーブル化理由が強いもの

- project
- dataset
- dataset_version
- execution
- stage_execution
- stage_attempt
- result
- artifact
- causal_graph
- causal_graph_version
- lineage input binding
- outbox_event（Web非同期実行を維持する場合）

### 9.2 Versioned JSONへ統合可能な候補

- Research Contextの詳細
- Analysis Definition domain-specific specification
- Execution Plan
- Causal Design
- Graph constraint metadata
- Interpretation assumptions / limitations

### 9.3 Projectionまたは再生成候補

- Comparison
- result summary
- Graph difference
- lineage view
- dashboard counts
- frequently used filter aggregates

### 9.4 独立化を保留する候補

- Question Tree
- Comparison Resource
- Adjustment Set Resource
- Parameter Set Resource
- Decision Resource
- Claim approval workflow
- Sensitivity Analysis Resource

## 10. 不変条件

1. 使用済みDataset Version、Analysis Definition VersionおよびGraph Versionを上書きしない
2. Execution Plan snapshotを変更しない
3. Resultは生成元Executionを必ず持つ
4. Artifactは生成元ExecutionまたはResultへ遡れる
5. Estimation Resultは使用Graph Version、Dataset Version、treatment、outcome、estimandを同定できる
6. Interpretationは正式化時にResearch ContextとEvidence Resultを持つ
7. Algorithm/Parameter変更再実行と技術的retryを混同しない
8. Scientific outcomeとExecution technical statusを混同しない
9. Discovery Graphの型とendpoint意味を失わない
10. CLI Runに擬似Ariadne Execution IDを付与しない
