# 10 要件定義

- 文書状態: 討議用ドラフト
- 作成日: 2026-08-05
- 上位文書: `00_プロダクトコンセプトメモ.md`
- 対象: Ariadne 初期プロダクト
- 要件レベル:
  - **MUST**: 初期E2Eシナリオ成立に必要
  - **SHOULD**: 初期検証で有用性を確認する
  - **MAY**: 将来拡張または利用者検証後に判断する

## 1. 適用範囲

Ariadneは、前処理済み表形式データを用いた以下の分析作業を初期対象とする。

- 因果探索
- 因果Graph候補比較
- パラメータ感度比較
- Graph選定・修正
- 二値TreatmentのATE/ATT推定
- 複数推定器比較
- Dataset Versionを変えた再評価
- 問いから結果・Interpretationまでの来歴確認

主対象用途は売上改善とし、退職者抑制および従業員エンゲージメント向上をTransfer Caseとする。

## 2. 利用者と役割

| Actor | 主な責務 |
|---|---|
| Analyst | Dataset登録、分析設計、Execution、比較、Graph選定、Interpretation作成 |
| Reviewer | Result、Diagnostics、Lineage、Interpretationの確認 |
| Project Admin | Project、Member、権限、共有範囲の管理 |
| System Operator | API、Worker、DB、Artifact Store、Queue、監視の運用 |

初期利用価値の主検証対象はAnalystおよびReviewerである。

## 4. 業務シナリオ

### 4.1 シナリオ分類

| 分類 | 意味 |
|---|---|
| E2E | 利用者の業務目的と価値提供可能性を検証するEnd-to-End Scenario |
| AS | E2E内の因果分析工程を検証するAnalysis Scenario |
| CR | 複数のE2E/ASに横断して必要となるCross-cutting Scenario |

「横断シナリオ」は厳密にはE2Eの部分集合ではなく、複数シナリオから再利用される共通能力・共通検証観点である。

### 4.2 E2Eシナリオ

#### E2E-01 探索的分析から候補仮説を形成する

前処理済みDatasetを登録し、複数の因果探索結果とパラメータ感度を比較する。分析者はGraph候補を選定し、次に検証すべき候補仮説またはResearch Questionを記録する。

#### E2E-02 明示した因果仮説を評価する

明示したResearch Questionについて、Graph VersionとCausal Designを定義し、ATE/ATTを複数推定器で推定・比較する。分析者はDiagnosticsを確認し、限定付きInterpretationを記録する。

#### E2E-03 第三者が結果をレビューする

分析に参加していないReviewerが、InterpretationからResult、Execution、Analysis Definition、Graph、Dataset Versionへ遡り、採用可否を判断する。

#### E2E-04 同一の問いを別条件で再評価する

同じResearch Contextについて、Algorithm、Parameter、EstimatorまたはDataset Versionを変更して新しいExecutionを行い、結論の安定性と変更理由を確認する。

### 4.3 分析シナリオ

| ID | シナリオ | 概要 |
|---|---|---|
| AS-01 | 複数探索アルゴリズム比較 | PC、GES、LiNGAM、NOTEARS等のGraph Resultを比較する |
| AS-02 | パラメータ感度比較 | PC alpha等を変更した複数Executionを比較する |
| AS-03 | Graph選定・修正 | 候補Graphを選択し、制約・方向付け・手動修正を行う |
| AS-04 | ATE/ATT推定 | GraphとCausal Designを使用してTreatment Effectを推定する |
| AS-05 | 複数推定器比較 | 同一Causal Designで複数Estimatorを比較する |
| AS-06 | 識別不能・推定不能・信頼不能 | 数値推定を採用できない状態と理由を保存する |
| AS-07 | Dataset Version再評価 | 分析条件を固定し、Dataset Versionを変更して比較する |

AS-04は、Causal Design定義と識別可能性確認を前提とする。識別可能性は独立Stageとして実装するか、AS-04の前処理として実装するかは基本設計で決定する。

### 4.4 横断シナリオ

| ID | シナリオ | 概要 |
|---|---|---|
| CR-01 | 複数Result比較 | 共通条件、変更条件、結果差分を同定する |
| CR-02 | Resultから来歴への遡及 | Resultから上流のDataset、Graph、Definition、Executionへ遡る |
| CR-03 | 上流Resultを下流入力として同定 | Discovery Result等をInference入力として固定する |
| CR-04 | Research ContextからInterpretationまでの追跡 | 問いからExperiment、Execution、Result、Interpretationを追跡する |
| CR-05 | 分析方針の選定理由追跡 | 過去Result等を受けて次のExperimentを選んだ理由を確認する |
| CR-06 | 差分の再現 | 比較画面で確認した差分をmachine-readable形式でexportする |

### 4.5 シナリオ対応表

| E2E | 主に使用するAS | 主に使用するCR |
|---|---|---|
| E2E-01 | AS-01、AS-02、AS-03 | CR-01、CR-02、CR-05 |
| E2E-02 | AS-03、AS-04、AS-05、AS-06 | CR-01、CR-02、CR-03、CR-04 |
| E2E-03 | — | CR-02、CR-04、CR-05、CR-06 |
| E2E-04 | AS-01〜AS-07の任意 | CR-01〜CR-06 |

## 6. 対象アルゴリズム

### 6.1 現行コードで確認できる因果探索

| Algorithm | 位置付け | 初期対象 |
|---|---|---|
| PC | constraint-based。出力はCPDAG等になり得る | MUST |
| GES | score-based。同値類Graphを返し得る | MUST |
| DirectLiNGAM | 線形・非Gaussian等の仮定を持つ | SHOULD |
| linear NOTEARS | 連続最適化ベースのdirected graph探索 | SHOULD |

PCで現行コードが許可する独立性検定:

- Fisher's Z (`fisherz`)
- Kernel Conditional Independence (`kci`)
- Chi-square (`chisq`)
- G-square (`gsq`)

現行コードにはalpha grid感度分析およびbootstrap安定性設定が存在する。

### 6.2 現行コードで確認できる推定方法

| Method | Estimand | 初期対象 |
|---|---|---|
| Difference in means | treated-controlの未調整平均差。ATE/ATTで数値は同一だが、交絡調整された因果効果ではない | 参照値としてMAY |
| OLS coefficient | `outcome ~ treatment + covariates`のtreatment回帰係数。現行コード上のestimand表示は`regression_coefficient` | MUST |
| G-computation | ATE / ATT | MUST |
| IPW | ATE / ATT | MUST |
| AIPW | ATE / ATT | SHOULD |
| Edge-weight regression | Graph edgeごとの探索的係数 | Treatment Effectとは別機能 |

現行の調整変数戦略:

- `pre_treatment_covariates`
- `manual`
- `graph_parents`

現行のrobust standard error:

- none
- HC0
- HC1
- HC2
- HC3

### 6.3 初期対象外の分析方法

- Continuous / multi-valued treatment
- CATE / HTE
- Instrumental Variables
- Difference-in-Differences
- Regression Discontinuity
- Synthetic Control
- Mediation analysis
- Longitudinal causal inference
- Survival causal analysis
- Policy learning

これらは用途検証で必要性が確認された場合に追加する。

## 7. インターフェース要件

### 7.1 基本原則

「すべての機能をWeb App、Web API、CLIへ同一形で提供する」ことは要求しない。

要求するのは次である。

1. 科学計算の中核ロジックはApplication Serviceとして共通化する
2. Web AppはWeb APIを通じて共同作業・比較・レビューを提供する
3. Web APIはResource、Version、ExecutionおよびLineageの正本を提供する
4. CLIはローカル分析、再現性ManifestおよびArtifact生成を提供する
5. Control Plane機能とLocal CLIのIdentityを混同しない

### 7.2 Capability Matrix

| Capability | Web App | Web API | CLI |
|---|---:|---:|---:|
| Project/Member管理 | MUST | MUST | MAY |
| Research Context編集 | MUST | MUST | MAY（file編集/import） |
| Dataset Upload/Version | MUST | MUST | SHOULD（登録またはimport） |
| Discovery実行 | MUST | MUST | MUST |
| Discovery比較 | MUST | MUST | SHOULD（report生成） |
| Graph選定・編集 | MUST | MUST | SHOULD（fileベース） |
| ATE/ATT推定 | MUST | MUST | MUST |
| Estimator比較 | MUST | MUST | SHOULD（report生成） |
| Lineage Review | MUST | MUST | SHOULD（manifest参照） |
| Interpretation作成・review | MUST | MUST | MAY |
| cancel/retry/queue管理 | MUST | MUST | 非該当 |
| Local Manifest | 非該当 | MAY（import） | MUST |

CLIからWeb管理下へ結果を取り込む場合は、CLI Runを既存Ariadne Executionと偽装せず、Import元Identityを明示した別Resourceまたはimport処理として扱う。

|---|---|
| NFR-SEC-001 | Project境界で認可を行う |
| NFR-SEC-002 | cross-project resourceの存在を権限のない利用者へ露出しない |
| NFR-SEC-003 | PII/RESTRICTED列のpreview、analysis、downloadを制御できる |
| NFR-SEC-004 | 人事データでは機微属性の利用目的および制約を記録できる |

### 8.4 監査・観測性

| ID | 要件 |
|---|---|
| NFR-AUD-001 | Resource変更、Execution状態遷移およびreview操作を監査可能にする |
| NFR-OBS-001 | request ID、correlation ID、Execution EventおよびWorker errorを追跡できる |
| NFR-OBS-002 | retryで過去Attemptを上書きしない |

### 8.5 Portability

| ID | 要件 |
|---|---|
| NFR-PORT-001 | Analysis Definition、Manifest、Result summaryおよびLineageをmachine-readable形式でexportできる |
| NFR-PORT-002 | Artifact Storeの物理pathをAPI契約に直接露出しない |

## 9. 受入れ条件の骨格

各E2Eシナリオについて、次を定義する必要がある。

- 被験者へ渡す課題文
- 使用する半人工Dataset
- 正解ではなく観察すべき行動
- 完了条件
- 失敗条件
- 参照されたmetadata
- 不要だったmetadata
- Notebook/CLIへ戻った箇所
- 誤った因果解釈
- 所要時間と介助回数

詳細な検証プロトコルは別成果物とする。
