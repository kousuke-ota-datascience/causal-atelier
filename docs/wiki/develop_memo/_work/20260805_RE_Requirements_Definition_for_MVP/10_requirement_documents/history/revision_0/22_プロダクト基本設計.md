## 3. アーキテクチャ原則

### 3.1 Application Serviceを科学計算の正本とする

Web Worker、CLIおよびPipelineは、同一のDiscovery/Inference Application Serviceを利用する。

Interfaceごとに数値実装を重複させない。

### 3.2 Control PlaneとExecution Planeを分離する

Control Plane:

- Project、Dataset、Version、Experiment、Executionの受付
- 認証・認可
- idempotency
- status、cancel、retry
- Metadata、Lineage、Comparison API

Execution Plane:

- workspace materialization
- Discovery/Inference実行
- Artifact生成
- Result登録
- lease、heartbeat、Attempt
- MLflow logging

### 3.3 WebとCLIのIdentityを分離する

Web/API:

- `execution_id`を受付時に採番
- Queue、RBAC、cancel、retryを管理
- Worker開始時にMLflow Runをensure可能

CLI:

- Ariadne Executionを作成しない
- `execution_id`を生成しない
- Manifest、hash、Artifact、code versionを保存
- MLflow有効時は`mlflow_run_id`を使用
- Webへ取り込む場合はimport元として扱う

### 3.4 MetadataとArtifactを分離する

Metadata DB:

- ID
- Version
- hash
- status
- relation
- summary
- policy
- audit

Artifact Store:

- CSV/Parquet
- Graph JSON/PNG
- report
- diagnostics
- manifest
- config snapshot
- logs

APIはArtifact Storeのlocal absolute pathを返さない。

### 3.5 比較はProjectionとして生成する

初期Comparisonは、複数Result/Executionの入力から生成するquery resultとする。

比較を保存・共有・承認する要件が確認された場合のみResource化する。

## 5. Web App情報設計

### 5.1 主要ナビゲーション

```text
Project
├── Overview
├── Research Contexts
├── Datasets
├── Experiments
├── Executions
├── Graphs
├── Results / Comparisons
└── Interpretations / Review
```

Question Treeを主ナビゲーションにしない。Research Context一覧はフラット表示を基本とし、任意Relationがある場合のみ派生表示を提供する。

### 5.2 Project Overview

表示:

- Project summary
- active Research Context
- recent Experiments
- recent Executions
- latest Results
- unresolved warnings
- recent Interpretations

目的:

- 分析状況の把握
- 次に行う作業への入口
- Execution管理画面への過度な偏重を避ける

### 5.3 Research Context画面

機能:

- Problem Statement / Objective入力
- Research Question / Hypothesisの任意入力
- DRAFT保存
- Context Version履歴
- optional relation追加
- 関連Experiment、Result、Interpretation表示

入力原則:

- 分析開始時に全項目を必須にしない
- Interpretation正式化時に回答対象QuestionまたはObjectiveを要求する

### 5.4 Dataset画面

機能:

- CSV/Parquet upload
- Dataset作成
- Dataset Version作成
- preview / profile
- column type / missing / distribution確認
- column semantics:
  - time role
  - actionable
  - sensitive
  - treatment candidate
  - outcome candidate
  - pre/post-treatment

### 5.5 Experiment Workspace

表示:

- 対象Research Context
- objective
- rationale
- derived from Result/Interpretation
- Analysis Definition
- Execution一覧
- 比較対象選択
- memo

典型例:

```text
Experiment:
PC alpha感度を確認する

Rationale:
alpha=0.01のGraphで主要edgeが少なく、
結論が閾値依存か確認するため

Executions:
- alpha=0.001
- alpha=0.005
- alpha=0.01
- alpha=0.05
```

### 5.6 Discovery Setup画面

入力:

- Dataset Version
- feature set
- algorithm
- algorithm parameters
- background knowledge / constraints
- random seed
- output options

実行形態:

- 単一実行
- Algorithm batch
- Parameter grid

表示上、一括操作とExecution Identityを分離する。一括操作から複数Executionを生成できる。

### 5.7 Discovery Comparison画面

3領域で表示する。

#### 共通条件

- Dataset Version
- feature set
- preprocessing
- seed等

#### 変更条件

- Algorithm
- alpha
- independence test
- score function
- threshold
- background knowledge

#### 結果差分

- node count
- edge count
- edge追加・削除
- endpoint/orientation差分
- stable/unstable edge
- Graph距離
- warning / runtime

PC/GES Resultを一律DAGと表示しない。

### 5.8 Graph Workbench

機能:

- Algorithm Output Graphの参照
- Graph候補の複製
- 必須edge / 禁止edge
- direction edit
- temporal ordering
- edit rationale
- diff preview
- Graph Version publish

表示:

- source Discovery Result
- source Algorithm/Parameter
- edit history
- downstream Inference一覧

### 5.9 Causal Design画面

入力:

- Graph Version
- Dataset Version
- treatment
- outcome
- estimand: ATE / ATT
- target population
- adjustment strategy
- adjustment set
- assumptions
- exclusion criteria

支援:

- Graph parents候補
- pre-treatment covariates
- post-treatment warning
- sensitive/non-actionable variable warning
- no valid adjustment set warning

システムはassumptionを証明したと表示しない。

### 5.10 Identification / Preflight画面

出力:

- IDENTIFIED / NOT_IDENTIFIED / UNDETERMINED
- candidate adjustment set
- open backdoor path
- unobserved confounding warning
- positivity precheck
- sample size precheck
- required additional information

NOT_IDENTIFIEDの場合もResultとして保存できる。

### 5.11 Inference Result画面

表示:

- estimand
- estimate
- standard error
- confidence interval
- estimator
- sample size
- adjustment set
- overlap
- balance
- outcome diagnostics
- warnings
- Graph Version
- Dataset Version
- Execution条件

点推定値をDiagnosticsから切り離して表示しない。

### 5.12 Result Comparison画面

対象:

- Discovery Result
- Treatment Effect Result
- Dataset Version再評価
- Graph Version別推定

共通UI:

```text
Common Conditions
Changed Conditions
Result Differences
Warnings / Diagnostics
Lineage
```

### 5.13 Interpretation / Review画面

入力:

- 回答対象Research Context
- statement
- claim type
- evidence Results
- scope
- assumptions
- uncertainty
- limitations
- next action

Reviewer表示:

- evidence一覧
- Result comparison
- Dataset/Graph/Definition lineage
- unresolved warning
- review comment

初期段階では複雑なapproval workflowを導入せず、DRAFT / REVIEWED / SUPERSEDED程度とする。

## 6. E2E処理フロー

### 6.1 E2E-01 探索的分析から候補仮説形成

```text
1. Projectを選択または作成
2. DRAFT Research Contextを記録
3. DatasetをuploadしDataset Versionを固定
4. Experimentを作成しobjective/rationaleを記録
5. Discovery Analysis Definitionを選択
6. 複数AlgorithmまたはParameter gridを実行
7. Discovery Resultを比較
8. Graph候補を選択・必要に応じて編集
9. Graph Versionをpublish
10. 候補仮説または次のResearch Contextを記録
```

完了条件:

- 複数Resultの比較根拠が残る
- 採用Graph Versionと選定理由が残る
- 次に評価するQuestionまたはHypothesisが残る

### 6.2 E2E-02 明示した因果仮説を評価

```text
1. Research Contextを選択
2. Experimentを作成
3. Dataset VersionとGraph Versionを選択
4. Causal Designを定義
5. Identification / Preflightを実行
6. 複数Estimatorで新しいExecutionを実行
7. ResultとDiagnosticsを比較
8. Interpretationを記録
9. Evidence Resultを関連付ける
```

完了条件:

- treatment/outcome/estimand/populationを同定できる
- Resultから上流Graph/Datasetへ遡れる
- Interpretationに根拠、仮定、範囲、限界がある

### 6.3 E2E-03 第三者レビュー

```text
1. ReviewerがInterpretationを開く
2. 回答対象Research Contextを確認
3. Evidence Resultを確認
4. Result Comparisonを確認
5. Dataset、Graph、Algorithm、Parameterへ遡る
6. Diagnosticsとwarningを確認
7. review結果を記録
```

完了条件:

- 分析者への口頭確認なしに主要根拠を再構成できる
- 不足情報を明示できる
- 強い主張と根拠の不一致を発見できる

### 6.4 E2E-04 同一の問いを別条件で再評価

```text
1. 過去ExperimentまたはExecutionを選択
2. 固定条件を引き継ぐ
3. Algorithm / Parameter / Estimator / Dataset Versionの一部を変更
4. 新しいExecutionを作成
5. 元Resultと比較
6. Interpretationを維持、修正またはsupersede
```

## 7. Web API基本設計

### 7.1 Resource API

初期target例:

- `/projects`
- `/projects/{id}/research-contexts`
- `/datasets`
- `/datasets/{id}/versions`
- `/experiments`
- `/analysis-definitions`
- `/analysis-definition-versions`
- `/executions`
- `/results`
- `/artifacts`
- `/causal-graphs`
- `/causal-graph-versions`
- `/interpretations`

現行APIに存在しないResearch Context、InterpretationおよびComparison endpointは追加候補である。

### 7.2 Action API

例:

- validate/publish Analysis Definition Version
- execute Discovery/Inference
- cancel/retry Execution
- publish Graph Version
- compare Results
- export Manifest/Lineage
- review Interpretation

### 7.3 Comparison API

ComparisonをResource化しない初期案:

```http
POST /api/v1/result-comparisons
```

Request:

- result_ids
- baseline_result_id optional
- dimensions
- output format

Response:

- common_conditions
- changed_conditions
- result_differences
- warnings
- lineage_summary

初期Responseは一時的Projectionであり、comparison_idを必須としない。

### 7.4 Lineage API

最低限必要な方向:

- Result → upstream
- Artifact → upstream
- Graph Version → source Result
- Execution → inputs
- Interpretation → evidence Result
- Research Context → Experiments/Interpretations

### 7.5 Idempotency

Execution作成および主要Resource作成ではIdempotency-Keyを使用可能にする。

同一Project・同一key・同一requestは既存Resourceを返し、異なるrequestで同一keyを再利用した場合はConflictとする。

## 9. Worker基本設計

### 9.1 Stage

初期Stage例:

- DATA_PROFILE
- DISCOVERY
- GRAPH_VALIDATION
- IDENTIFICATION
- INFERENCE
- COMPARISON_EXPORT

Stageを増やすこと自体を目的としない。Identificationを独立Stageにするかは、保存・再利用・失敗扱いの必要性で決定する。

### 9.2 Attempt

Attemptは次を保持する。

- lease
- heartbeat
- workspace
- started/ended time
- error
- resource usage
- worker identity

retry時に過去Attemptを上書きしない。

### 9.3 Result登録

WorkerはStage完了後に以下を原子的に扱う。

1. Artifact保存
2. checksum計算
3. Result登録
4. Lineage登録
5. Result Projection更新
6. Event発行

## 10. Scientific Guardrails

### 10.1 Discovery

- PC/GES ResultをDAGと断定しない
- Graph typeとendpointを表示する
- Algorithm assumptionsを表示する
- stability/sensitivityを確認可能にする

### 10.2 Estimation

- estimandを必須表示
- adjustment setを必須表示
- assumptionsを必須表示
- overlap/balanceを必須表示
- simple differenceを因果効果として自動採用しない

### 10.3 Interpretation

- causal claim typeを他のclaim typeと区別する
- Resultの自動文章化と人間の確定Interpretationを区別する
- unsupported conclusionを警告する
- limitation未記載の場合はformalizeを抑制することを検討する

## 11. 権限基本設計

既存Roleを利用する場合の責務案:

| Role | 権限 |
|---|---|
| VIEWER | Project、Dataset metadata、Result、Interpretation閲覧 |
| ANALYST | Experiment作成、Execution実行、Graph draft、Interpretation draft |
| MAINTAINER | Dataset/Definition/Graph Version publish、retry、review |
| PROJECT_ADMIN | Member・Project設定・削除・権限管理 |

人事データではColumn PolicyとRoleを併用する。

## 12. エラー・負の結果設計

### 12.1 Technical Failure

例:

- worker crash
- dependency unavailable
- invalid configuration
- artifact write failure

表現:

- Execution/Stage status: FAILED
- error code
- retryability
- event/log

### 12.2 Scientific Outcome

例:

- NOT_IDENTIFIED
- INSUFFICIENT_OVERLAP
- ESTIMATION_UNRELIABLE

表現:

- ExecutionはSUCCEEDEDになり得る
- Result scientific outcomeで表現
- 理由、影響範囲、推奨次アクションを保存

この区別は必須である。
