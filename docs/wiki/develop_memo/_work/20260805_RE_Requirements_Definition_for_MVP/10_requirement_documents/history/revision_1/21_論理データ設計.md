# 21 論理データ設計 — 初期縮約版

- 文書状態: 討議用ドラフト
- 作成日: 2026-08-05
- 上位文書:
  - `00_プロダクトコンセプトメモ.md`
  - `10_要件定義.md`
- 目的: 初期Golden Pathを成立させる最小の正本Entityと関係を定義する

## 1. 設計方針

### 1.1 最小化の原則

初期版では、意味論上区別できる概念をすべて独立Entityにしない。

次をExecutionの不変snapshotへ統合する。

- Research Context
- Experiment objective / rationale
- Analysis Definition
- Execution Plan
- Causal Design

次を正本Entityにしない。

- Comparison: 複数Execution / Resultから生成するProjection
- Lineage Relation: 明示参照から導出するView
- Dataset: Dataset Versionの`dataset_key`で論理系列を表現
- Causal Graph: Graph Versionだけで開始
- Claim: 初期版ではAnnotationとして扱う
- Stage Execution / Stage Attempt: 初期版ではExecution内部状態として扱う

### 1.2 初期正本Entity

初期版の正本Entityは次の7つとする。

1. Project
2. Dataset Version
3. Execution
4. Result
5. Artifact
6. Graph Version
7. Annotation

Annotationを後回しにする実装では6EntityでもGolden Pathの計算部分は成立する。ただし、採用理由・仮定・限界を残す価値検証のため、初期論理モデルには含める。

## 2. 全体関係

```text
Project
 ├── Dataset Version
 ├── Execution
 │    ├── input Dataset Version
 │    ├── input Graph Version [optional]
 │    ├── Result
 │    └── Artifact
 ├── Graph Version
 │    └── source Discovery Result
 └── Annotation
      ├── target Result or Graph Version
      └── evidence Result IDs
```

比較と来歴は次から導出する。

```text
Comparison View
  = selected Executions / Results
  + execution snapshots
  + result payloads

Lineage View
  = Result.execution_id
  + Execution.dataset_version_id
  + Execution.input_graph_version_id
  + GraphVersion.source_result_id
  + Artifact.execution_id / result_id
  + Annotation target / evidence references
```

## 3. Entity定義

## 3.1 Project

**定義**

1つの分析テーマと、そのデータ・実行・結果の境界。

**主要属性**

- `project_id`
- `name`
- `topic`
- `objective`
- `memo`
- `status`
- `created_at`
- `updated_at`

**設計判断**

- Research Topicを独立Entityにしない
- Question Treeを保持しない
- Projectの目的・問題意識は自由記述から開始できる

## 3.2 Dataset Version

**定義**

Executionで使用する前処理済みデータ内容を固定した不変Version。

**主要属性**

- `dataset_version_id`
- `project_id`
- `dataset_key`
- `name`
- `version_label`
- `content_hash`
- `schema_json`
- `profile_summary_json`
- `row_count`
- `column_count`
- `artifact_id`
- `source_note`
- `created_at`

**設計判断**

- DatasetとDataset Versionを初期物理モデルでは分離しない
- 同じ`dataset_key`を持つVersion群を同一Dataset系列として表示する
- 登録後の内容を上書きしない

## 3.3 Execution

**定義**

Web/API経路でAriadneが管理する、一つのalgorithm / parameter / estimator条件による一回の処理要求。

**主要属性**

- `execution_id`
- `project_id`
- `batch_key`
- `operation`: `DISCOVERY` / `ESTIMATION`
- `objective_snapshot`
- `rationale_snapshot`
- `dataset_version_id`
- `input_graph_version_id` nullable
- `analysis_spec_json`
- `algorithm_or_estimator`
- `parameter_json`
- `random_seed`
- `code_version`
- `runtime_version_json`
- `snapshot_hash`
- `status`
- `retry_count`
- `last_error_summary` nullable
- `requested_by`
- `requested_at`
- `started_at` nullable
- `finished_at` nullable

**`analysis_spec_json`の例**

Discovery:

- feature set
- graph constraints
- algorithm-specific configuration
- expected output type

Estimation:

- treatment
- outcome
- estimand
- target population
- adjustment set
- assumptions
- inference options

**不変条件**

- submit後のsnapshotを変更しない
- algorithm、parameter、Dataset Version、Graph VersionまたはEstimator変更は新Execution
- `batch_key`は一括操作・比較単位でありExecution Identityではない
- 技術的retryは同じExecutionとして扱う

## 3.4 Result

**定義**

Executionによって生成され、利用者が比較・判断する論理結果。

**主要属性**

- `result_id`
- `execution_id`
- `result_type`
- `scientific_status`
- `summary_json`
- `payload_json`
- `diagnostics_json`
- `warning_json`
- `created_at`

**Result Type例**

- `DISCOVERY_GRAPH_RESULT`
- `TREATMENT_EFFECT_RESULT`
- `IDENTIFICATION_RESULT`

**Scientific Status例**

- `VALID`
- `NOT_IDENTIFIED`
- `INSUFFICIENT_OVERLAP`
- `INSUFFICIENT_SAMPLE`
- `ESTIMATION_UNRELIABLE`

**設計判断**

- Executionの技術的`FAILED`と科学的負結果を区別する
- ResultとArtifactを分離する
- ComparisonはResultの集合から生成する

## 3.5 Artifact

**定義**

Dataset、ExecutionまたはResultを構成・裏付け・再現する物理生成物。

**主要属性**

- `artifact_id`
- `project_id`
- `execution_id` nullable
- `result_id` nullable
- `artifact_type`
- `object_key`
- `content_hash`
- `media_type`
- `size_bytes`
- `metadata_json`
- `created_at`

**Artifact Type例**

- `DATASET_FILE`
- `GRAPH_JSON`
- `GRAPH_IMAGE`
- `EFFECT_TABLE`
- `DIAGNOSTICS_TABLE`
- `MANIFEST`
- `CONFIG_SNAPSHOT`
- `LOG`

**不変条件**

- APIはlocal absolute pathを正本識別子として返さない
- Artifactのhashを検証できる

## 3.6 Graph Version

**定義**

選択・修正・推論入力に使用する因果Graphの不変Version。

**主要属性**

- `graph_version_id`
- `project_id`
- `source_result_id`
- `name`
- `graph_type`
- `graph_json`
- `content_hash`
- `edit_rationale`
- `status`: `DRAFT` / `FIXED`
- `created_at`
- `created_by`

**Graph Type例**

- `DAG`
- `CPDAG`
- `PAG`
- `DIRECTED_GRAPH`
- `MIXED_GRAPH`

**不変条件**

- `FIXED`後の内容を上書きしない
- 修正する場合は新しいGraph Versionを作る
- source Discovery Resultを特定できる
- 推論に使用したGraph VersionをExecutionから特定できる

**設計判断**

- `Causal Graph`親Resourceは初期には作らない
- Project内のGraph一覧はGraph Versionを直接表示する

## 3.7 Annotation

**定義**

ResultまたはGraph Versionに対する、人間の判断・選定理由・仮定・限界を保持する軽量な記録。

**主要属性**

- `annotation_id`
- `project_id`
- `target_type`: `RESULT` / `GRAPH_VERSION`
- `target_id`
- `statement`
- `rationale`
- `assumptions_json`
- `limitations_json`
- `evidence_result_ids_json`
- `created_by`
- `created_at`
- `updated_at`

**設計判断**

- 初期版では正式なClaim Resource、Version、承認状態を持たない
- `evidence_result_ids_json`は初期縮約のための非正規化である
- 複雑な検索・N:M整合性が必要になった場合にassociation Entityへ昇格させる

## 4. 導出モデル

## 4.1 Comparison Projection

Comparisonは正本Entityではない。

**入力**

- `execution_ids[]`または`result_ids[]`

**出力**

```text
common_conditions
changed_conditions
result_differences
warnings
lineage_summary
```

**Discovery差分例**

- algorithm
- alpha等のparameter
- graph type
- edge count
- edge追加・削除
- endpoint / orientation変更
- runtime

**Estimation差分例**

- estimator
- estimator parameter
- estimate
- standard error
- confidence interval
- overlap
- balance
- sample loss
- warning

## 4.2 Lineage View

Lineageは正本Relationテーブルを置かず、明示参照から生成する。

**問い相当の文脈からResultへ**

```text
Project objective
→ Execution objective / rationale snapshot
→ Result
→ Artifact
```

**Graph探索から推論へ**

```text
Discovery Execution
→ Discovery Result
→ Graph Version
→ Estimation Execution
→ Estimation Result
```

**判断から根拠へ**

```text
Annotation
→ target Result / Graph Version
→ evidence Result IDs
→ corresponding Executions
→ Dataset Version / parameters / code version
```

## 5. 状態モデル

### 5.1 Execution

```text
QUEUED → RUNNING → SUCCEEDED
                 ↘ FAILED
                 ↘ CANCELLED
```

Scientific StatusはExecution statusとは別にResultへ保持する。

### 5.2 Graph Version

```text
DRAFT → FIXED
```

`FIXED`後の修正は新Versionを作成する。

## 6. 主な制約

1. Project外Entityを参照してはならない
2. Dataset Version、Execution snapshot、Result、ArtifactおよびFIXED Graph Versionを上書きしない
3. Estimation Executionの`input_graph_version_id`は同一Projectに属すること
4. Graph Versionの`source_result_id`はDiscovery Resultであること
5. Resultは必ず1つのExecutionに属すること
6. ArtifactはProjectに属し、ExecutionまたはResultとの関係を必要に応じて持つこと
7. Annotationのtargetとevidenceは同一Projectに属すること

## 7. 将来Entityへの昇格条件

| 概念 | 独立Entityへ昇格する条件 |
|---|---|
| Dataset | Version系列のライフサイクル、検索、権限を独立管理する必要が生じる |
| Research Context | 複数Executionから再利用、独立レビュー、Version差分、検索が必要になる |
| Experiment | batchを超える目的・状態・共同作業・再利用が必要になる |
| Analysis Definition | 複数Projectまたは多数Executionで仕様を再利用・publishする必要が生じる |
| Claim | evidence N:M、承認、Version、独立URLが必要になる |
| Comparison | 比較状態の保存、共有、コメント、承認が必要になる |
| Lineage Relation | 明示FKでは表せない任意関係の検索・監査が必要になる |
| Stage / Attempt | 複数Stage、lease、heartbeat、resource usageの独立管理が必要になる |
