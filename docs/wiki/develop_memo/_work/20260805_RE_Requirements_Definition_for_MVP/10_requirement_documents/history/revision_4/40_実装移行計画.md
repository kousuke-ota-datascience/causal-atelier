## 1. 目的

本書は、前身コードを全面的に改修するのではなく、因果探索・因果推論の科学計算資産を選択的に流用しつつ、初期価値検証版のProduct Domain、DB、API、WorkerおよびWeb Appを新しい境界で構築するための移行方針を定義する。

移行では、次の二つを同時に満たす。

1. 前身APIまたはCLIを使用する既存clientへの必要な後方互換性を提供する
2. 後方互換性のために、新Product Domain、論理データモデルおよび科学的意味論を歪めない

本計画における最優先事項は、新システムの内部整合性である。後方互換性は、新システム外縁のCompatibility Adapterによって提供し、新Domain Entityや新DB schemaへLegacy固有概念を持ち込まない。

## 2. 前提と基本判断

### 2.1 前提

本計画は次を前提とする。

- 旧Metadata DB内のデータはすべて破棄してよい
- 旧DBから新DBへのrecord移行、ID対応付けおよび履歴変換は行わない
- 初期価値検証では、新DBを空の状態から開始できる
- 後方互換の対象は、保存済みデータではなく、前身のAPI、CLI、設定形式等を利用するclientである
- 初期Artifact StoreはLocal filesystemでよい
- 初期対象は、前処理済み表形式データに対する因果探索と二値TreatmentのATE / ATT推定である
- 後方互換対象は実在するclientまたは運用手順に限定し、推測で互換範囲を拡大しない

### 2.2 採用方式

採用する移行方式は次である。

```text
Scientific Core
  = 前身コードを選択的に流用する

Product Domain / Metadata DB / API / Worker / Web App
  = 新規構築する

Backward Compatibility
  = Compatibility Adapterで新Application Serviceへ変換する

Legacy Control Plane
  = 新規機能を追加せず、切替後に停止・廃止する
```

これは、完全なリライトでも、前身Control Planeのインプレース改修でもない。

### 2.3 移行の優先順位

優先順位は次のとおりとする。

1. 新システムの科学的・ドメイン的整合性
2. 新APIおよび新CLIの明確で自己完結した契約
3. 実在clientに必要な限定的後方互換
4. 前身内部実装との類似性

下位の目的が上位の目的を損なう場合、下位の目的を採用しない。

## 3. 整合性を守るための移行原則

### 3.1 新Product Domainを唯一の正本とする

切替後は、新Product Domainと新DBだけを業務状態の正本とする。

- Legacy ORMを新Application Serviceから参照しない
- Legacy DBを新APIのread sourceにしない
- Legacy statusと新statusを二重管理しない
- Legacy Resourceを新Domain Entityとして復活させない

### 3.2 Compatibility AdapterをAnti-Corruption Layerとする

前身契約との変換は、`interfaces/legacy_compat/`配下だけで行う。

```text
Legacy Client
  → Legacy Compatibility Endpoint / CLI Alias
  → Request Translator
  → New Application Service
  → Response Translator
  → Legacy Client
```

Compatibility Adapterの責務は次である。

- Legacy request fieldを新Commandへ変換する
- Legacy response schemaへ新Query Resultを写像する
- Legacy statusと新statusの明示的mappingを行う
- 変換不能な入力を拒否する
- 非互換差分と廃止予定を警告する

Compatibility Adapterは、業務判断、科学計算、永続化またはtransactionを独自実装しない。

### 3.3 Silent conversionを禁止する

互換変換で意味が確定できない場合、推測で補完しない。

禁止例:

- 不明なLegacy parameterを無視して実行する
- Legacy Graph typeを一律DAGとして扱う
- `NOT_IDENTIFIED`を技術的成功だけに縮約し、科学的状態を隠す
- Legacy statusへ変換できない状態を`SUCCEEDED`として返す
- Legacy ConfigurationからResearch Contextを推定生成する

変換不能時は、明示的なvalidation errorまたはcompatibility errorを返す。

### 3.4 Dual-writeを行わない

新旧DBへのdual-writeは採用しない。

理由:

- 新旧のEntity境界と意味が一致しない
- 整合性確認が二重化する
- Compatibility Adapterが永続化責務を持つことになる
- 新DomainがLegacy schemaへ引き戻される

### 3.5 Legacy IDを新DBの恒久属性にしない

- 新Entity IDは新規採番する
- Legacy requestで返却IDが必要な場合、新IDをLegacy field名へ表示上写像する
- 新DBへ`legacy_id`、`legacy_status`、`legacy_type`等を互換目的だけで追加しない
- client側がLegacy ID形式に強く依存する場合は、Compatibility Adapter内の一時mapping storeを別途検討する

初期価値検証では旧DBデータを移行しないため、過去Legacy IDの検索互換は提供しない。

- 新Web API
- 新Execution Worker

### 4.2 選択的流用領域

次をPort / Adapterを介して選択的に流用する。

- 因果探索Algorithm

## 5. 前身コード資産の流用判定

### 5.1 判定区分

| 判定 | 意味 |
|---|---|
| `REUSE` | public interfaceを固定し、原則そのまま利用する |
| `ADAPT` | Adapterまたは限定的refactorを介して利用する |
| `CHARACTERIZE` | 既存挙動をTestで固定してから利用可否を確定する |
| `DEFER` | 初期価値検証では接続しない |
| `RETIRE` | 新システムから利用せず廃止する |

### 5.2 Scientific Core

| 前身資産 | 判定 | 移行方針 |
|---|---|---|
| `ariadne.causal.discovery.*` | `ADAPT` | DB、Web schema、Execution stateへの依存を持たないScientific Adapterから呼び出す |
| `ariadne.causal.inference.*` | `ADAPT` | Estimatorとdiagnosticsを新Scientific Output契約へ変換する |
| `ariadne.causal.design.schemas` | `CHARACTERIZE` | 新Estimation Analysis Specとの意味差をTestで固定する |
| `ariadne.preprocessing.common.*` | `REUSE`候補 | 純粋関数だけを利用する |
| `ariadne.preprocessing.discovery.*` | `CHARACTERIZE` | 前処理済みデータ入力に必要な処理だけ残す |
| `ariadne.preprocessing.inference.*` | `CHARACTERIZE` | Estimator入力契約に必要な処理だけ残す |
| `ariadne.application.discovery.service` | `ADAPT` | Provider等の依存を分離できる場合のみ利用する |
| `ariadne.application.pipeline.*` | `RETIRE` | 新Golden PathはPipeline Resourceを前提にしない |
| `ariadne.etl.completejourney.*` | `DEFER` | 初期Web/APIの対象外とする |

### 5.3 Infrastructure / Interface

| 前身資産 | 判定 | 移行方針 |
|---|---|---|
| Local Artifact Store | `ADAPT` | 新`ArtifactStorePort`へ適合させる |
| S3 / Azure Blob Adapter | `DEFER` | 初期価値検証では接続しない |
| MLflow Adapter | `DEFER` | Scientific Coreの必須依存にしない |
| Discovery CLI | `ADAPT` | 新Scientific Coreを利用するCLIへ置換し、必要なaliasを提供する |
| Inference CLI | `ADAPT` | 新Analysis Spec / Manifestへ統一する |
| Pipeline CLI | `RETIRE`候補 | 初期Golden Pathでは公開しない |
| Legacy FastAPI Router | `RETIRE` | 新APIを実装し、必要endpointだけCompatibility Adapterを置く |
| Legacy Worker | `RETIRE` | 新Execution状態モデルに合わせて置換する |
| Legacy Frontend | `RETIRE` | 4 Workspaceを新規構築する |

### 5.4 流用時の禁止事項

- 前身ORM Entityを新Product Domainへ渡さない
- Scientific CoreからRepository、API schema、Execution statusを参照しない
- 前身Execution / Stage / Attempt Identityを新Executionへ持ち込まない
- 前身Configuration / Experiment Resourceを互換目的で新DBに復活させない
- Legacy clientの都合で新論理モデルへLegacy固有FKまたはcolumnを追加しない

### 6.2 許可する依存

```text

  → Product Application

  → Scientific / Infrastructure Adapter

  → Product Application
```

### 6.3 禁止する依存

```text
Product Domain
  → Legacy Compatibility Adapter

Product Application
  → Legacy ORM / Legacy Router / Legacy Worker

Scientific Core
  → Product Repository / Web API / ORM

New API
  → Legacy DB
```

### 6.4 Legacy凍結

新規実装開始後、Legacy領域への変更は次に限定する。

- Scientific Coreの明確なbug fix
- Scientific Adapter接続に必要な最小限の依存分離
- Characterization Test追加
- Critical security fix
- Compatibility Adapterの入口として必要なrouting変更

新Golden Path機能をLegacy Domain、Legacy DBまたはLegacy Frontendへ追加しない。

## 7. DB切替計画

### 7.1 方針

旧Metadata DB内データは移行しない。新システムは空の新DBから開始する。

したがって、次を実装しない。

- record変換Importer
- Legacy IDと新IDのmapping
- Execution履歴移行
- Result / Artifact metadata移行
- Graph Version移行
- DB間照合処理
- reverse migration

### 7.2 新DBの構築

- 新しいDatabaseまたは独立schemaを使用する
- 新しいAlembic version tableを使用する
- 新baseline migrationから7 Entityと制約を作成する
- 旧Alembic revisionの続きとして新schemaを作らない
- 新codeからLegacy tableを参照できない接続権限またはschema設定とする

同一PostgreSQL instanceを用いる場合の例:

```text
legacy schema: ariadne_legacy
new schema:    ariadne_product
```

### 7.3 旧DBの扱い

切替前:

- 必要に応じてrollback確認用snapshotを取得する
- Legacy systemが稼働している間だけLegacy DBを利用する

切替後:

- 新API、新Workerおよび新Web AppからLegacy DBへの接続を除去する
- 旧データ保持要件がないため、確認期間終了後にLegacy DBを破棄できる
- 破棄時期は、Golden Path、Scientific differential test、Compatibility contract testおよび新DB backup / restore testの完了後とする

### 7.4 DB切替の受入れ条件

- 空DBから新baseline migrationだけで構築できる
- 新Application TestがLegacy ORMをimportせず成功する
- 新DB userにLegacy schemaのread / write権限がない
- 新API / WorkerのSQL logにLegacy table参照がない
- backup / restore後にGolden Path smoke testが成功する

## 8. 後方互換性の対象とレベル

### 8.1 互換対象

後方互換は次のいずれかに限定する。

- 前身Web APIを呼ぶ実在client
- 前身CLI commandを呼ぶscriptまたは手順
- 前身config fileを使用する自動処理
- 前身Manifestを読む実在tool

次は互換対象外である。

- 旧DB内の過去record
- Legacy内部class / package import path
- Legacy ORM schema
- Legacy Worker内部protocol
- Legacy Frontendの内部状態
- 実在clientが確認できないendpoint

### 8.2 互換レベル

| Level | 内容 |
|---|---|
| `C0` | 互換なし。新契約へ移行する |
| `C1` | 名前・path・command aliasのみ維持し、新契約へ誘導する |
| `C2` | Request / ResponseをCompatibility Adapterで変換する |
| `C3` | side effect、error、status、timingを含めて完全互換とする |

既定は`C0`または`C1`とする。実在clientの停止が困難な場合だけendpoint / command単位で`C2`を採用する。`C3`は新システムの整合性を損なう可能性が高いため原則採用しない。

### 8.3 互換性台帳

互換対象ごとに次を記録する。

| 項目 | 内容 |
|---|---|
| Compatibility ID | 一意な識別子 |
| Client / Owner | 利用clientと責任者 |
| Legacy contract | path、method、command、schema version |
| New contract | 対応する新API / CLI |
| Compatibility level | C0〜C3 |
| Semantic gap | 意味差、情報欠落、非対応条件 |
| Test fixture | Request / Response fixture |
| Deprecation date | 互換終了予定日 |
| Removal condition | 削除条件 |

互換性台帳にないendpointまたはcommandは互換対象としない。

## 9. API後方互換設計

### 9.1 配置

```text
interfaces/legacy_compat/http/
  ├── routers/
  ├── request_translators/
  ├── response_translators/
  ├── status_mapping.py
  └── compatibility_errors.py
```

### 9.2 変換原則

- Legacy requestを新Commandへ一方向変換する
- 新Application Serviceの結果をLegacy responseへ一方向変換する
- Compatibility Adapter内にRepositoryを置かない
- Compatibility AdapterからScientific Coreを直接呼ばない
- Adapter固有の状態を新DBの業務tableへ保存しない
- mappingが情報損失を伴う場合、warning headerまたはresponse metadataで明示する
- 科学的意味を誤って伝える情報損失は許可せず、非互換errorとする

### 9.3 Status mapping

新statusをLegacy statusへ変換する場合、mapping tableを明示する。

例:

| New state | Legacy state | 許可 | 条件 |
|---|---|---:|---|
| `PENDING` | `PENDING` | Yes | 意味が一致する |
| `RUNNING` | `RUNNING` | Yes | 意味が一致する |
| `SUCCEEDED` | `SUCCEEDED` | Yes | Scientific Statusは別fieldまたはwarningで保持できること |
| `FAILED` | `FAILED` | Yes | technical failureに限定する |
| `CANCELLED` | `CANCELLED` | Yes | 意味が一致する |
| `NOT_IDENTIFIED` | `SUCCEEDED` | Conditional | Legacy schemaでScientific Statusを併記できる場合のみ。隠蔽される場合は互換不可 |
| `ESTIMATION_UNRELIABLE` | `SUCCEEDED` | Conditional | warning / scientific statusを欠落させない場合のみ |

注: `NOT_IDENTIFIED`等はExecutionの技術statusではなくResultのScientific Statusである。互換responseがこの区別を表現できない場合、そのendpointはC2対象にしない。

### 9.4 Resource mapping

| Legacy Resource | 新システムでの扱い |
|---|---|
| Project | 新Projectへ変換可能 |
| Dataset / Dataset Version | 新Dataset Versionへ変換。旧親Dataset Resourceは互換responseだけで合成可能 |
| Execution | 新Executionへ変換可能 |
| Result / Artifact | 新Result / Artifactから互換responseを生成可能 |
| Causal Graph / Graph Version | 新Graph Versionから必要なLegacy viewを生成可能 |
| Configuration | 独立Resourceとして作成しない。Execution snapshotへの変換が一意な場合のみ受付可能 |
| Experiment | 新Entityとして作成しない。objective / rationaleへの変換が一意な場合のみ受付可能 |
| Pipeline Definition | 対応概念がないため互換対象外 |
| Stage Execution / Attempt | 対応概念がないため互換対象外 |

### 9.5 Idempotency

Legacy commandにidempotency keyがある場合、新Commandのidempotency機構へ変換する。

Legacy commandにidempotency情報がない場合、Compatibility Adapterが独自に推測生成しない。重複受付の危険があるendpointはC2対象外とするか、client側変更を要求する。

### 9.6 API versionと廃止

- 新APIは正本versionとして公開する
- Legacy pathはCompatibility Adapterだけが提供する
- Legacy responseにDeprecationおよびSunset情報を付与する
- 新機能はLegacy APIへ追加しない
- Compatibility Adapter削除後も新API契約は変更しない

## 10. CLI後方互換設計

### 10.1 実行Identity

CLIとWeb/APIは独立した実行粒度を持ち、識別用IDを共有しない。

- Web/APIはAriadne Executionを作成して`execution_id`を使用する
- CLIはAriadne Executionを作成せず、Manifest、hash、code versionで再現性を保持する

Legacy CLI aliasを残す場合も、この原則を変更しない。

### 10.2 Command互換

| Legacy command | 方針 |
|---|---|
| `ariadne-discovery` | C1またはC2候補。新CLIへaliasし、config変換結果を明示する |
| `ariadne-inference` | C1またはC2候補。新Manifest schemaへ統一する |
| `ariadne-pipeline` | 対応概念がないため廃止する |

### 10.3 Config変換

旧config変換時は次を行う。

- field単位の明示mapping
- 変換不能fieldのerror
- 非推奨fieldのwarning
- 変換後configの書出し
- silent default補完の禁止
- `config_version`、`manifest_version`の明示

### 10.4 CLI互換終了

- alias commandには廃止予定を表示する
- 新CLIへの変換済みconfigを出力可能にする
- 一定期間後、aliasを削除する
- alias削除はScientific Coreや新CLIの内部契約へ影響させない

## 11. 移行Phase

### Phase 0: Baselineと互換対象の固定

**作業**

- 前身code、API endpoint、CLI command、config形式をtagで固定する
- Scientific Characterization Testを実行する
- 実在clientとownerを棚卸しする
- 互換性台帳を作成する
- 旧DBデータを移行しないことを確定する

**完了条件**

- 流用候補の数値挙動が記録されている
- C2対象候補がclient単位で特定されている
- 互換対象外endpointが明示されている

### Phase 1: Scientific Core Adapter

**作業**

- `ScientificCorePort`を定義する
- Discovery / Estimation Adapterを実装する
- Legacy Scientific moduleからDB、ETL、Web、Cloud SDK依存を分離する
- 共通Scientific Outputへ変換する

**完了条件**

- DBなしでDiscovery / Estimationを実行できる
- 主要Estimatorの数値差が許容範囲内である
- Graph serializationがround tripする

### Phase 2: 新Product Domain・新DB

**作業**

- 7 Entityを実装する
- 新Alembic baselineを作成する
- Repository / Unit of Workを実装する
- Comparison / Lineage Queryを実装する

**完了条件**

- 空DBから構築できる
- FK、CHECK、UNIQUE制約Testが成功する
- Legacy ORMをimportせずApplication Testが成功する

### Phase 3: 新API・Worker・CLI

**作業**

- 新Command / Query APIを実装する
- Execution claimとWorker処理を実装する
- Result / Artifact保存とScientific Status変換を実装する
- 新CLIを実装する

**完了条件**

- Dataset登録からResult保存までComponent Testが成功する
- 技術失敗と科学的負結果が分離される
- 新CLIがWeb/APIから独立して実行できる

### Phase 4: 4 Workspace Web App

**作業**

- Project / Data
- Discovery
- Inference
- Results / Lineage

**完了条件**

- E2E-01〜03が新Web Appだけで成立する
- Legacy Frontendを参照せずGolden Pathが完了する

### Phase 5: Compatibility Adapter

**作業**

- 互換性台帳でC2としたendpoint / commandだけAdapterを実装する
- Request / Response / status mappingを実装する
- Deprecation / Sunset通知を実装する
- Compatibility Contract Testを実装する

**完了条件**

- Compatibility Adapterを外しても新APIと新Web Appが完全に動作する
- Legacy固有fieldが新Domain / DBへ追加されていない
- semantic gapがTestと文書で明示されている
- 実在clientのContract Testが成功する

### Phase 6: Cutover

**作業**

- Legacy writeを停止する
- 新DBをbaselineから構築する
- 新API / Worker / Web App / CLIを有効化する
- Compatibility Adapterを有効化する
- Golden Pathと互換clientのsmoke testを実行する

**完了条件**

- 新システムだけで新規データを登録・分析できる
- Legacy DBへのruntime接続がない
- 互換clientが新Application Service経由で動作する

### Phase 7: Legacy廃止と互換縮退

**作業**

- Legacy API / Frontend / Workerを停止する
- Legacy DBを破棄する
- Legacy codeをarchiveまたは削除する
- client移行に応じてC2からC1、C0へ縮退する
- Compatibility Adapterを最終的に削除する

**完了条件**

- 残存Legacy runtime dependencyがScientific Adapterだけである
- 互換性台帳の全項目がC0または削除済みである
- 新Domain / DBにLegacy互換専用属性が存在しない

## 12. CutoverとRollback

### 12.1 Cutover方式

旧DBデータ移行とdual-writeを行わないため、短いmaintenance windowによる一方向切替を採用する。

手順:

1. Legacy code、API契約、CLI fixtureの最終snapshotを取得する
2. Legacy writeを停止する
3. 新DBをbaseline migrationから構築する
4. 新systemを起動する
5. Golden Path smoke testを実行する
6. Compatibility Contract Testを実行する
7. trafficを新APIおよびCompatibility Adapterへ切り替える
8. Legacy API / Workerを停止する

### 12.2 Rollback条件

次の場合はrollbackを判断する。

- 新規Dataset登録またはExecution受付が利用不能
- Scientific Resultがbaselineから許容範囲を超えて乖離
- Artifact hashまたはLineageが復元不能
- Executionが重複claimされる
- Compatibility AdapterがLegacy requestを誤って別の科学的意味へ変換する
- 新DBの制約違反またはdata corruptionが確認される

### 12.3 Rollback方法

初期pilotでは新DBデータも破棄可能であることを前提とし、rollback時は次を行う。

1. trafficを停止する
2. 新systemを停止する
3. 原因を特定する
4. 必要な場合はLegacy systemを再起動する
5. 新DBは破棄またはread-onlyで保存する

新DBからLegacy DBへのreverse migrationは行わない。

### 12.4 Compatibility障害の局所化

新APIが正常でCompatibility Adapterだけが障害の場合、次を優先する。

- 新APIと新Web Appは稼働継続する
- 対象Legacy endpointだけ停止する
- clientへ新API利用を案内する
- 新Domain / DBのrollbackは行わない

Compatibility障害をProduct Core全体の障害として扱わない。

## 13. Test・品質保証

### 13.1 Characterization Test

- Discovery Algorithmの主要出力
- Estimatorの点推定、標準誤差、信頼区間
- Diagnostics
- Graph serialization
- Config hashing
- CLI exit code / Manifest

### 13.2 Differential Test

同一入力・同一条件をScientific Adapterと前身Scientific CLIへ与え、次を比較する。

- Scientific Status
- Graph node / edge / endpoint
- estimate
- confidence interval
- diagnostics summary
- warning

許容差はAlgorithm / Estimatorごとに定義する。

### 13.3 DB Test

- 空DBからのbaseline migration
- FK / CHECK / UNIQUE制約
- backup / restore
- Legacy schemaへの接続禁止
- Legacy ORM非依存

旧DB record移行Testは作成しない。

### 13.4 Compatibility Contract Test

C2対象だけ、Legacy Request / Response fixtureを用いたContract Testを作成する。

Test項目:

- field mapping
- validation error
- status mapping
- idempotency
- scientific statusの欠落防止
- deprecation header
- 新Application Serviceと同一side effectであること

### 13.5 Architecture Test

次の依存禁止を自動Testする。

- `product`から`legacy_compat`へのimport禁止
- `product`からLegacy ORMへのimport禁止
- `scientific_adapter`からProduct Repositoryへのimport禁止
- 新APIからLegacy DB clientへのimport禁止
- Compatibility Adapter内のRepository実装禁止

## 15. Riskと対策

| Risk | 影響 | 対策 |
|---|---|---|
| Compatibility要求が拡大する | 新設計がLegacyへ引き戻される | 実在client、owner、期限がある契約だけC2とする |
| Legacy statusへ科学的状態を表現できない | 誤解を招くresponse | 変換を拒否し、C2対象外とする |
| Legacy parameterを一意に変換できない | 異なる分析が実行される | silent conversionを禁止しvalidation errorとする |
| Adapterにbusiness logicが増える | 二重実装と不整合 | AdapterはtranslationだけとしArchitecture Testで監視する |
| Legacy ID互換がDBへ侵入する | 新Entityが汚染される | Legacy IDを恒久保存せず、必要なら外部mapping storeを期限付きで使用する |
| Scientific moduleがControl Planeへ依存する | Adapter分離が困難 | import dependencyを切り、Characterization Testを先行する |
| Compatibility Adapter障害が全体停止を招く | 新システム利用不能 | 新APIと互換APIを分離し、互換経路だけ停止可能にする |
| 旧DBを残すことで誤参照する | 正本が二重化する | 新DB userからLegacy schema権限を除去し、切替後に破棄する |

## 16. Decision Gate

### Gate 1: Scientific Core再利用可否

次を満たすAlgorithm / Estimatorだけを流用する。

- DBなしで実行可能
- 数値回帰Testが成立する
- Graph semanticsを共通出力へ変換可能

満たさない単位だけを置換し、Scientific Core全体を一括リライトしない。

### Gate 2: C2互換要否

次をすべて確認できる契約だけC2とする。

- 実在client
- client owner
- client変更が困難な理由
- Legacy Request / Response fixture
- 新契約との意味mapping
- 廃止期限
- Compatibility Contract Test

一つでも欠ける場合はC0またはC1とする。

### Gate 3: Cutover可否

次を満たした場合に切替する。

- E2E-01〜03成功
- Scientific differential test成功
- 新DB backup / restore成功
- Architecture Test成功
- C2対象clientのContract Test成功
- rollback smoke test成功

### Gate 4: Legacy DB破棄

次を満たした場合に旧DBを破棄する。

- 新システム切替後の確認期間が完了
- Legacy DBへのruntime接続が0
- 旧データ保持要件がないことを再確認
- 新DBのbackup / restoreが確認済み

### Gate 5: Compatibility Adapter削除

次を満たした契約から順に削除する。

- clientが新契約へ移行済み
- deprecation期間が終了
- trafficが0
- ownerが削除を承認
- 新APIのContract Testに影響しない

## 17. 完了条件

実装移行は次を満たした時点で完了とする。

1. 初期Golden Pathが新Web App / API / Worker / DBだけで完了する
2. Scientific CoreはPort / Adapter境界を介して呼び出される
3. 新Product DomainがLegacy ORM、Router、Worker、DBへ依存しない
4. 新7 Entity以外のLegacy Entityを正本として参照しない
5. 新DBは空状態から独立baseline migrationで再構築できる
6. 旧DBデータの移行コードが存在しない
7. C2互換は互換性台帳に登録された契約だけに限定される
8. Compatibility Adapterを外しても新システムが完全に動作する
9. Legacy固有属性が新Domain / DBに存在しない
10. Legacy API、Frontend、WorkerおよびDBが停止・廃止される
11. Scientific Regression、API Contract、Compatibility Contract、E2E、DBおよびArchitecture Testが成功する
12. Compatibility Adapterに明示的な廃止期限と削除条件がある
