## 1. 設計対象と責務

### 1.1 対象コンポーネント

| コンポーネント | 存在目的 | 主な責務 | 主な対象外 |
|---|---|---|---|
| Web App | Analyst / Viewerが分析作業と結果確認を行うUIを提供する | 入力支援、Workspace遷移、Graph可視化、Comparison表示、Lineage表示、Annotation編集 | 数値計算、正本データの直接更新、長時間処理 |
| Web API | Web系機能の正本Control Planeを提供する | validation、認可、Entity CRUD、Execution受付、status取得、Comparison / Lineage Query、Artifact参照 | Scientific Coreの数値実装、長時間計算の同期実行 |
| 非同期Execution Worker | Web requestから長時間計算を分離し、受付済みExecutionを確実に処理する | QUEUED Executionのclaim、入力解決、Scientific Core呼出し、Result / Artifact保存、status更新、技術エラー記録 | UI、分析条件の決定、科学的結論の作成 |
| Metadata DB | 分析来歴と実行状態の正本を保持する | Project、Dataset Version、Execution、Result、Graph Version、Annotation、Artifact metadataの永続化、参照整合性 | 大容量ファイル本体の保存、数値計算 |
| Artifact Store | 大容量・ファイル形式の生成物を保存する | Dataset file、Graph JSON / image、table、manifest、logの保存、hash検証、download提供 | Entity関係やstatusの正本管理 |
| Scientific Core | 因果探索・因果推論の再利用可能な科学計算能力を提供する | Discovery、Graph utilities、Identification / preflight、Treatment Effect Estimation、Diagnostics、構造化Result生成 | Web/API/DBへの依存、Execution status管理、Artifact所在の決定 |
| Local CLI | Scientific Coreをローカルで直接利用する | config validation、Discovery / Estimation実行、local Result / Artifact / manifest生成、optional tracking連携 | Web Project管理、Web Execution ID、Comparison UI、Queue管理 |

### 1.2 Workerを非同期化する理由

因果探索・因果推論は、Web requestの許容時間を超える可能性があり、複数条件の一括実行では処理時間がさらに増える。Workerは次を実現するために設ける。

- Web Appを計算完了までblockしない
- Executionごとにstatusを追跡する
- 技術例外を他のExecutionから隔離する
- ResultおよびArtifact保存を一貫した処理として行う
- cancelおよび技術的retryの制御点を設ける

### 1.3 初期対象外

- Research Context / Experiment / Analysis Definition専用モジュール
- 汎用Workflow / Pipeline Designer
- Stage / Attemptの詳細管理UI
- 独立Comparison Resource
- 独立Lineage Relation Store
- 承認Workflow
- 詳細監査UI
- 複数Artifact Storeの同時サポート
- 高可用性・マルチテナント構成

## 3. アーキテクチャ原則

### 3.1 プロダクト層とScientific Coreを分離する

Scientific CoreはWeb、WorkerおよびCLIから再利用する。

- 数値実装をinterfaceごとに複製しない
- Metadata DBやWeb frameworkへの依存をScientific Coreへ持ち込まない
- optional external adapterをcore import時に必須としない

### 3.2 単純なExecutionモデルを使う

- 1 algorithm / parameter / estimator条件 = 1 Execution
- 複数条件は`batch_key`で束ねる
- WorkerはExecution単位で処理する
- 初期版ではStage / Attempt Entityを作らない
- retry回数とerror summaryはExecutionに保持する

### 3.3 Snapshotを正本とする

Execution submit時に、次をcanonical JSONとして固定する。

- objective / rationale
- Dataset Version
- Graph Version
- analysis specification
- algorithm / estimator
- parameters
- random seed
- code / runtime version

Execution後に元フォームを変更しても、過去Executionのsnapshotは変えない。

### 3.4 ComparisonとLineageはQuery Modelとする

ComparisonおよびLineageを独立CRUDモジュールにしない。

- Comparison APIは選択されたExecution / Resultから差分を生成する
- Lineage APIは明示FKを辿って表示用graphを生成する

### 3.5 Web/APIとCLIの実行Identityを分離する

Web/API経路は、Ariadne管理下の非同期処理要求として`execution_id`を持ち、Queue、status、cancelおよびretryを管理する。

CLI経路はWeb/APIと独立した実行粒度を持ち、Ariadne `execution_id`を生成しない。再現性はmanifest、hash、code version、ResultおよびArtifactで保持する。

## 6. 画面遷移とDTO設計

### 6.1 DTOの役割

画面間ではEntity object全体を直接引き渡さず、安定した識別子と必要最小限のUI contextだけをDTOで渡す。受信画面は識別子を用いてWeb APIから正本情報を再取得する。

DTOを次の4種類に分ける。

| DTO種別 | 用途 |
|---|---|
| Navigation Context DTO | Workspace遷移時にProject、Dataset、Graph、Result等のIDを渡す |
| Command DTO | 作成、実行、固定、Annotation更新等の変更要求をAPIへ渡す |
| Query / Response DTO | Workspace表示、Comparison、Lineage等の読取結果を返す |
| Scientific Core DTO | WorkerとScientific Core間で計算入力・出力を受け渡す |

### 6.2 画面遷移一覧

| 遷移元 | 遷移先 | 契機 | 引き渡すDTO | 受信画面の処理 |
|---|---|---|---|---|
| Project / Data | Discovery | Dataset Versionを選択して探索開始 | `DiscoveryStartContextDTO` | Dataset metadataを取得し、探索フォームを初期化する |
| Discovery | Inference | Graph Versionを固定して推論開始 | `InferenceStartContextDTO` | Dataset、Graphおよびsource Resultを取得し、Causal Designを初期化する |
| Discovery | Results / Lineage | Discovery Resultを比較・確認 | `ResultSelectionContextDTO` | ResultとExecution Snapshotを取得し、Comparisonを生成する |
| Inference | Results / Lineage | Estimation Resultを比較・確認 | `ResultSelectionContextDTO` | Result、diagnosticsおよびLineageを取得する |
| Results / Lineage | Discovery | 探索条件を変更して再実行 | `RerunStartContextDTO` | source Executionからprefill情報を取得し、新規フォームとして表示する |
| Results / Lineage | Inference | 推定条件を変更して再実行 | `RerunStartContextDTO` | source Executionからprefill情報を取得し、新規フォームとして表示する |

### 6.3 Navigation Context DTO

#### 6.3.1 `DiscoveryStartContextDTO`

```text
project_id: UUID
selected_dataset_version_id: UUID
source_execution_id: UUID | null
```

#### 6.3.2 `InferenceStartContextDTO`

```text
project_id: UUID
dataset_version_id: UUID
graph_version_id: UUID
source_discovery_result_id: UUID
```

`source_discovery_result_id`は画面表示用の補助情報であり、正本関係はGraph Versionから再取得する。

#### 6.3.3 `ResultSelectionContextDTO`

```text
project_id: UUID
result_ids: UUID[]
comparison_mode: DISCOVERY | ESTIMATION
return_workspace: DISCOVERY | INFERENCE | RESULTS
```

#### 6.3.4 `RerunStartContextDTO`

```text
project_id: UUID
source_execution_id: UUID
target_workspace: DISCOVERY | INFERENCE
```

再実行時のparameterや分析仕様はDTOへ複製せず、`source_execution_id`からAPIでprefill用Response DTOを取得する。

## 8. Worker基本設計

### 8.1 受付から完了までの責務

WorkerはExecutionを1件ずつ処理する。

```text
QUEUED
→ claim
→ 入力EntityとArtifactの解決
→ Snapshot hashの検証
→ RUNNING
→ Scientific Core実行
→ Artifact保存
→ Result保存
→ SUCCEEDED
```

Workerの主な責務は次のとおりである。

1. 同じExecutionが同時に複数Workerで実行されないようclaimする
2. Dataset Version、Graph VersionおよびArtifactを解決する
3. EntityをScientific Core Input DTOへ変換する
4. Scientific CoreのResult DTOをResult / Artifactへ変換する
5. 技術例外を捕捉し、log Artifactとerror summaryを保存する
6. Execution statusとtimestampsを更新する
7. cancel要求を安全な境界で反映する

### 8.2 技術例外と科学的負結果

技術例外時:

```text
RUNNING
→ error summary / log Artifact保存
→ FAILED
```

Scientific Coreが`NOT_IDENTIFIED`等を返した場合:

```text
RUNNING
→ Result(scientific_status=NOT_IDENTIFIED)保存
→ SUCCEEDED
```

### 8.3 Queue

初期版ではDB-backed queueを基本とする。

- `execution.status=QUEUED`をWorkerがrow lockまたはclaim tokenで取得する
- Transactional Outbox、lease、heartbeatの完全モデルは初期必須にしない
- Worker停止後のstale `RUNNING`回復はOperator手順または単純なtimeout判定から開始する

## 9. Scientific Core Interface

### 9.1 Discovery

```text

  dataset_ref,

  constraints,
  seed
```

```text
  dataset_ref,
```

`EstimationResultDTO`は少なくとも次を返す。

- scientific status

- uncertainty
- diagnostics

## 13. 初期テスト戦略

- synthetic dataによるDiscovery妥当性

- Batch Commandから複数Executionが生成される
- Snapshotが不変である
- Graph Versionがsource Resultを保持する
- Estimationがinput Graph Versionを保持する
- Comparisonが共通・変更・結果差分を生成する
- LineageがDiscoveryからEstimationまで復元できる
- Navigation Context DTOがID以外の正本情報を保持しない
