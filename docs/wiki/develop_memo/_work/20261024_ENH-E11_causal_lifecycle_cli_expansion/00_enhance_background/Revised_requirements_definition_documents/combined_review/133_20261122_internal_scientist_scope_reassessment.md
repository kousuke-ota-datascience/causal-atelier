## 1. Governing filter

A requirement or derived design obligation is in E11 only if it (a) directly provides a selected causal Method/Estimand/identification/inference/diagnostic, or (b) is needed for correct execution, reproducible evidence, safe local data handling and the non-regression of **already implemented Product**, or (c) is explicitly accepted as a current, bounded user workflow. A speculative future external customer/recipient, shared-workspace, provider-independent data-distribution product, independent authority, or multi-tenant service does not satisfy this filter.

Scientific acceptance is a **hard boundary**, not an overengineering candidate merely because quantitative tests are labor-intensive. All 41 approved methods, 68 scope dispositions, independent DGP/NEG/REF, Method-specific inference/negative-state, NFR-035/AR-044, FWER decisions and v2 backward compatibility remain.

## 4. Explicitly KEEP / no speculative user-product expansion

- FR-186–194, FR-196–203, NFR-029/030/031/032/033/035/036, AR-028–044 and selected 41 Method semantics/quantitative independent verification. FR-195 requires usable individual HTE results and safe local output, not independent corporate release approval.
- Distinguish identification, Estimator eligibility, point, interval/inference, scientific acceptance and technical run status; do not label exploratory effect confirmed.
- Real backend/libraries/seed/lock/inputs and independent validation; selected Method must have actual external backend where applicable, no hidden fallback.
- Local path traversal/symlink protection, output ownership/privacy, fail-closed row export, no sensitive values in log/aggregate output, no false-success partial save, no clobber of committed runs.
- Legacy Product Web/API/Worker/DB and Project role contracts remain **existing** features. Scope explicitly excludes E11 new Product integration, multi-tenant RBAC, managed customer Release and unspecified services.
