## 1. 文書の設計粒度

本書は、利用者・画面・システムコンポーネント間の責務と、相互に受け渡す**論理情報**を定義する。

本書では次を確定しない。

- DTOクラス名と全フィールド
- JSON Schema、serialization形式
- Web APIのEndpoint一覧
- validation ruleとerror code
- package、class、repositoryの物理構成
- transaction境界と例外処理の実装方法

これらは、それぞれ`23_API・インターフェース設計.md`および`30_詳細設計.md`で定義する。

## 2. 設計対象と責務

### 2.1 対象コンポーネント

| コンポーネント | 存在目的 | 主な責務 | 主な対象外 |
|---|---|---|---|
| Web App | Analyst / Viewerが分析作業と結果確認を行うUIを提供する | 入力支援、Workspace遷移、Graph可視化、Comparison表示、Lineage表示、Annotation編集 | 数値計算、正本データの直接更新、長時間処理 |
| Web API | Web系機能の正本Control Planeを提供する | validation、認可、Entity操作、Execution受付、status取得、Comparison / Lineage照会、Artifact参照 | Scientific Coreの数値実装、長時間計算の同期実行 |
| 非同期Execution Worker | Web requestから長時間計算を分離し、受付済みExecutionを処理する | Executionの取得、入力解決、Scientific Core呼出し、Result / Artifact保存、status更新、技術エラー記録 | UI、分析条件の決定、科学的結論の作成 |
| Metadata DB | 分析来歴と実行状態の正本を保持する | 7つの正本Entityの永続化、参照整合性、状態管理 | 大容量ファイル本体の保存、数値計算 |
| Artifact Store | Datasetおよび生成物の物理ファイルを保存する | Dataset file、Graph、table、manifest、logの保存、hash検証、取得 | Entity関係やstatusの正本管理 |
| Scientific Core | 因果探索・因果推論の再利用可能な科学計算能力を提供する | Discovery、Graph utilities、Identification / preflight、Treatment Effect Estimation、Diagnostics、構造化Result生成 | Web/API/DBへの依存、Execution status管理、Artifact所在の決定 |
| Local CLI | Scientific Coreをローカルで直接利用する | 設定検証、Discovery / Estimation実行、local Result / Artifact / manifest生成 | Web Project管理、Web Execution Identity、Comparison UI、Queue管理 |

### 2.2 Workerを設ける理由

因果探索・因果推論は、Web requestの許容時間を超える可能性がある。複数条件の一括実行では処理時間がさらに増える。Workerは次を実現するために設ける。

- Web Appを計算完了までblockしない
- Executionごとにstatusを追跡する
- 技術例外を他のExecutionから隔離する
- ResultおよびArtifact保存を一貫した処理として行う
- cancelおよび技術的retryの制御点を設ける

### 2.3 初期対象外

- Research Context / Experiment / Analysis Definition専用モジュール
- 汎用Workflow / Pipeline Designer
- Stage / Attemptの詳細管理
- 独立Comparison Resource
- 独立Lineage Relation Store
- 承認Workflow
- 詳細監査UI
- 複数Artifact Storeの同時サポート
- 高可用性・マルチテナント構成

## 3. システム構成

### 3.1 Web構成

初期版はモジュラーモノリスを基本とする。

```text
Analyst / Viewer
      |
      v
   Web App
      |
      v
   Web API
   |      |       \
   |      |        \--> Artifact Store
   |      +-----------> Metadata DB
   |
   +--> Execution Worker
              |
              v
       Scientific Core
       ├── Discovery
       ├── Graph utilities
       ├── Identification / preflight
       ├── Treatment Effect Estimation
       └── Diagnostics
```

Web APIとWorkerは同一アプリケーションコードを共有してよいが、実行プロセスと責務を分離する。

### 3.2 Local CLI構成

```text
Local CLI
  ├── Scientific Core
  ├── local manifest
  ├── local Artifact
  └── experiment tracking adapter [optional]
```

CLIとWeb/APIは科学計算能力を共有するが、実行IdentityとControl Planeを共有しない。

## 4. アーキテクチャ原則

### 4.1 Product層とScientific Coreを分離する

- 数値実装をinterfaceごとに複製しない
- Metadata DBやWeb frameworkへの依存をScientific Coreへ持ち込まない
- optional external adapterをcore import時に必須としない
- Scientific Coreは構造化された入力を受け、構造化された科学結果を返す

### 4.2 単純なExecutionモデルを使う

- 1 algorithm / parameter / estimator条件 = 1 Execution
- 複数条件は`batch_key`で束ねる
- WorkerはExecution単位で処理する
- 初期版ではStage / Attempt Entityを作らない
- 技術的retry情報はExecutionに保持する

### 4.3 Execution Snapshotを正本とする

Execution受付時に次の論理情報を固定し、実行後に上書きしない。

- objective / rationale
- Dataset Version
- Graph Version
- analysis specification
- algorithm / estimator
- parameters
- random seed
- code / runtime version

### 4.4 ComparisonとLineageはQuery Modelとする

- Comparisonは選択されたExecution / Resultから都度導出する
- Lineageは論理データ設計上の明示参照を辿って導出する
- 初期版ではComparisonやLineageを独立CRUD対象にしない

### 4.5 Web/APIとCLIの実行Identityを分離する

Web/API経路は、Ariadne管理下の非同期処理要求として`execution_id`を持つ。CLI経路は独立した実行粒度を持ち、Web/APIの識別子を共有しない。

## 5. プロダクトモジュール

### 5.1 利用者向けWorkspace

| Workspace | 主な責務 |
|---|---|
| Project / Data Workspace | Project目的、Dataset Version登録・確認、最近の分析 |
| Discovery Workspace | 条件設定、一括実行、Graph比較、Graph選定・簡易修正 |
| Inference Workspace | Causal Design、preflight、複数Estimator実行、diagnostics比較 |
| Results / Lineage Workspace | Result比較、判断メモ、来歴、Artifact、read-only共有 |

### 5.2 論理Application Service

| Service | 主な責務 |
|---|---|
| Project Data Service | ProjectとDataset Versionの登録・照会 |
| Execution Service | 複数Executionの受付、状態照会、cancel、retry |
| Graph Version Service | Discovery ResultからGraph Versionを作成・固定する |
| Comparison Query Service | Execution SnapshotとResultから比較表示を生成する |
| Lineage Query Service | 明示参照からLineage表示を生成する |
| Annotation Service | Result / Graph Versionへの判断メモを管理する |
| Artifact Service | Artifact metadata、保存、取得、hash検証を仲介する |
| Scientific Core Adapter | Product層とScientific Core間の論理変換を行う |

Serviceのclass、method、repository依存は`30_詳細設計.md`で定義する。

## 6. Web App情報設計

### 6.1 主要ナビゲーション

```text
Project
├── Data
├── Discovery
├── Inference
└── Results
```

Execution、Graph Version、Artifactは主要ナビゲーションに出さず、各Workspaceの内部情報として表示する。

### 6.2 Project / Data Workspace

#### 6.2.1 目的

分析テーマと使用可能なDataset Versionを確認し、次の分析へ進む。

#### 6.2.2 表示

- Project name
- topic / objective / memo
- Dataset Version一覧
- dataset key / version label
- row / column count
- content hash
- 最近のDiscovery / Inference実行群

#### 6.2.3 操作

- Project作成・編集
- CSV / Parquet upload
- Dataset preview
- Dataset Version選択
- Discovery開始

### 6.3 Discovery Workspace

#### 6.3.1 目的

複数のDiscovery Executionを実行・比較し、Algorithm Output、Constraint AdjustedおよびUser Edited Graphを区別して採用Graph Versionを固定する。

#### 6.3.2 画面構成

- Dataset / Feature Set
- Algorithm / Parameter Variants
- Background Knowledge / Constraint
- Execution一覧
- Graph比較
- Graph Provenance
- Graph Version作成・編集・固定

#### 6.3.3 表示項目

- Graph Type
- Graph Origin
- Source Backend / Version
- Constraint Mode
- Parent Graph Version
- Unresolved Orientation
- Latent Confounding Warning
- Bootstrap / Algorithm Agreement

#### 6.3.4 制約

- Post-hoc Constraint適用GraphをAlgorithmの直接出力と表示しない
- CPDAG / PAGをDAGとして表示しない
- User-defined / Imported Graphの直接登録を許可する
- FIXED後の編集は新Graph Versionとする
### 6.4 Inference Workspace

#### 6.4.1 目的

Causal Question、Causal Design、Identification、Data Eligibility、Estimation、Diagnostics、RefutationおよびSensitivityを段階的に実行・確認する。

#### 6.4.2 画面構成

```text
1. Research Context / Causal Question / Causal Design
2. Identification / Data Eligibility
3. Estimation / Diagnostics
4. Refutation / Sensitivity
```

#### 6.4.3 Identification操作

- FIXED Graph Version選択
- Causal Question / Design入力
- Identification Strategy選択
- Identification Execution作成
- Identification Status、Adjustment Set候補、Assumption、非識別理由表示

#### 6.4.4 Data Eligibility表示

- `PASS / WARN / FAIL`
- Check Code、Message、Evidence
- Missingness、Sample Size、Treatment Prevalence
- Post-treatment、Overlap、Extreme Weight Risk

#### 6.4.5 Estimation Gate

- `NOT_IDENTIFIED`の場合、通常Estimation操作を無効化する
- Data Eligibility `FAIL`の場合、Estimation操作を無効化する
- `WARN`の場合、Override ReasonとActorを必須入力とする
- Estimator Capabilityとの互換性を表示する

#### 6.4.6 Estimation・Diagnostics

- 同一Identification Resultを複数Estimatorで再利用する
- Treatment EffectとDiagnosticsを別Resultとして表示する
- Diagnostics `FAIL`でもExecutionの技術成功を許容する

#### 6.4.7 Refutation・Sensitivity

- Placebo Treatment
- Data Subset
- Adjustment Set Variation
- Propensity Clipping Variation

RefutationまたはSensitivityを仮定の証明として表示しない。
### 6.5 Results / Lineage Workspace

#### 6.5.1 目的

科学段階ごとのResultを比較し、上流条件、Graph Provenance、ArtifactおよびAnnotationを確認する。

#### 6.5.2 表示

- Result Type
- Scientific Status
- Common / Changed Conditions
- Upstream Result
- Dataset / Graph
- Graph Origin
- Snapshot Hash
- Override Reason
- Artifact
- Annotation

#### 6.5.3 Comparison

同一Project、同一Result Type、同一Estimand、同一Outcome Scale、同一Population定義のResultのみ数値比較する。

#### 6.5.4 Lineage

```text
Result
→ Execution
→ Input Result Chain
→ Dataset Version
→ Graph Version
→ Graph Source / Parent
→ Artifact
→ Annotation
```
## 7. 画面遷移と論理引渡し情報

### 7.1 設計方針

画面間ではEntity全体を保持せず、識別子と遷移に必要な最小contextを引き渡す。遷移先は識別子を用いてWeb APIから正本情報を再取得する。

型、必須性、JSON表現およびDTO名は`23_API・インターフェース設計.md`で定義する。

### 7.2 遷移一覧

| 遷移元 | 遷移先 | 契機 | 引き渡す論理情報 | 遷移先の責務 |
|---|---|---|---|---|
| Project / Data | Discovery | Dataset Versionを選択して探索開始 | Project、Dataset Version、任意の元Execution | Dataset metadataを取得し、探索条件を初期化する |
| Discovery | Inference | Graph Versionを固定して推論開始 | Project、Dataset Version、Graph Version、source Discovery Result | Dataset、Graph、source Resultを取得し、Causal Designを初期化する |
| Discovery | Results / Lineage | Discovery Resultを比較する | Project、Result集合、比較種別 | ResultとExecution Snapshotを取得し、比較表示を生成する |
| Inference | Results / Lineage | Estimation Resultを比較する | Project、Result集合、比較種別 | Result、diagnostics、Lineageを取得する |
| Results / Lineage | Discovery | 探索条件を変更して再実行 | Project、元Execution、遷移先種別 | 元Executionから初期値を取得し、新規実行フォームとして表示する |
| Results / Lineage | Inference | 推定条件を変更して再実行 | Project、元Execution、遷移先種別 | 元Executionから初期値を取得し、新規実行フォームとして表示する |

## 8. Worker基本設計

### 8.1 論理処理

```text
QUEUED
→ Execution取得
→ Dataset解決
→ Graph解決
→ Upstream Result解決
→ Snapshot Hash検証
→ Operation別Input構築
→ Scientific Core実行
→ Result群構築
→ Artifact保存
→ Result・Artifact・Execution StatusをTransaction確定
→ SUCCEEDED
```

### 8.2 Operation Dispatch

Workerは次を明示Dispatchする。

- DISCOVERY
- IDENTIFICATION
- ESTIMATION
- REFUTATION
- SENSITIVITY

曖昧な`else=ESTIMATION`分岐を使用しない。

### 8.3 技術失敗と科学的負結果

- Infrastructure / Adapter例外: `FAILED`
- Scientific Negative Outcome: Result保存後`SUCCEEDED`
- `NOT_IDENTIFIED`、Eligibility `FAIL`、Refutation `FAILURE_DETECTED`、Sensitivity `FRAGILE`を技術失敗に変換しない

### 8.4 Queueの初期方針

PostgreSQLの`FOR UPDATE SKIP LOCKED`等で短いClaim Transactionを構成する。

Stage / Attempt Entityは追加しない。
## 9. Scientific Core基本設計

### 9.1 共通境界

Scientific CoreはProduct Domain、DB Repository、Web API SchemaおよびArtifact最終保存先を参照しない。

### 9.2 Discovery能力

- PC / GES等の探索
- DAG / CPDAG / PAG表現
- Constraint入力またはPost-hoc変換の区別
- Provenance / Warning / Backend Version出力

### 9.3 Identification能力

ENH-E1の必須Strategy:

- RANDOMIZED
- BACKDOOR

出力:

- Identification Status
- Identified Estimand
- Adjustment Set候補
- Assumptions
- Explanation
- Non-identification Reason

CPDAG / PAGで一意判断できない場合は`REQUIRES_REVIEW`とする。

### 9.4 Data Eligibility能力

- Schema / Column Validation
- Missingness
- Duplicate Analysis Unit
- Sample Size
- Treatment Prevalence
- Post-treatment Check
- Preliminary Overlap
- Extreme Propensity Risk

### 9.5 Estimation能力

- 二値TreatmentのATE / ATT
- Identification Result参照
- Estimator Capability Validation
- Treatment EffectとDiagnosticsの分離

### 9.6 Refutation能力

- Placebo Treatment
- Data Subset

### 9.7 Sensitivity能力

- Adjustment Set Variation
- Propensity Clipping Threshold Variation

## 11. ENH-E1 E2E処理フロー

### 11.1 Discovery / Graph Registration

1. Dataset Versionを選択する
2. Discoveryを実行するかGraphを直接登録する
3. Graph ResultとProvenanceを比較する
4. Graph Versionを作成・修正・固定する

### 11.2 Identification-first Inference

1. FIXED Graph Versionを選択する
2. Research Context、Causal Question、Causal Designを固定する
3. Identificationを実行する
4. Data Eligibilityを確認する
5. Gate通過時のみEstimationを実行する
6. Treatment EffectとDiagnosticsを比較する
7. Refutation / Sensitivityを実行する
8. Annotationを記録する
9. Lineageを確認する

### 11.3 非識別

Identification Executionは`SUCCEEDED`、Identification Resultは`NOT_IDENTIFIED`とし、通常Estimationを禁止する。
## 12. 基本設計上の受入れ条件

- 4 Workspaceを維持してENH-E1を実現できる
- IdentificationをEstimator選択前に実行できる
- 非識別Resultを正常保存できる
- Data Eligibility Gateが機能する
- 上流Result参照からLineageを生成できる
- Graph OriginとEndpoint Semanticsを保持できる
- User-defined / Imported Graphを使用できる
- Refutation / Sensitivityを独立Executionとして扱える
- 新しい主要Entityを追加していない
- External Backend型をProduct層へ漏らしていない
- 実装から要件定義書を更新していない
