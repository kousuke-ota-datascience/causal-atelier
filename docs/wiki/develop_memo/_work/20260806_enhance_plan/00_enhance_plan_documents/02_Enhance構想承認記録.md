## 1. 承認対象

### 1.1. 計画識別子

```text
ENH-E1
```

### 1.2. 計画名称

```text
科学的妥当性基盤強化
```

### 1.3. 対象範囲

Enhance構想、要件定義書改定、各設計書改定、要件・設計トレーサビリティ確認および実装指示書作成までを対象とする。

実装および本番リリースは本承認の対象外とする。

## 2. 承認事項

以下を承認事項として扱う。

1. Enhance計画を科学的方法論要求と旧アーキテクチャ実装指示に分離する
2. 科学的方法論要求を現行MVPへ再写像する
3. 主要Entityを7件のまま維持する
4. Execution Snapshotモデルを維持する
5. Identification、Refutation、SensitivityをExecution Operationとして追加する
6. Data EligibilityおよびDiagnosticsをResultとして表現する
7. Research Context等を現時点で独立Resource化しない
8. 要件・設計文書を実装より先に更新する
9. 文書間整合性確認後に実装指示書を作成する
10. 実装から要件定義書を更新しない
11. 既存コードはAs-Is調査対象であり、To-Be要件の根拠とはしない
12. 旧Enhance Coding Instructionを現行MVPへ直接適用しない

## 3. 条件付き承認事項

### 3.1. CPDAG／PAG

CPDAGまたはPAGに対して自動識別できない場合、恣意的にDAG化せず`REQUIRES_REVIEW`とすること。

### 3.2. 外部Scientific Backend

DoWhy、causal-learn等の外部型をProduct Domainへ漏らさないこと。

### 3.3. Refutation

Refutation成功を識別仮定の証明として表示しないこと。

### 3.4. Sensitivity

Sensitivity Resultを因果効果の真実性の証明として表示しないこと。

### 3.5. Graph Provenance

Graph編集後のResultをAlgorithm Outputと混同しないこと。

### 3.6. Validation Override

`WARN` overrideを無記録で許可しないこと。

### 3.7. Migration

旧DBデータ保持を目的とした複雑な互換層を作らないこと。

## 5. 承認の前提

### 5.1. 文書優先順位

以下の順序を維持する。

```text
要件定義書
→ 基本設計書
→ データモデル定義書
→ インターフェース設計書
→ 詳細設計書
→ 実装指示書
→ 実装
→ 検証
```

### 5.2. 変更統制

実装時に要件不足または設計矛盾が判明した場合、Coding Agentが独自判断して補完してはならない。

以下の手順へ戻る。

```text
変更提案
→ 承認
→ 要件定義書更新
→ 下位設計更新
→ トレーサビリティ再確認
→ 実装指示書更新
→ 実装再開
```

## 6. 承認再審議条件

以下の場合、本承認を再審議する。

1. 7 Entityでは承認済み要件を満たせないことが実証された
2. Result Typeの増加により一貫したValidationが不可能になった
3. 単一`input_result_id`ではLineageを正確に表現できない
4. CPDAG／PAGの意味保持が現行Graph表現では不可能である
5. ENH-E1の実装規模が初期価値検証の目的を損なう
6. 科学ベンチマークで既存推定器の重大な不整合が確認された
7. 要件と設計の間に未解消の矛盾が発見された
8. 実装指示書に設計書で定義されていない要求が混入した
