# 0. Ariadne Product Concept

## 0.1. Product Concept

> **分析の目的・前提・手法・実行・結果・解釈を一連の構造として保持し、
> 「何を根拠に、どこまで主張できるか」を追跡可能にする分析基盤**

分析結果だけを残しても、その結果がどのようなビジネス課題 / 問い・前提・判断から生まれたのかは分からない。

また、分析の妥当性は結果の数値だけではなく、前提や検証方法にも依存する。

Ariadneでは、結果だけでなく、その前後にある分析プロセス全体を一体として扱う。

つまり、

> **分析を「結果」ではなく「検証可能なプロセス」として扱う**

---

## 0.2. 本質的価値と現行プロダクト構成

> **Ariadneの本質は分析プロセスを構造化することだが、その価値を具体的に利用できる形として、現在は3つの分析ファミリを提供している**

「分析の目的・前提・履歴を管理する」という価値は抽象度が高く、それだけでは利用者に具体的な利用場面が伝わりにくい。

そこで現行プロダクトでは、

* **Exploratory**：データを理解し、仮説を探索する
* **Predictive**：未知・将来の値を予測する
* **Causal**：介入・施策の効果を推定する

という異なる分析アプローチを、共通の `Planning → Execution` モデル上で扱えるようにしている。

| ビジネス課題 / 問い     | 主に対応する分析    |
| --------------- | ----------- |
| 「現状、何が起きているのか」  | Exploratory |
| 「今後、何が起こりそうか」   | Predictive  |
| 「施策を行うと何が変わるのか」 | Causal      |

> **一つのビジネス課題 / 問いを、探索・予測・因果という複数の観点から包括的に扱えることが、現行プロダクトにおける具体的な価値の見せ方**

ただし、この3分析ファミリ自体がAriadneの本質ではない。

# 1. Ariadneが解決する課題

## 1.1. 分析業務における典型的なプロセスと課題

> **分析業務の本質は「計算」だけではなく、計算の前後にある多数の判断にある**

* 分析の最終結果は、ビジネス課題 / 問いの設定、前提、手法選択など、それ以前の判断の積み重ねによって決まる
* 一方、実務ではビジネス課題 / 問いや手法選択の理由、前提条件などが、最終的な報告資料に十分残らないことがある
* その結果、「どの課題 / 問いのもとで、何を分析し、何が得られたため、この結論に至ったのか」という流れが失われやすい

| 分析プロセス      | そこで行う判断            |
| ----------- | ------------------ |
| ビジネス課題 / 問い | 何を明らかにし、何を意思決定したいか |
| 分析上の問い      | 何を分析すれば答えられるか      |
| データ・変数      | 何を使って分析するか         |
| 前提条件        | 何を仮定するか            |
| 分析手法        | どの手法を使うか           |
| 実行          | 何を計算するか            |
| 診断・比較       | 結果はどの程度妥当か         |
| 解釈          | 何が言えて、何が言えないか      |
| ビジネス上の主張    | 意思決定にどうつなげるか       |

---

## 1.2. 分析情報の分散

> **一つの分析を構成する情報が、複数の場所や人に分散している**

分析コードだけを見ても、どのビジネス課題 / 問いに答えるための分析なのかは分からない。

一方、分析の背景や判断理由はコードとは別の場所に残されることが多く、分析結果との対応関係が失われやすい。

| 分析に必要な情報 | 実際に存在する場所の例             |
| -------- | ----------------------- |
| 分析コード    | Notebook / Source Code  |
| 前提・条件    | 文書 / PowerPoint         |
| 議論・判断理由  | Slack / Email / Meeting |
| 結果の解釈    | Report / Presentation   |
| 選択理由・暗黙知 | 分析者の頭の中                 |

> **結果と、その結果に至った判断過程を一体として残す仕組みが必要になる**

---

## 1.3. 分析プロセス分断による問題

> **分析プロセスが分断されると、分析の再現・比較・再利用・説明が難しくなる**

情報が残っていても、それぞれが独立して管理されていると、後から一つの分析として再構成する必要がある。

担当者が変わった場合や、過去の分析を別案件で再利用する場合には、この問題がより顕在化する。

| 問題      | 具体的に起こること         |
| ------- | ----------------- |
| 根拠の追跡   | なぜその分析をしたのか分からない  |
| 前提の確認   | どの前提に依存した結果か分からない |
| 手法選択の説明 | なぜその手法を選んだか分からない  |
| 再現      | 他の分析者が同じ分析を再現しにくい |
| 再利用     | 類似する分析を毎回作り直す     |
| 説明      | 結果だけが独り歩きする       |

> **Ariadneでは、分析結果ではなく「分析プロセス」を管理単位とする**

# 2. Product Principles

## 2.1. 主張と前提の関係

> **あらゆる分析結果から導かれる主張には、前提が伴う。強い主張には強い前提が伴う**

* 同じデータを分析しても、置く前提によって導ける結論は変わり得る
* 特に因果関係などの強い主張には、その主張を成立させる追加の条件・前提が必要になる
* したがって、高い精度や強い結論だけをもって、良い分析とは判断できない

| 分析結果だけを見る場合   | Ariadneで重視すること      |
| ------------- | ------------------- |
| 「この結果が得られた」   | どの前提から得られた結果か       |
| 「精度が高い」       | 前提・検証方法は妥当か         |
| 「効果がある」       | どの条件下で、その主張が成立するか   |
| 「最も強い結論を採用する」 | 結論の強さに見合う前提が成立しているか |

> **「この結果が正しい」ではなく、
> 「この前提のもとでは、ここまで主張できる」と扱う**

---

## 2.2. 分析アルゴリズムに対する基本方針

> **分析アルゴリズム単体の性能競争を、Ariadneの主戦場にはしない**

scikit-learn、DoWhy、EconMLなど、分析アルゴリズムについては成熟した既存ライブラリが存在する。

これらと同じ土俵で「より多くの独自アルゴリズム」「より高い単一指標上の精度」を競っても、持続的な差別化にはつながりにくい。

さらに、AriadneのProduct Principlesから見ても、分析品質はアルゴリズムの精度だけでは決まらない。

| 既存技術を活用する領域 | Ariadneが価値を置く領域 |
| ----------- | --------------- |
| 統計アルゴリズム    | ビジネス課題 / 問いの整理  |
| 機械学習アルゴリズム  | 分析設計            |
| 因果推論アルゴリズム  | 前提条件の管理         |
| 推定・予測処理     | 手法・条件間の比較       |
| 数値計算        | 結果の解釈・根拠の追跡     |

> **良いアルゴリズムを自らすべて作るのではなく、
> 良いアルゴリズムを適切に選び、検証し、解釈できる仕組みに価値を置く**

---

## 2.3. 分析プロセスの一体管理

> **Ariadneが扱う単位は、個々のアルゴリズムではなく、一連の分析プロセスである**

同じ分析手法を使っていても、ビジネス課題 / 問い・前提・データ・解釈が異なれば、その分析が意味するものは異なる。

したがって、計算処理だけを再利用しても、分析そのものを再利用したことにはならない。

| 構成要素        | 保持する内容        |
| ----------- | ------------- |
| ビジネス課題 / 問い | 何を明らかにしたいか    |
| 分析上の問い      | 何を分析すれば答えられるか |
| 前提          | 何を仮定するか       |
| データ         | 何を使うか         |
| 手法          | どう分析するか       |
| 実行          | 何を実行したか       |
| 診断          | 妥当性をどう確認したか   |
| 結果          | 何が得られたか       |
| 解釈          | 何を主張するか       |

> **分析の目的から結論までを一つの単位として管理し、再現・比較・再利用できるようにする**

# 3. Analysis Workflow

## 3.1. Planning → Execution

> **Ariadneでは、分析を `Planning → Execution` の二段階で構造化して扱う**

Planningでは、ビジネス課題 / 問いに対して、

* 何を分析するか
* どの前提を置くか
* どの手法を使うか
* どのような順序で実行するか

を定義する。

Executionでは、そのPlanに基づいて実際の処理を行い、結果・診断・履歴をPlanへ紐付ける。

| Planning    | Execution        |
| ----------- | ---------------- |
| ビジネス課題 / 問い | 分析処理の実行          |
| 分析上の問い      | 実行結果             |
| 前提条件        | 診断結果             |
| 手法選択        | 実行履歴             |
| 実行計画        | Error / Metadata |

> **「何をする予定だったか」と「実際に何をしたか」を分離しつつ、相互に追跡できるようにする**

---

## 3.2. 現在の分析ファミリ

> **現在は、ビジネス課題 / 問いを異なる角度から扱う3つの分析ファミリを提供している**

| Analysis Family | 主な役割        | 代表的な問い         |
| --------------- | ----------- | -------------- |
| **Exploratory** | データの理解・仮説探索 | 「何が起きているのか？」   |
| **Predictive**  | 未知・将来の結果の予測 | 「何が起こりそうか？」    |
| **Causal**      | 介入・施策の効果推定  | 「何をすると何が変わるか？」 |

3つを別々のプロダクトとして扱うのではなく、同じPlanning → Executionモデルの上で利用する。

> **一つのビジネス課題 / 問いに対して、探索・予測・因果という異なる分析アプローチを組み合わせられる**

---

## 3.3. 分析結果の比較と安定性

> **一つの結果を正解とみなすのではなく、前提や手法を変えても結論が維持されるかを確認する**

ある一つの分析で得られた結果だけでは、その結論が特定の前提や手法に強く依存しているか判断できない。

前提や手法を変更した場合にも同様の結論が得られるのであれば、より安定した主張として扱える。

| 前提   | 手法   | 得られた結果 |
| ---- | ---- | ------ |
| 前提 A | 手法 1 | 結果 A   |
| 前提 B | 手法 1 | 結果 B   |
| 前提 A | 手法 2 | 結果 C   |

> **条件変更による結果の変化そのものを、分析結果の一部として扱う**

---

## 3.4. Analysis Workflowの拡張性

> **AriadneのWorkflowは、Exploratory / Predictive / Causalの3種類に限定されない**

Ariadneの中核は、特定の統計手法ではなく `Planning → Execution` という実行モデルにある。

そのため、Planningで実行内容を記述し、Execution側の実装層を追加できれば、既存の分析ファミリ以外の処理もWorkflowへ組み込める。

| 現在             | 将来              |
| -------------- | --------------- |
| Exploratory    | 新しい分析ファミリ       |
| Predictive     | 顧客固有の分析処理       |
| Causal         | 外部ツール / Program |
| 既存のExecution実装 | 新しいExecution実装  |

実際に新しい処理を追加する際には、末端のExecutionを担う実装クラスを追加する必要がある。

しかし、上位のPlanning・履歴管理・結果との関連付けという仕組みは共通して利用できる。

> **Ariadneは「3種類の分析ツール」ではなく、
> Planning → Executionに適合する処理を拡張可能な分析Workflow基盤として設計されている**

# 4. System Positioning

## 4.1. Analysis ContextとExecutionの分離

> **Ariadne自身が、すべての分析計算を実行する必要はない**

多くの企業には、既にデータベース、データレイク、分析基盤、計算環境が存在する。

Ariadneがそれらすべてを置き換えることを前提にすると、既存投資との重複やデータ移動が発生し、導入障壁が大きくなる。

| Ariadneが担う領域      | 既存基盤でも担える領域   |
| ----------------- | ------------- |
| ビジネス課題 / 問い       | データ処理         |
| 前提条件              | SQL実行         |
| 分析設計              | Python実行      |
| Analysis Workflow | Spark処理       |
| 実行履歴              | 統計・機械学習処理     |
| 結果との対応            | 計算資源          |
| 結果の解釈             | Job Execution |

> **「分析をなぜ・どう行ったか」と、「実際にどこで計算したか」を分離して扱う**

---

## 4.2. 外部データ・分析基盤との接続

> **Databricks等の既存基盤を活用し、その上で行われる分析の目的と履歴をAriadneが管理する**

例えばDatabricks上にデータと分析処理が既に存在する場合、計算をAriadne側へ移す必要はない。

分析コードや実行結果を外部基盤に残したまま、それらをAriadne上のビジネス課題 / 問い・前提・解釈と関連付けられればよい。

| 項目               | 方針                     |
| ---------------- | ---------------------- |
| データ              | 既存基盤上にあってよい            |
| 計算資源             | 既存基盤を利用してよい            |
| 分析コード            | 外部基盤で実行してよい            |
| 実行結果             | Ariadneから参照・関連付けできればよい |
| Analysis Context | **Ariadneが保持する**       |

想定する接続先：

* Databricks
* Data Lake / Lakehouse
* Analytics Platform
* 顧客固有の計算環境

> **既存のData / Compute基盤と競合するのではなく、その上位で分析を構造化する**

---

## 4.3. Analysis Context / History

> **究極的には、Ariadne自身が分析を実行しなくても、分析の目的と履歴を保持できればよい**

計算処理そのものは、既存ライブラリや分析基盤によって代替できる。

一方、「なぜその分析を行ったのか」「どの前提で実行したのか」「その結果をどう解釈したのか」は、実行環境が変わっても必要になる。

| Ariadneが残すべき問い | 保持する情報   |
| -------------- | -------- |
| なぜ？            | 何のための分析か |
| 何を？            | 何を分析したか  |
| どの前提で？         | 何を仮定したか  |
| どうやって？         | 何を実行したか  |
| 何が起きたか？        | 何が得られたか  |
| だから何か？         | 何を主張したか  |

> **Ariadneを「独自のAnalysis Engine」ではなく、
> Analysis Contextと履歴を管理するレイヤーとして位置づける**

---

# 5. Interfaces

## 5.1. Interface構成

> **同じAriadneの機能を、利用者・利用形態に応じて異なるInterfaceから利用する**

分析者が対話的に使う場合と、エンジニアがシステムへ組み込む場合では、必要なInterfaceが異なる。

そのため、Ariadneの中核機能自体は共通化しつつ、複数の利用方法を提供する。

| Interface      | 主な利用者 / 利用主体                             | 主な用途              |
| -------------- | ---------------------------------------- | ----------------- |
| WebUI          | 分析者 / Data Scientist / Reviewer          | 対話的分析、確認、可視化      |
| CLI / Codebase | Engineer / SI担当者                         | Script、Batch、組み込み |
| Web API        | Application / Workflow Engine / AI Agent | 分析機能の呼び出し         |

---

## 5.2. WebUI

> **WebUIは、人がAriadneの分析モデルを操作・確認するためのInterfaceとして位置づける**

分析者がAnalysis Processを直接操作したり、レビュー担当者が分析内容を確認したりする場合には、視覚的なInterfaceが有効になる。

一方で、Ariadneの価値自体をWebUIに依存させる必要はない。

| 項目       | 内容                              |
| -------- | ------------------------------- |
| 主な利用者    | 分析者 / Data Scientist / Reviewer |
| 用途       | 対話的分析                           |
| 確認対象     | Analysis Workflow / Result      |
| 事業上の用途   | PoC / Demonstration             |
| 現時点の位置づけ | 人がAriadneを利用・確認するための入口          |

> **現時点ではWebUI自体を主要な商品化対象とは位置づけない**

---

## 5.3. CLI / Codebase・Web API

> **CLI / CodebaseとWeb APIは、Ariadneの分析機能を他のSystem / Solutionへ組み込むためのInterfaceとなる**

顧客の利用環境によって、コードとして直接組み込みたいケースと、Serviceとして呼び出したいケースが存在する。

また、どちらの場合もAriadne専用のWebUIを利用する必要はない。

|        | CLI / Codebase   | Web API                |
| ------ | ---------------- | ---------------------- |
| 主な利用主体 | Engineer / SI担当者 | Application / AI Agent |
| 利用形態   | コードとして組み込む       | Serviceとして呼び出す         |
| 統合単位   | Code Level       | API Level              |
| 主用途    | SI Solution      | System Integration     |

# 6. Productization

## 6.0. 商品化方針サマリ

> **Ariadne単独で新しい商品化プロセスを作るのではなく、既存の「再利用可能なSI Componentを商品化する」取り組みに合流しながら、WebUI / Web API / CLI・Codebaseの3方向で商品価値を検証・形成する**

- Ariadneは既存の商品化活動とは別系統で立ち上がったため、社内で既に検討されている商品化プロセスとの接続が必要
- 既存プロセスでは、SI案件で利用した技術資産を **再利用可能コンポーネント** として整理し、他案件でも利用可能にする方向を検討している
- Ariadneの商品化First Stepも、この考え方に合わせる
- 一方でAriadneにはWebUIという顧客接点があるため、Component化だけでなく、商談・PoC・社内利用を通じてUser-facingな価値も並行して育てる
- Web APIは既にWebUIから利用されているため、API自体を新たに作るのではなく、将来的な外部提供を見据えてInterface・接続性・運用品質を成熟させる

### 商品化対象の全体像

| 機能開発優先順位 | 外販商品化優先順位 | 対象 | 提供するもの | 主な利用場面 |
|---:|---:|---|---|---|
| 1 | N/A (*1) | **WebUI** | 分析設計・実行を支援する対話型Interface | 商談Demo / PoC / 社内利用 |
| 3 (*2) | 2 | **Web API** | AriadneのAnalysis Capability | 顧客System / Application / 外部Platformからの利用 |
| 2 | 1 | **CLI / Codebase** | Analysis Model / Workflow / 再利用可能コンポーネント | SI Solutionへの組み込み |

(*1) WebUIは「顧客から直接対価を得て提供する商品」としての優先度は低い。一方、社内Consultantによる利用、商談・PoCへの活用を通じてオファリング売上へ貢献するため、機能開発優先度は高い。

(*2) WebUI自体がWeb APIを利用して成立しているため、APIの基本機能もWebUI開発と並行して成熟する。優先度3は、Databricks等の外部Platformから直接利用するためのInterface標準化・接続検証を後順位とする意味。

---

## 6.1. 既存の商品化プロセスとの合流

> **Ariadneの商品化を独自路線で進めるのではなく、既に社内で検討されている「SI資産のComponent化」の枠組みに載せる**

### 背景

- 社内では既に、案件ごとに開発した技術資産を再利用可能なComponentへ変える商品化プロセスが検討されている
- Ariadneはこの検討とは別系統で立ち上がったため、そのままでは組織的な商品化プロセスから外れる可能性がある
- 特にCLI / Codebaseは、既存のComponent化プロセスとの親和性が高い
- 既存の仕組みに合流することで、Ariadne独自の商品化プロセスを新たに構築するコストを抑えながら、社内での再利用・展開を進められる

### 商品化の基本的な流れ

```text
個別SIでの利用
    ↓
共通部分の抽出
    ↓
再利用可能コンポーネント
    ↓
他案件で再利用
    ↓
標準化・商品化
```

> **既存の商品化プロセスを、Ariadneの市場投入・再利用拡大のレールとして利用する**

---

## 6.2. Productization First Step

> **Planning → Executionモデルに基づき、予測・最適化などの分析処理を再利用可能なWorkflowとして実行・管理できるComponentを構築する**

### First Stepとしてこれを選ぶ理由

- 既存の商品化プロセスが求める「SIで再利用可能なComponent」という形に合わせやすい
- チームが既に持つPredictive / OptimizationのSkillを直接利用できる
- 性質の異なる処理を同じPlanning → Executionモデルで扱うことで、Ariadneの拡張性を実証できる
- SI案件で実際に利用することで、どの分析処理に再利用価値があるかを検証できる
- 将来的なWeb API化に必要となるInput / Output・実行条件の標準化にもつなげられる

### 初期対象

| 処理 | Planning | Execution |
|---|---|---|
| **Predictive** | Target / Features / Model / Metrics / Validation | Train / Evaluate / Predict |
| **Optimization** | Objective / Decision Variables / Constraints / Solver | Build / Solve / Evaluate |

PredictiveとOptimizationは処理内容が大きく異なる。

この2つを同じPlanning → Executionモデルで扱えることを確認することで、Ariadneが特定の分析Familyに依存しないFrameworkであることを実装面から検証する。

### First Stepのゴール

> **「Ariadneの分析機能を増やす」のではなく、「次の案件でも再利用できるAriadne Component」を作る**

## 6.3. WebUIの機能完成度向上

> **WebUIは商談・PoCで初期段階から活用するとともに、社内Consultantに使い込んでもらうことで、人が使うAriadneとしての価値を作り込む**

### 想定する役割

| 利用場面 | 狙い |
|---|---|
| 商談Demo | 顧客関心の喚起 |
| PoC | 分析着手・実行の効率化 |
| PoC成果物 | 分析品質の高水準での平準化 |
| 社内利用 | UI / 分析支援機能の改善 |

### 想定する主要User

> **プログラミングスキルは専門エンジニア / Data Scientistほど高くない一方で、仮説立案・顧客課題整理に長けたConsultant**

このUser層に対して、以下を実現できるかを検証する。

- コードを書かずに分析設計を進められるか
- ビジネス課題 / 問いを適切な分析へ落とし込めるか
- 仮説に応じて適切な分析手法を選択できるか
- 分析結果を顧客への説明・提案へつなげられるか
- 個人のプログラミングスキルに依存せず、一定水準のPoCを実施できるか

### 商品化上の位置づけ

WebUIは、現時点では単独で直接販売するSaaSとしての優先度は高くない。

一方で、

- 商談時の顧客関心の喚起
- PoC実施コストの低減
- PoC品質の平準化
- ConsultantによるAriadne利用の拡大
- 実利用Feedbackを通じたProduct Discovery

という役割を持つ。

> **WebUIは「完成してから売る」のではなく、社内利用・商談・PoCを通じてProductとしての価値を形成していく**

---

## 6.4. CLI / Codebaseの商品化

> **CLI / Codebaseは、既存の商品化プロセスに最も直接的に合流するSI組み込み用Componentとして育てる**

### 主な用途

- SI Solutionへの組み込み
- Predictive / Optimization等の分析処理の再利用
- 顧客固有Workflowへの適用
- 案件間での共通実装の再利用
- Planning → Executionモデルを利用した分析処理の標準化

### 目指す状態

```text
案件A ─┐
案件B ─┼→ 共通Analysis Component → Ariadne
案件C ─┘
```

案件ごとに全てを作り直すのではなく、

- 共通化可能な分析処理
- Planning / Executionの構造
- 実行・評価・履歴管理

をAriadne Componentとして再利用する。

一方、顧客固有の業務ロジックやIntegrationのみを個別SIとして実装する。

> **共通部分はAriadne Component、顧客固有部分は個別SI、という役割分担を目指す**

## 6.5. Web APIの商品化

> **WebUIを支えるWeb APIを、将来的には顧客System / Application / 外部Platformから直接利用可能なAnalysis Serviceとして商品化する**

Ariadneでは既にWebUIからWeb APIを利用しており、Analysis CapabilityをAPI経由で呼び出す基本構造は存在する。

したがって、Web APIの商品化では「APIを新たに作る」ことよりも、外部から安定的に利用できる商品へ成熟させることが中心となる。

### 外部提供に向けて成熟させる領域

- Input / Output仕様
- Interfaceの標準化
- Error Handling
- Authentication / Authorization
- 利用単位・実行単位
- 外部Systemからの呼び出し方式
- Databricks等の外部Platformとの接続
- Serviceとしての運用・監視

### 主な利用主体

- 顧客System
- Application
- Workflow Engine
- AI Agent
- Databricks等の外部Analytics Platform

### Productizationの考え方

```text
WebUI開発
    ↓
Web APIの基本機能も成熟
    ↓
SI / PoCでAnalysis Capabilityを利用
    ↓
Input / Output・利用方法を標準化
    ↓
外部System / Platformとの接続を検証
    ↓
External Analysis Service
```

> **APIそのものを後から作るのではなく、既存APIを「外部から安心して利用できる商品」へ成熟させる**

## 6.6. 3つの商品化対象の役割分担

> **WebUI / Web API / CLI・Codebaseは競合する商品形態ではなく、それぞれ異なる顧客接点・利用形態・商品化プロセスを担う**

| 対象 | 主なUser / 利用主体 | 主な価値 | 商品化の進め方 |
|---|---|---|---|
| **WebUI** | Consultant / Analyst | 分析設計・PoC支援 | 社内利用・商談・顧客案件で磨く |
| **CLI / Codebase** | SI Engineer / Developer | Analysis Componentの再利用 | 既存Component化プロセスへ合流 |
| **Web API** | System / Application / Agent | 標準化されたAnalysis Capability | 既存APIを外部利用可能なServiceへ成熟させる |

### 全体像

```text
                         ┌─ WebUI
                         │  Consultant / 商談 / PoC
                         │  ↓
                         │  UX・分析支援機能を改善
                         │
Ariadne Core ────────────┼─ CLI / Codebase
Planning → Execution     │  SI 再利用可能コンポーネント
                         │  ↓
                         │  既存商品化プロセスへ合流
                         │
                         └─ Web API
                            WebUI内部では既に利用
                            ↓
                            外部利用要件を標準化・検証
                            ↓
                            External Analysis Service
```

> **SIで再利用可能コンポーネントを育て、WebUIでUser-facingな価値を磨き、Web APIを外部利用可能なServiceへ成熟させる**

Ariadneの商品化は、単一の一本道ではなく、3つの経路を並行して進める。

```text
                         ┌→ WebUI
                         │  社内Consultantによる利用
                         │  商談・PoCでの活用
                         │  ↓
                         │  UX / Analysis Supportを改善
                         │
SI Project ─→ 再利用可能コンポーネント
                         │
                         ├→ CLI / Codebase
                         │  他SI案件へ再利用
                         │  ↓
                         │  Componentとして商品化
                         │
                         └→ Analysis Capability
                                    ↓

                                    ↓
                         External Analysis Service
```

### Productization First Step

> **Planning → Executionモデルに基づくPredictive / Optimization等のAnalysis Componentを構築し、まずSIで「本当に再利用されるか」を検証する**

これをCLI / Codebaseの商品化につなげると同時に、実案件で得られる利用パターンをWeb APIの外部提供仕様へ反映する。

その一方で、

> **WebUIは初期段階からConsultant・商談・PoCで利用し、「人が使うAriadne」としての価値を並行して作り込む**

# 7. Go-To-Market

## 7.1. Product Core ValueとMarket Entry Point

> **Ariadneの本質的な価値と、顧客が最初に購入する理由は一致しなくてよい**

Ariadneとして長期的に実現したいのは、Analysis Processの構造化や追跡可能性である。

一方、顧客が実際に予算を付けるのは、「分析に時間がかかる」「属人化している」といった、より具体的な業務課題である可能性が高い。

| Product Core Value   | 顧客が認識しやすい初期課題  |
| -------------------- | -------------- |
| Analysis Processの構造化 | 分析工数が大きい       |
| 前提の明示                | 品質が人に依存する      |
| 根拠の追跡性               | レビューが難しい       |
| 再現性                  | 説明責任が重い        |
| Analysis Contextの蓄積  | 同じ分析を何度も実装している |

> **Productとして目指す価値は維持しつつ、市場には具体的な業務課題から入る**

---

## 7.2. SIを活用したProduct Discovery

> **既存SI案件を、顧客価値と商品化可能性を検証する場として利用する**

SIerとして既に顧客・実データ・実課題への接点を持っている。

この接点を利用すれば、机上で市場仮説を作るだけでなく、実際の案件で「どこに価値があるか」を確認できる。

| 段階          | 検証すること                        |
| ----------- | ----------------------------- |
| 顧客案件へ適用     | どんな課題があるか                     |
| 効果を測定       | 何がどれだけ改善するか                   |
| Patternを抽出  | 他案件でも再利用できるか                  |
| Component化  | SI部品として成立するか                  |
| Standardize | API化できるAnalysis Capabilityは何か |
| Productize  | 継続的に販売できるか                    |

> **SIそのものをゴールとせず、商品化できる共通部分を発見するために利用する**

---

## 7.3. Productization Path

> **SI案件で見つけた再利用可能な分析Patternを、Component化・標準化し、Productへ発展させる**

最初から汎用品として設計すると、実際の顧客課題と乖離したものを作るリスクがある。

まず実案件で利用し、複数案件で繰り返し使われる部分を確認した上で、徐々に個別案件への依存を減らす。

| 段階                              | 位置づけ              |
| ------------------------------- | ----------------- |
| SI Project                      | 個別顧客の実課題を解く       |
| Reusable Component              | 複数案件で再利用する        |
| Standardized Capability         | 個別案件への依存を減らす      |
| Web API / Productized Component | 継続販売可能なProductにする |

> **SIとProductを二者択一にせず、SIからProductへ連続的に発展させる**

---

## 7.4. 商品形態とCustomer Value

> **「何を売るか」と「なぜ顧客がお金を払うか」は分けて検証する**

Web APIやSI組み込みComponentは「商品をどう提供するか」という話である。

一方、顧客が実際に対価を払う理由は、工数削減・品質改善・標準化など、その先に生まれる業務上の価値にある。

| 商品として提供するもの         | 顧客が対価を払う可能性のある価値  |
| ------------------- | ----------------- |
| Web API             | 分析工数削減            |
| SI組み込みComponent     | 開発工数削減            |
| Analysis Capability | 高度分析の再利用          |
| Analysis Model      | 分析方法の標準化          |
| Workflow            | レビュー容易性           |
| Analysis History    | Governance / 説明責任 |

> **Pricingを決める前に、顧客が何に価値を感じるのかを検証する**

---

## 7.5. User / Integrator / Buyer

> **Ariadneを使う人と、Ariadneに予算を付ける人は必ずしも同じではない**

例えば、実際にAriadneを利用するのはData Scientistでも、購入判断をするのはProject OwnerやManagerである可能性がある。

また、Web APIの場合には、直接Ariadneを利用する主体が人間ではなくApplicationやAI Agentになることも考えられる。

| Role       | 想定例                      | 主な関心      |
| ---------- | ------------------------ | --------- |
| User       | Analyst / Data Scientist | 分析しやすいか   |
| Integrator | SI Engineer / Developer  | 組み込みやすいか  |
| Buyer      | Project Owner / Manager  | 投資対効果があるか |

> **User Valueだけでなく、Integrator Value・Buyer Valueまで分けて検証する**
