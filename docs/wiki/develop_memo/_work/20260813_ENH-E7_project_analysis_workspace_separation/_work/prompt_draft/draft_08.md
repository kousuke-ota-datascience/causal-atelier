もともとは以下がworkflowtemplate整備の思想だったはず。

設計、実装、テストを分離することでトークン消費量を抑える
コーディングエージェントに、いろんなドキュメントを探させない。トークン消費を抑え、コードの質を上げるため。
ファイルを介したやり取りにすることで、追跡性を上げる。なので、 workpackage 間や、 Gate 間でファイルを出力し、それを足がかりにして次のステップに行くのは良い
要件定義書を常に正本にすることで、あるべきから外れないようにする
要件定義署を常に正本にすることで初見の人がシステムを見たときにわかりやすいようにする
そのエンハンスで何が変わったのか、一発でわかるようにする。要件定義〜詳細設計の差分から、どのようなコードを書くべきと決めたのか、その思考形跡をトレースできるようにする
ゲートに分けたのは、「コード改変による成果」単位で品質を保証するため。なのでGate単位でテストを実施
workpackageを導入したのは、1Gateの作業量が大きすぎた場合にエージェントが迷いなくコードを書くため


SHAを厳密に合わせるとか、プレイスホルダを許さないとか、厳密というよりも、過剰設計によるデメリットのほうが大きくなっていた
